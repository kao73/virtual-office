# virtual-office

Команда AI-агентов, ведущая разработку проекта-клиента через его трекер.
Человек участвует в фиксированных точках, а не в каждом шаге.

Замысел и архитектурные решения — `docs/DESIGN.md`, это источник истины.

Сделаны четыре этапа. Первый дал запуск агента в роли: команда получает роль
и рабочую папку, а возвращает машиночитаемый результат. Второй обстроил её
конвейером: раннер берёт задачу из трекера, готовит worktree, зовёт агента,
публикует ветку, пишет отчёт в тикет и двигает задачу по графу — на файловом
трекере и на настоящей JIRA Server 8.13.

Третий сделал ролей две. `implementer` работает, `reviewer` разбирает
сделанное и либо возвращает работу автору, либо отправляет её в `Approved` —
это значит «разбор пройден», и дальше задачу ведёт PR-проход. Править код reviewer не может — у него нет
инструментов записи, кроме собственного отчёта. Круги «правки → ревью» ограничены,
расход прогонов учитывается и при желании ограничивается, сеть роли задаётся списком
доменов в её спецификации. Живые прогоны обоих трекеров — `docs/notes/stage-3-smoke.md`.

Четвёртый добавил третью роль — `analyst` — и вместе с ней замысел как артефакт:
план задачи живёт не в отчёте, а в ветке, каталогом `docs/changes/<KEY>/`. Спорную
постановку роль превращает в **типизированный вопрос**, на который человек отвечает
одним словом. Что роли положено писать и куда, проверяет не доверие, а ограждение.
Семь задач тремя ролями за 76 минут — `docs/notes/stage-4-load-2.md`.

## Что нужно на машине

| Инструмент | Зачем |
|---|---|
| Go 1.26+ | раннер |
| `git` | рабочая папка агента — git-репозиторий |
| `sbx` | Docker Sandboxes: изоляция прогона, бэкенд по умолчанию |
| `claude` | агент; нужен только бэкенду `local` |
| `python3`, `uv` | инструменты учебной задачи smoke-теста, не раннера |

Авторизация агента — переменной окружения, `ANTHROPIC_API_KEY`
или `CLAUDE_CODE_OAUTH_TOKEN`; оба пути описаны в `docs/notes/auth.md`.
Секретов в репозитории нет и не будет: всё через окружение.

Своё хозяйство раннер держит в `${OFFICE_HOME:-~/.office}`.

## От нуля до первой задачи

Ниже — путь целиком, на файловом трекере. Он лежит в `${OFFICE_HOME}/mock`,
правится руками и нужен ровно за тем, чтобы отладить конвейер, не поднимая JIRA.

Настоящий заход — от чистой машины и пустой JIRA до задачи с открытым pull
request — описан отдельно и чек-листом: **`docs/ONBOARDING.md`**. Быстрый старт
ниже его не заменяет: он показывает, как офис работает, а тот проводит через
то, что для этого надо завести.

```sh
# 1. Клон и кред агента
git clone <repo> virtual-office && cd virtual-office
export CLAUDE_CODE_OAUTH_TOKEN='...'      # или ANTHROPIC_API_KEY

# 2. Репозиторий проекта-клиента. Годится любой; для пробы — локальный.
#    Пустого мало: ветку задачи раннер ответвляет от origin/<default_branch>,
#    и без единого коммита такой ссылки нет.
git init --bare -b master /tmp/client.git
git clone -q /tmp/client.git /tmp/client
git -C /tmp/client -c user.name=you -c user.email=you@local commit -q --allow-empty -m init
git -C /tmp/client push -q origin master

# 3. Назвать проект офису — projects.yaml в репозитории. Поставляемый файл
#    описывает полигоны ЭТОГО офиса (OFFICE и VO); заведя свой, замените их:
#    раннер требует машинную половину для КАЖДОГО названного проекта и без неё
#    не начинает цикл.
#    OFF:
#      default_branch: master
#      branch_prefix: agent/
#
# 4. Сказать, где он на этой машине. Каталога может ещё не быть:
mkdir -p "${OFFICE_HOME:-$HOME/.office}"
#    ${OFFICE_HOME}/projects.local.yaml
#    OFF:
#      repo_url: /tmp/client.git
#      tracker: mock          # чей проект: mock или jira
#      # forge не задан: локальный репозиторий, открывать PR негде

# 5. Завести задачу и отдать её офису — в очередь аналитика
./bin/runner mock add OFF-1 --status Analysis \
  --summary "Добавить hello.py" \
  --description "Создай hello.py, печатающий приветствие, и тест к нему. Закоммить."

# 6. Цикл по всем ролям: аналитик напишет план, разработчик сделает,
#    ревьюер разберёт. По задаче за роль за заход — значит трижды,
#    и ещё раз, чтобы системный проход закрыл задачу.
./bin/runner tick
./bin/runner tick
./bin/runner tick
./bin/runner tick

# 7. Посмотреть, что вышло
./bin/runner mock show OFF-1
git -C /tmp/client.git log --oneline agent/OFF-1
git -C /tmp/client.git show agent/OFF-1:docs/changes/OFF-1/tasks.md
```

Шестая команда делает всё: разбирает ответы человека на заблокированные задачи,
гоняет системный проход (pull request и уборка папок), берёт из очереди первую
годную задачу, захватывает её арендой, заводит worktree ветки `agent/OFF-1`
от свежего `origin/master`, собирает агенту постановку и контекст, запускает его
в песочнице, публикует ветку, пишет в тикет отчёт и двигает задачу по графу.
Не больше одной задачи на роль за цикл — так проще и останавливать, и разбирать.

Роль можно вызвать и по одной: `tick --role analyst`. Задача, заведённая сразу
в `Ready`, поедет без плана — офис не настаивает, чтобы у всякой работы был
аналитик.

Задача, на которой агент упрётся в неоднозначность, уедет в `Blocked` с вопросами
и атрибутом ожидания. Ответить можно тем же CLI:

```sh
./bin/runner mock comment OFF-1 "Берём Stripe, точка входа — payments/stripe.py"
./bin/runner tick --role implementer      # ответ попадёт в контекст следующего прогона
```

Вопросы приходят с метками, и отвечать на них можно одним словом — так короче
и так они точно попадут туда, куда нужно:

```
## Вопросы

Q1: Идемпотентность или скорость?
  a) идемпотентность
  b) скорость

Q2: Какой формат даты в экспорте?

Ответьте комментарием: `Q1: a`, `Q2: <текст>`; можно и прозой.
```

```sh
./bin/runner mock comment OFF-1 "Q1: b
Q2: ISO-8601"
```

Раннер разберёт ответ по меткам и положит его в контекст **той роли, которая
спрашивала**, — разобранным, вместе с текстом вопроса и подписью выбранного
варианта. Ответ мимо вариантов не отвергается: он придёт роли как есть, с пометкой.
Прозу тоже никто не теряет — она едет в контекст целиком, как ехала всегда.

Комментарий пишется от учётки `human`: раннер отличает голос человека от своего
по автору, а не по тексту. Свои учётки он знает наперечёт — общую (`office`)
и по одной на роль (`office-analyst`, `office-implementer`, `office-reviewer`), —
и всё, написанное не ими, считает словами человека.

Так же возвращаются и задачи, которые раннер заблокировал сам, — исчерпав попытки
или устав возвращать задачу, на которой прогон не доживает до отчёта. Ответом
считается любая реплика человека после последней записи офиса, и задача уходит
в очередь той роли, которая говорила последней. Отложить ожидающую задачу словами
нельзя: «давайте потом» вернёт её в работу, как и любой другой комментарий, —
для этого снимают атрибут ожидания.

### То же самое против JIRA

Отличий два: настроенный инстанс и флаг.

```sh
export JIRA_USER=admin JIRA_PASSWORD='...'
export JIRA_REVIEWER_USER=office-reviewer JIRA_REVIEWER_PASSWORD='...'
./bin/runner tick --tracker jira --role implementer
```

Подключение, соответствие статусов графа статусам JIRA, идентификаторы полей аренды
и раскладка учёток — в `${OFFICE_HOME}/tracker.yaml`; в репозитории лежит образец
`tracker.example.yaml`, из которого этот файл делают. В нём только имена переменных,
значения живут в окружении. В каком порядке всё это заводят и чем проверяют каждый
шаг — `docs/ONBOARDING.md`; почему именно так — `docs/notes/jira-setup.md`. Сам
инстанс, если своего нет, поднимается из `bootstrap/jira/`. Отдельная учётка для человека
обязательна: с одним аккаунтом ответ от вопроса не отличить. Учётки ролей — опция:
уберите `accounts.roles`, и всё поедет под общей.

Эмпирика REST, на которую стоит смотреть прежде документации, — `docs/notes/jira-api.md`.

### По расписанию

Раннер не демон и не supervisor: он не следит за собой и не перезапускается.
Расписание держит планировщик — примеры задания launchd и пары service+timer
для systemd лежат в `bootstrap/` вместе с объяснением, что и почему.

```sh
./bin/runner reap                  # вернуть задачи с истёкшей арендой
./bin/runner loop --every 2m       # цикл до сигнала, если планировщика нет
```

Посмотреть, что происходит прямо сейчас, — `runner ls`: доска целиком, по одному
запросу на проект.

```sh
./bin/runner ls                    # все проекты
./bin/runner ls --project OFFICE   # один
```

```
OFFICE-1  InProgress  implementer до 15:04:05  попыток:0                  12м  Добавить hello.py
OFFICE-2  Blocked     —                        попыток:3 [ждёт человека]  2д   Спорная постановка
```

Задачи с живой арендой из списка не выбрасываются — наоборот, ради них он и нужен:
«кто работает» видно по столбцу аренды, а «сколько висит» — по возрасту. Переписку
команда не тянет: она стоит запроса на задачу.

Во что это обходится — `runner ledger`. Каждый прогон пишется строкой в реестр
`${OFFICE_HOME}/ledger.jsonl`, и учёт ведётся всегда, настроены пределы или нет.

```sh
./bin/runner ledger                       # всё, что было на этой машине
./bin/runner ledger --since 24h --role implementer
```

```
прогонов: 3, сумма $0.4652, в среднем $0.1551
исходы: done 3
```

Реестр локален для машины: два раннера на один проект дадут две сводки. Общее для
всех место — тикет: цена прогона стоит последней строкой в его отчёте.

Деньги — не единственный предел. У подписки есть окно (пятичасовое, недельное),
и кончиться может оно, а не бюджет. Состояние окна раннер читает из лога прогона
и говорит о нём, когда есть что сказать: «на исходе» и «исчерпано». Прогон,
отвергнутый до первого шага, провалом агента не считается: работы не было — значит
нет и следа, а прогон без следа попытки не тратит. Отказ после работы след
оставляет, и там попытка тратится по делу. Нерешённым остаётся одно — пауза роли
до сброса окна; она решается по первому живому отказу (`docs/notes/budgets.md`).

Ограничить расход можно необязательным `budgets.yaml` — трёх видов и с режимом
на каждый: `per_task` (сумма по задаче), `per_role_daily` (роль за сутки), `per_run`
(один прогон). Файлов два: дефолты офиса в репозитории и накладка машины
в `${OFFICE_HOME}`, оба необязательны — нет ни одного, значит только учёт.
Режим по умолчанию — `warn`,
он говорит и не мешает работать. `stop` для `per_task` отдаёт задачу человеку,
для `per_role_daily` — оставляет роль без работы до конца суток. Прогон по цене
не прерывается вовсе: она известна, когда работа уже сделана, — жёсткая граница
у прогона своя, `limits.max_turns` в роли.

`reap` нужен потому, что аренда — lease, а не lock: раннера могли убить посреди
прогона, и задача осталась бы «в работе» навсегда. Reaper вернёт её в очередь,
объяснит это в тикете и сохранит рабочую папку — следующий прогон продолжит
с того же места. Счётчик попыток он при этом не трогает: смерть прогона — не провал
агента, и считается она отдельно, по маркерам в тикете. Если прогон не доживает
до отчёта раз за разом, человека позовут — но с другим разговором: дело не в агенте,
смотреть надо туда, где обрывается прогон. Заодно он сносит песочницу мёртвого прогона: та переживает
своего раннера и держит память и диск, пока её не уберут. Убирается ровно
та, чью аренду reaper вернул, — чужая живая песочница не его дело.

## Три роли и путь задачи

```
   человек        analyst      implementer     reviewer        человек
      │              │              │              │              │
   Backlog ──▶ Analysis ──▶ Ready ──▶ InProgress ──▶ Review ──▶ Approved ──▶ Done
                   ▲            ▲                      │  │
                   │            └─── возврат автору ───┘  │
                   └──────── возврат за планом ───────────┘
```

- **analyst** превращает постановку в план: `brief.md` (зачем и критерии приёмки),
  `design.md` (как и почему именно так), `tasks.md` (что делать, пункт — коммит).
  Кода не пишет;
- **implementer** работает по плану, отмечает сделанные пункты и коммитит на пункт.
  Расходится план с кодом — возвращает задачу аналитику, а не правит план сам;
- **reviewer** проверяет работу сначала против плана, потом по коду. Ничего
  не правит: инструментов записи у него нет.

`Backlog` — территория человека, офис туда не смотрит; задачу в работу отдаёт он,
переводя её в `Analysis`.

`Approved` означает «разбор пройден, pull request открыт», а не «готово».
Дальше работает системный проход — он безролевой, агента у него нет:

- открывает pull request веткой задачи, телом берёт `brief.md` из ветки
  и последний отчёт из тикета, ссылку кладёт комментарием;
- **сливает человек.** Офис за него этого не делает и на этом этапе делать
  не будет;
- слияние он видит сам и уводит задачу в `Done` — единственный терминальный
  статус;
- закрытый без слияния PR — разговор с человеком: задача уходит в `Blocked`,
  и ответ возвращает её в `Approved`, где PR открывается заново;
- **конфликт слияния — это работа, а не провал.** Задача возвращается
  разработчику в `Ready`, счётчик попыток не тратится, а тот же PR ждёт её
  возвращения. Считается конфликт локально, `git merge-tree` по bare-клону:
  ни сети, ни forge для этого не нужно.

Куда именно ведёт каждый из этих исходов, записано в `workflow.yaml` блоком `pr`
— как и весь остальной маршрут. У проекта без forge (например, у полигона
на локальном bare-репозитории) проход вырождается: задача уходит в `Done` сразу,
записью `pr-skipped`, потому что слияния не было.

Любая роль вправе увести задачу в `Blocked` — там она ждёт человека. Его ответ
возвращает задачу **той роли, которая спрашивала**, без промежуточных.

### Статус — не колонка

Раннер оперирует **статусами**: это узлы workflow самого трекера, и только они
записаны в `workflow.yaml`. **Колонка** — свойство доски, представление; досок
с разной раскладкой одних и тех же статусов бывает сколько угодно, и раннер о них
не знает ничего.

Отсюда две доски на проект, и делают они разное. Инженерная — колонка на статус,
по ней отлаживают конвейер. Человеческая — та, на которую смотрит владелец:
ей неважно, какая роль держит задачу сейчас, ей важно, ждут ли чего-то от него.

```
Backlog | У агентов (Analysis, Ready, InProgress, Review) | Ждёт меня (Blocked) | К слиянию (Approved) | Done
```

Обе заводит `scripts/jira-boards.sh`. Статус, не попавший ни в одну колонку,
**исчезает с доски вместе с задачами** — скрипт про такие говорит отдельной строкой.

### Каталог изменения

План задачи живёт в её ветке, а не в переписке: следующая роль видит ветку,
а не чужую рабочую папку.

```
docs/changes/<KEY>/
├── brief.md     зачем, критерии приёмки, что не входит
├── design.md    что трогаем и почему, решения и отвергнутые альтернативы, риски
└── tasks.md     упорядоченные `- [ ]`, каждый — один коммит
```

Каталог готовит раннер — по шаблонам из `roles/analyst/templates/`, — и он же
убирает заготовки, до которых прогон не дошёл: три пустых шаблона следующая роль
прочитала бы как план. Кто и что вправе там менять, проверяют **ограждения**:
аналитику дано право писать только в этот каталог, разработчику в `tasks.md`
положены только отметки. Ограждение зовёт сам агент на попытке завершиться —
и раннер после прогона, потому что прогон, убитый таймаутом, до хука не доживает.

Не прошло ограждение после прогона — исход **переигрывается**: отчёт агента
остаётся в тикете как есть, следом идёт запись с причиной, а задача едет как
`failed`. Это сигнализация, а не барьер: ветка публикуется до проверок, и лишний
коммит к тому моменту уже в `origin`.

## Как это устроено

Решения принимает код, а не промпт. Куда двигать задачу по каждому исходу, считать
ли попытку и звать ли человека — записано в `workflow.yaml`; агент этого файла
не видит вовсе. Его дело — рабочая папка и файл результата.

Хозяйство раннера держит вторую половину конфигурации и всё, что он наработал:
на проект — bare-клон, на задачу — worktree.

```
${OFFICE_HOME:-~/.office}/
├── projects.local.yaml             где проекты на этой машине
├── tracker.yaml                    подключение к JIRA: адрес, учётки, поля
├── budgets.yaml                    перекрытие пределов, необязательное
├── repos/<проект>.git              bare-клон: ветки, объекты, ссылки origin
├── worktrees/<проект>/<KEY>/       рабочая папка задачи
├── runs/<run_id>/                  архив прогонов: постановка, контекст, лог, результат
├── ledger.jsonl                    реестр прогонов: строка на прогон
└── bin/                            собранные бинарники раннера и ограждения
```

Worktree переживает прогон: после `reap` или ответа человека задача возвращается
к той же незаконченной работе. Убирает его системный проход, когда задача доходит
до терминального статуса (`Done`): работа слита, и папка больше не нужна.

Живёт она поэтому до слияния, то есть неделю человеческого времени, — и это
намеренно: вернуться в неё может понадобиться конфликтом. Обходит проход папки,
а не задачи: список закрытых задач в живом проекте растёт вечно, а папок —
единицы, и заодно так убираются папки задач, которые человек закрыл руками.

Двух папок проход не трогает: занятой — в ней прямо сейчас работает агент —
и **грязной**, где есть незакоммиченное. Про грязную он говорит в лог; убирают
её руками:

```sh
./bin/runner worktree ls              # что лежит, сколько занимает, где незакоммиченное
./bin/runner worktree rm OFF-1        # снести рабочую папку; ветка остаётся в клоне
```

Ветка удаление переживает — она живёт в bare-клоне. Не переживают его две вещи,
и на обе команда ругается, пока ей не скажут `--force`: незакоммиченная работа,
у которой другого места нет, и папка задачи с живой арендой — в ней прямо сейчас
работает агент, она смонтирована в его песочницу.

Ветка уезжает в `origin` всегда, когда на ней есть
новые коммиты, независимо от исхода. Пуш делает раннер, а не агент: это единственное
место с сетевым git-доступом, и роли он недоступен. Токен берётся из `GITHUB_TOKEN`
и передаётся git помощником по учётным данным — ни в конфиге репозитория,
ни в командной строке его нет.

Куда роли можно ходить по сети, складывается из четырёх слоёв, а не только из
самого `role.yaml`: repo-wide умолчания (`defaults` в `projects.yaml`), слой
проекта, слой машины (`projects.local.yaml`) и, поверх них, слой роли. Каждый
слой может только добавлять хосты к унаследованному от менее специфичных —
итог всегда объединение (union), ни один слой не может убрать то, что назвал
другой. Единственная реальная граница разрешений — не список `allow`, а
`tools.deny`: он тоже объединяется по всем слоям и не ослабляется allow более
специфичного уровня. Подробности слияния, ключ `defaults` и границы
модели — `docs/contracts/role-sandbox-permissions.md`.

Список, полученный слиянием, выдаётся песочнице этого прогона и только ему.
API Claude Code в него добавляет адаптер отдельно, потому что встроенный кит
песочницы его не открывает (измерено, `docs/notes/sbx.md`).

Но **закрытое умолчание ставит машина, а не раннер**: в sbx запрет сильнее разрешения,
поэтому «закрыть всё и открыть названное» на уровне одной песочницы не собирается —
закрыв всё, закроешь и API самого агента. Базовая политика глобальная:

```sh
sbx policy ls --wide                              # посмотреть, что есть сейчас
sbx policy rm network --id default-allow-all      # закрыть сеть песочниц
sbx policy allow network "**"                     # вернуть как было
```

Закрыть сеть раннер не может, но **проверяет, закрыта ли она**: перед каждым
прогоном спрашивает политику машины про `example.com` — домен, которого нет
и не будет ни в одной роли. Пустят туда — значит пустят куда угодно, и в лог
уйдёт строка об этом. Прогон при этом не отменяется: гарантию даёт машина,
раннер о ней рассказывает.

Бэкенд `local` сети не закрывает вовсе и говорит об этом при старте роли с непустым
списком: агент там бежит в сети хоста.

Контракты, по которым всё это держится:

- `docs/contracts/agent-io.md` — что раннер кладёт агенту и что обязан получить;
- `docs/contracts/tracker-protocol.md` — аренда, правило владения, протокол
  комментариев и нарезка истории;
- `docs/contracts/role-sandbox-permissions.md` — слоистое разрешение
  `network.allow`/`tools.allow`/`tools.deny` из repo-wide, проектного,
  машинного и ролевого слоёв.

## Ручной запуск агента

`run-agent` — та же чистая функция, что зовёт конвейер, только рабочую папку
и постановку задаёт человек. Ею отлаживают роль.

```sh
mkdir -p /tmp/task-123 && git -C /tmp/task-123 init -q
git -C /tmp/task-123 commit -q --allow-empty -m init
echo 'Создай файл hello.py и закоммить.' > /tmp/task.md

# посмотреть, что получит агент, ничего не запуская и не тратя токенов
./bin/run-agent --role implementer --workdir /tmp/task-123 --task /tmp/task.md --dry-run

# запустить по-настоящему — по умолчанию в песочнице
./bin/run-agent --role implementer --workdir /tmp/task-123 --task /tmp/task.md
```

| Флаг | Смысл |
|---|---|
| `--role` | имя роли из `roles/` |
| `--workdir` | рабочая папка агента: git-репозиторий |
| `--task` | файл с постановкой; без него берётся уже лежащий `.agent/task.md` |
| `--base` | базовая ветка: от неё считается разница по задаче. Нужна `reviewer`'у — свою ветку рабочая папка называет сама, базу назвать некому |
| `--backend` | `sbx` (песочница, по умолчанию) или `local` (без изоляции, для отладки) |
| `--dry-run` | показать команду, окружение, настройки и промпты — и ничего не запускать |

Коды возврата у обеих команд одни:

| Код | Что означает |
|---|---|
| `0` | цикл прошёл; для `run-agent` — валидный результат с исходом `done`, `needs_human` или `blocked` |
| `1` | исход `failed`: агент не справился |
| `2` | инфраструктурная беда — нет роли, бэкенда, креда. Запускать было нечем |

На бэкенде `local` изоляции нет: агент работает в файловой системе владельца машины.
Ему подменяют `HOME` и отбирают у git ssh-личности, но это защита от случайности,
а не граница. Настоящая граница — песочница, поэтому она и стоит по умолчанию.

Сборки не требуется: обёртки в `bin/` собирают бинарник в `${OFFICE_HOME}/bin`
и запускают его через `exec`. Именно `exec`, а не `go run`: тот держит бинарник
потомком и не передаёт ему сигналов, так что остановить `loop` штатным способом
было бы нечем.

Смотреть, что агент делает прямо сейчас:

```sh
tail -f <рабочая папка>/.agent/run.log
```

Завершиться без валидного результата агенту не даёт ограждение на событии `Stop`.
Схему оно разбирает тем же кодом, что и раннер, — командой `validate-result`,
которую раннер собирает под платформу бэкенда и кладёт агенту рядом с хуками.
Тот же разбор доступен человеку:

```sh
./bin/run-agent validate-result /tmp/task-123/.agent/result.json
```

## Проверки

```sh
go test ./...                               # всё, кроме прогонов агента
./scripts/smoke.sh all                      # девять сценариев, настоящие прогоны
./scripts/smoke.sh analyst                  # только роль analyst: три из них
OFFICE_BACKEND=sbx ./scripts/smoke.sh all   # они же в песочнице
```

Smoke-тест тратит подписку или деньги. Проверяются им три слоя, и каждый — своим
действием: правило разрешений (попыткой записать не туда), ограждение (тем, что
мимо правила проходит) и сама работа роли. Результаты последних прогонов —
`docs/notes/stage-4-smoke.md`, раньше — `smoke.md` и `stage-2-smoke.md`.

## Где что лежит

```
roles/                 спецификации ролей: промпт, машиночитаемый контракт, шаблоны артефактов
skills/                кастомные скиллы, подключаются ролью поимённо
hooks/                 скрипты ограждений на событии Stop
cmd/                   точки входа: runner, run-agent, validate-result
internal/guard/        сами ограждения: проверки прогона, общие для хука и раннера
internal/adapters/     перевод роли в вызов конкретного агента
internal/backends/     где выполняется агент: local, sbx
internal/runner/       контракт обмена, загрузка роли, сборка входа, архив, команды
internal/runagent/     один прогон агента: роль плюс рабочая папка → результат
internal/tracker/      контракт трекера: задача, аренда, правило владения, комментарии
internal/tracker/mock/ файловый трекер: отладка конвейера без JIRA
internal/forge/        pull request: интерфейс и GitHub через REST
internal/tracker/jira/ трекер поверх JIRA Server REST API v2
internal/workspace/    bare-клоны, worktree задач, публикация веток
internal/ledger/       реестр прогонов: строка на прогон, локально для машины
internal/budget/       пределы расхода поверх реестра
internal/pipeline/     конвейер: захват задачи, прогон, разбор исхода, переходы
bootstrap/             обвязка машины: задания планировщика, локальная JIRA в контейнере
scripts/               smoke-тест, настройка полигона JIRA: статусы, workflow, доски, очередь
docs/                  замысел, контракты, внедрение, рабочие заметки
workflow.yaml          граф состояний: статусы, роли, PR-проход, переходы по исходам
projects.yaml          проекты-клиенты офиса: имена и неизменные свойства веток
tracker.example.yaml   образец подключения к JIRA; рабочий файл — в ${OFFICE_HOME}
budgets.yaml           дефолтные пределы расхода; необязателен, перекрывается накладкой машины
```

Конфигурация лежит в двух местах, и граница простая: **репозиторий описывает офис,
`${OFFICE_HOME}` — инстанс.** Всё, что правят, заводя новую машину или второй
инстанс, живёт вне репозитория — эти три файла видны в дереве хозяйства выше,
а ключи у них такие:

```
projects.local.yaml   repo_url, worktree_root, tracker и forge на каждый проект
tracker.yaml          адрес, учётки, номера полей, карта статусов
budgets.yaml          перекрытие пределов, необязательное
```

Иначе правка под себя пачкает рабочее дерево, и метка прогона `config:…-dirty`
перестаёт что-либо значить. Совсем от неё это не спасает: список проектов офиса
поставляется в репозитории, так что шаг 3 быстрого старта — правка закоммиченного
файла, и первый же ваш прогон будет помечен. За границей следит загрузчик: машинный ключ, встреченный
в `projects.yaml`, — отказ при старте. Отказом же кончается и проект, названный офисом,
но не заведённый на машине, — молча пропущенный, он выглядел бы как проект, по которому
просто нет задач. При запуске раннер печатает, откуда взял каждый файл, и печатает
по ходу: при отказе строки уже выведены.

Заметки в `docs/notes/` — то, к чему возвращаются: поведение CLI агента и JIRA REST,
пути авторизации, устройство песочницы, что показывает счётчик стоимости под подпиской
(`budgets.md`), результаты прогонов и ретроспективы этапов.
