# virtual-office

Команда AI-агентов, ведущая разработку проекта-клиента через его трекер.
Человек участвует в фиксированных точках, а не в каждом шаге.

Замысел и архитектурные решения — `docs/DESIGN.md`, это источник истины.
Сейчас сделан этап 1: одна команда запускает агента в заданной роли над указанной
рабочей папкой и возвращает машиночитаемый результат. Трекера, аренды задач
и графа переходов ещё нет — это этап 2.

## Что нужно на машине

| Инструмент | Зачем |
|---|---|
| Go 1.26+ | раннер |
| `claude` | агент; для бэкенда `local` |
| `sbx` | Docker Sandboxes; для бэкенда `sbx` |
| `git` | рабочая папка агента — git-репозиторий |
| `python3`, `uv` | инструменты учебной задачи smoke-теста, не раннера |

Авторизация — переменной окружения, `ANTHROPIC_API_KEY` или `CLAUDE_CODE_OAUTH_TOKEN`.
Подробности обоих путей — `docs/notes/auth.md`. Секретов в репозитории нет и не будет.

## Запуск агента в роли

Пять команд от клона до smoke-теста.

```sh
# 1. Клон
git clone <repo> virtual-office && cd virtual-office

# 2. Кред: токен подписки (claude setup-token) или ключ из Claude Console
export CLAUDE_CODE_OAUTH_TOKEN='...'

# 3. Рабочая папка агента — любой git-репозиторий, и постановка задачи к ней
mkdir -p /tmp/task-123 && git -C /tmp/task-123 init -q
git -C /tmp/task-123 commit -q --allow-empty -m init
echo 'Создай файл hello.py и закоммить.' > /tmp/task.md

# 4. Посмотреть, что получит агент, ничего не запуская и не тратя токенов
./bin/run-agent --role implementer --workdir /tmp/task-123 --task /tmp/task.md --dry-run

# 5. Запустить по-настоящему — по умолчанию в песочнице
./bin/run-agent --role implementer --workdir /tmp/task-123 --task /tmp/task.md
```

Сборки не требуется: `bin/run-agent` — обёртка, Go собирает и запускает на месте.

Тот же прогон без изоляции, прямо на хосте, — только для отладки контура:

```sh
./bin/run-agent --role implementer --workdir /tmp/task-123 --task /tmp/task.md --backend local
```

На бэкенде `local` изоляции нет: агент работает в файловой системе владельца машины.
Ему подменяют `HOME` и отбирают у git ssh-личности, но это защита от случайности,
а не граница. Настоящая граница — песочница, поэтому она и стоит по умолчанию.

Smoke-тест гоняет три сценария на одноразовых репозиториях — самоописание роли,
выполнимая задача с коммитом и намеренно неоднозначная задача:

```sh
./scripts/smoke.sh all                      # без изоляции
OFFICE_BACKEND=sbx ./scripts/smoke.sh all   # в песочнице
```

Прогоны настоящие и расходуют подписку или деньги. Результаты последних —
`docs/notes/smoke.md`.

## Что делает `run-agent`

Читает спецификацию роли, собирает агенту входной пакет, запускает его в выбранном
бэкенде, разбирает результат и печатает исход.

| Флаг | Смысл |
|---|---|
| `--role` | имя роли из `roles/` |
| `--workdir` | рабочая папка агента: git-репозиторий |
| `--task` | файл с постановкой; без него берётся уже лежащий `.agent/task.md` |
| `--backend` | `sbx` (песочница, по умолчанию) или `local` (без изоляции, для отладки) |
| `--dry-run` | показать команду, окружение, настройки и промпты — и ничего не запускать |

Код возврата: `0`, если исход `done`, иначе `1`.

Всё общение с агентом идёт через каталог `.agent/` внутри рабочей папки: раннер кладёт
туда постановку, контекст и паспорт запуска, агент оставляет `result.json`, раннер
дописывает `run.log`. Контракт — `docs/contracts/agent-io.md`.

От git этот каталог прячется через `info/exclude`, то есть репозиторий проекта-клиента
не меняется: ни файла в дереве, ни строки в его `.gitignore`.

Смотреть, что агент делает прямо сейчас:

```sh
tail -f /tmp/task-123/.agent/run.log
```

## Где что лежит

```
roles/          спецификации ролей: промпт и машиночитаемый контракт
skills/         кастомные скиллы, подключаются ролью поимённо
hooks/          детерминированные ограждения
adapters/       перевод роли в вызов конкретного агента
backends/       где выполняется агент: local, sbx
runner/         контракт, загрузка роли, сборка входа, точка входа
scripts/        smoke-тест
docs/           замысел, контракт, рабочие заметки
```

Заметки в `docs/notes/` — то, к чему возвращаются: поведение CLI агента, пути
авторизации, устройство песочницы, результаты прогонов и ретроспектива этапа.
