# Beads и Gas Town: разбор чужого опыта

**Дата:** 2026-08-14
**Статус:** исследование чужих решений. По итогам взяты три правила (Р-37, §5.2);
ни один механизм Beads не заимствован.
**Формат:** разбор исходников и документации двух проектов + внешние обзоры.
**Источники:** склонированы `github.com/steveyegge/beads` и `github.com/gastownhall/gastown`
(shallow, на дату разбора), прочитаны исходники, `docs/`, `engdocs/` и шаблоны ролей.

---

## 0. Зачем смотрели

Владелец спросил, как у соседей устроены оркестрация задач, роли, ограничения
и настройки. Beads (`bd`) — известный трекер задач для кодящих агентов; при
разборе выяснилось, что оркестрация живёт не в нём, а в отдельном проекте
Gas Town (`gt`), и это разделение у них закреплено уставом.

---

## 1. Два проекта и граница между ними

- **Beads** (`bd`) — трекер задач для агентов. Go, ~18.7k звёзд. Граф задач,
  хранение в Dolt (версионируемый SQL), синхронизация через `refs/dolt/data`
  на git-remote. `.beads/issues.jsonl` — пассивный экспорт, а не протокол синка.
- **Gas Town** (`gt`) — оркестратор поверх Beads. Go, MIT, декабрь 2025,
  ~9k звёзд. Роли, воркеры, очередь слияния, эскалации.

`engdocs/PROJECT_CHARTER.md` формулирует границу прямо:

> Beads should not know about orchestration layers built on top of it. […]
> The orchestration layer owns orchestration policy: agent routing, task
> assignment strategy, model choice, retry plans, scheduling, workflow
> semantics, and cross-system coordination.

В версии 0.62 они физически вычистили из Beads всю терминологию Gas Town
(GUPP, polecat, HOP-поля, захардкоженные пути `~/gt/`).

Устав даёт и правило расширения: **данные оркестрации кладутся в `metadata`
задачи, и только при широком устойчивом смысле повышаются до поля схемы.**
Отдельный «интеграционный устав» ограничивает адаптеры трекеров: это мосты
для миграции, а не вторая продуктовая поверхность; они не воспроизводят UI
трекера, уведомления, хранилища кредов и кросс-трекерную автоматизацию.

## 2. Beads: модель работы

### 2.1 Задача

Типы: `bug`, `feature`, `task`, `epic`, `chore` (+ кастомные через
`types.custom`). Приоритеты `0`–`4` (critical / high / medium / low / backlog).
Статусы: `open`, `in_progress`, `blocked`, `closed`, `deferred`; кастомный
статус объявляется с «категорией поведения» (`active` / `wip` / `done` /
`frozen`), которая и определяет его роль в `bd ready` и `bd list`.

Поля сверх обычных: `--design`, `--notes`, `--acceptance`. Полнота карточки
проверяется машиной: `create.require-description` и
`validation.on-create | on-close | on-sync` со значениями `none` / `warn` / `error`.

ID хэшевые (`bd-a3f8`) — чтобы параллельные агенты и ветки не давали коллизий
при слиянии. Иерархия точками (`bd-a3f8.1.1`), глубина ограничена
`hierarchy.max-depth` (по умолчанию 3).

### 2.2 Зависимости и готовность

Блокируют готовность:

| Тип | Смысл |
|---|---|
| `blocks` | B не стартует, пока A не закрыта |
| `parent-child` | дети заблокированы, если заблокирован родитель |
| `conditional-blocks` | B выполняется только если A **провалилась** |
| `waits-for` | B ждёт всех динамически созданных детей A |

Не блокируют, только связывают: `related`, `tracks`, `discovered-from`,
`caused-by`, `validates`, `supersedes`, `replies-to`.

`bd ready` — все блокирующие зависимости закрыты. Циклы отбиваются на записи:
`bd dep add` проверяет граф до коммита.

Два типа стоят внимания. `conditional-blocks` — ветка «если упало» прямо
в графе задач: обработка отказа как данные, а не как код. `discovered-from` —
обнаруженная по ходу работа; наследует маршрутизацию родителя и делает
происхождение находки запрашиваемым.

### 2.3 Захват работы

```
bd update <id> --claim        # атомарно: assignee + in_progress
bd ready --claim --json       # взять первую подходящую готовую
```

Первый успевший выигрывает. **Ни TTL, ни срока, ни правил перезахвата
протухшего claim нет** — ни в документации по координации, ни в `claim.go`
(88 строк). Обнаружение зависших исполнителей целиком делегировано слою
оркестрации.

Единственный примитив взаимного исключения — `bd merge-slot`: одна
карточка-мьютекс на проект, `status=open` свободен, `in_progress` занят,
`metadata.holder` — держатель, `metadata.waiters` — очередь по приоритету.
Назначение в исходнике описано честно: предотвращать «monkey knife fights»,
когда несколько воркеров одновременно кидаются разруливать конфликт и
порождают каскад новых.

### 2.4 Гейты

Гейт — карточка, изображающая ожидание; блокирует шаг обычным ребром
зависимости.

| Тип | Чем закрывается |
|---|---|
| `human` | **только вручную**, `bd gate resolve` |
| `timer` | `bd gate check` по истечении срока |
| `gh:run` | успех workflow GitHub Actions |
| `gh:pr` | вливание PR |
| `bead` | закрытие карточки в другом проекте |

Человеческий гейт не закрывается автоматически никогда. Плюс отдельная
очередь человеческих решений: `bd human list | respond <id> | dismiss <id> |
stats` — карточки с меткой `human`. Входящие человека — самостоятельный
объект со своей статистикой, а не просто «карточка чего-то ждёт».

### 2.5 Процесс как данные

Формула (TOML) → `bd cook` → прото → `bd mol pour` → молекула.

```toml
formula = "release"
version = 1

[vars.version]
required = true
pattern = "^\\d+\\.\\d+\\.\\d+$"

[[steps]]
id = "changelog"
title = "Update CHANGELOG"
needs = ["bump-version"]

[[steps]]
id = "approve-deploy"
title = "Human approves the deploy"
[steps.gate]
type = "human"
```

Переменные с `required`, `pattern`, `enum` валидируются на подстановке.
Молекула — эпик с семантикой исполнения: **дети параллельны по умолчанию,
последовательность создаёт только явная зависимость.** Отдельно предупреждают
о ловушке: шаги, названные «Шаг 1, Шаг 2, Шаг 3», выполняются параллельно —
нумерация в заголовке ничего не упорядочивает.

Wisp — эфемерная молекула (`Ephemeral=true`): нормальная карточка в базе, но
исключена из синхронизации и вычищается после прогона. Для операционной
рутины (релизные чеклисты, патрули, диагностика), которая не должна засорять
след аудита. `bd mol squash` переводит в постоянное, `bd mol burn` удаляет.

### 2.6 Полномочия агента вычисляются, а не задаются

`bd prime` впрыскивает в контекст сессии блок правил, и текст этого блока
**вычисляется** из комбинации: профиль (`agent.profile` = `conservative`
по умолчанию | `minimal` | `team-maintainer`) × наличие git-remote ×
эфемерная ли ветка × выставлен ли `no-push` × stealth-режим.

Умолчание:

> Default: do not commit, push, or run dolt remote sync without explicit
> authority. Team-maintainer behavior is opt-in and still subordinate to
> user/orchestrator instructions.

В каждой ветке матрицы повторяется: явная инструкция пользователя или
оркестратора перекрывает профиль. Плюс оговорка в шаблоне `AGENTS.md`:

> The managed Beads block is task-tracking guidance, not permission to
> override repository, user, or orchestrator instructions.

Оттуда же — метаданные исполнения, которые оркестратор кладёт на карточку
и агент обязан прочитать **раньше прозы**:

```
execution_agent_type
execution_suggested_model
execution_reasoning_effort
execution_mode
execution_parallel_group
```

Мотивировка: запущенный субагент уже не может сменить себе модель и уровень
рассуждений, поэтому родитель читает это до порождения.

### 2.7 Интеграция с Jira

В Beads есть собственный клиент Jira (`internal/jira/`, ~1.3 тыс. строк без
тестов) и команда `bd jira`:

```
bd jira sync --pull          # импорт из Jira
bd jira sync --push          # экспорт в Jira
bd jira sync                 # двусторонний: pull, затем push
bd jira sync --dry-run
bd jira status
```

Конфиг: `jira.url`, `jira.project` / `jira.projects`, `jira.username`,
`jira.api_token`, `jira.push_prefix` (пушить только карточки заданных
префиксов), плюс `status_map`, `type_map`, `custom_fields`. Креды берутся
из `JIRA_API_TOKEN` / `JIRA_USERNAME` или из конфига; секреты в
git-tracked `config.yaml` система отбивает без `--force-git-tracked`.

**Разрешение конфликтов при двустороннем синке: по умолчанию побеждает более
свежая метка времени.** Переопределяется флагами `--prefer-local` /
`--prefer-jira`. Есть `--create-only`, выборочный синк по списку ID
(`--issues`), поддерево (`--parent`), фильтр по состоянию (`--state`).

Доступ — прямой REST к `jira.url`.

## 3. Gas Town: оркестрация и роли

### 3.1 Семь ролей плюс человек

Уровень города:

| Роль | Что делает | Жизненный цикл |
|---|---|---|
| **Mayor** | глобальный координатор, начальник штаба | синглтон, постоянный |
| **Deacon** | демон-сторож, гоняет патрульные циклы | синглтон, постоянный |
| **Dogs** | помощники Дикона для инфраструктурных задач | очень короткие |

Уровень проекта («риг»):

| Роль | Что делает | Жизненный цикл |
|---|---|---|
| **Witness** | надзор за воркерами; **не пишет код** | один на риг, постоянный |
| **Refinery** | очередь слияний | один на риг, постоянный |
| **Polecat** | воркер на одной задаче в изолированном worktree | эфемерный |
| **Crew** | долгоживущий воркер со своим клоном | управляется человеком |

**Overseer — это человек.** У него собственная идентичность в системе, свой
почтовый ящик, он отправляет и получает почту наравне с агентами. Собака
по имени Boot проверяет Дикона каждые пять минут — сторож над сторожем.

Роли **операционные, а не должности SDLC**. Внешний обзор противопоставляет
это схеме BMAD/SpecKit (Аналитик → PM → Архитектор → Разработчик), называя
имитацию оргструктуры ловушкой.

### 3.2 Принцип движения (GUPP)

> **If you find something on your hook, YOU RUN IT.**

Крюк (hook) — закреплённая за агентом карточка, его назначение. Нашёл работу
на крюке — исполняй немедленно, без подтверждений.

Названный ими режим отказа:

```
Полекат перезапускается с работой на крюке
  → объявляет о себе
  → ждёт подтверждения
  → Witness считает, что работа идёт
  → не происходит ничего
  → Gas Town останавливается
```

Это прямая противоположность нашей ставке: мы намеренно ставим гейты
владельца, они намеренно убирают человека из цикла и считают ожидание
отказом. Документированная цена их выбора (по внешним обзорам, не из
репозитория): порядка $100/час на токенах, агенты, вливающие падающие тесты,
непредсказуемое удаление кода Диконом, необходимость «постоянного
подруливания» вместо автономности.

### 3.3 Три слоя, которые нельзя путать

Ранние версии считали воркера монолитом, и это давало повторяющиеся сбои.
Разделили:

| Слой | Что это | Живёт |
|---|---|---|
| **Identity** | карточка агента, CV-цепочка, история работ | вечно |
| **Sandbox** | git worktree и ветка | на время назначения |
| **Session** | окно контекста в tmux | эфемерно, циклится |

Цикл сессии — **нормальная операция, а не сбой**: `gt handoff` между шагами,
компактификация контекста, падение. Все сессии одного назначения — один и тот
же воркер, песочница переживает их все.

Состояния: Working / Idle / Done / **Stalled** (сессия умерла на середине) /
**Zombie** (`gt done` упал при уборке).

### 3.4 Путь задачи

```
gt sling <bead> <rig>     # выделить слот из пула имён, создать worktree и ветку,
                          # запустить сессию, повесить работу на крюк
      ↓  работа, циклы сессий через gt handoff
gt done                   # запушить ветку, подать MR в очередь слияния,
                          # снести песочницу, убить собственную сессию
      ↓
Refinery                  # ребейз и слияние, закрытие карточки;
                          # при конфликте — задача воркеру
```

Воркер **никогда не пушит в main и не открывает PR**. Конвой (`gt convoy`) —
наряд, объединяющий связанные карточки, единая витрина «что в работе».

### 3.5 Два зафиксированных ими сбоя

**«Ересь праздного полеката».** Воркер, закончивший работу, но не выполнивший
`gt done`, — критический системный сбой. Шаблон роли повторяет это трижды,
включая финальное напоминание. Формулировка: «There is no approval step.»

**Штормы порождения.** Каждая сессия обязана закончиться либо пушем через
`gt done`, либо явным `bd close` на карточке крюка. Иначе патруль зомби
возвращает карточку в `open` и раздаёт её заново — у них это давало
**шесть-семь воркеров на одной карточке**.

### 3.6 Ограничения воркера

Из шаблона роли — их аналог наших законов:

- **Одна задача.** Не проверять почту повторно, не спрашивать про других
  воркеров, не работать над неназначенным. Обнаруженное — заводить карточкой,
  но **самому не чинить**.
- **Дисциплина каталога.** Файловые операции только внутри своего worktree,
  абсолютными путями. Никогда не писать в корень рига.
- **Гейты качества обязательны.** Не коммитить при красном линте или тестах.
  Worktree может не запускать pre-commit хуки — прогонять руками. Определение
  «готово» берётся из `AGENTS.md` проекта-клиента.
- **Сохранять находки в карточку рано и часто.** Код переживёт смерть сессии
  в git; анализ, выводы и решения живут только в окне контекста. Для
  задач-исследований находки и есть результат.
- **Застрял дольше 15 минут — писать надзирателю.**
- **Экономить на общении.** `gt nudge` бесплатен, `gt mail send` — вечный
  коммит в Dolt. Почтой только то, что должно пережить смерть сессии.

### 3.7 Эскалация

Трёхуровневая, с маршрутизацией по серьёзности:

| Уровень | Приоритет | Маршрут по умолчанию |
|---|---|---|
| CRITICAL | P0 | карточка + почта + email + **SMS человеку** |
| HIGH | P1 | карточка + почта + email |
| MEDIUM | P2 | карточка + почта мэру |

Цепочка: агент → Дикон (решает или передаёт) → Мэр (решает или передаёт) →
**Overseer, человек**. Каждое звено фиксируется комментарием в карточке.
`stale_threshold: 4h`, `max_reescalations: 2`.

### 3.8 Пульс — и честное признание провала

Отдельный документ описывает **три разных хранилища пульса** с разными
читателями и порогами и открывается признанием, что их рассинхронизация
давала ложные эскалации «агент завис». Плюс: сессия, которая долго не доходит
до точки ожидания сигнала, оставляет метку устаревшей на часы, будучи
здоровой.

Урок в жанре «как не надо»: три источника истины об одном факте — не
избыточность, а генератор багов.

## 4. Настройки

### 4.1 Очередь слияния

```json
"merge_queue": {
  "run_tests": true,
  "setup_command": "", "typecheck_command": "",
  "lint_command": "", "test_command": "", "build_command": "",
  "on_conflict": "assign_back",
  "retry_flaky_tests": 1,
  "poll_interval": "30s",
  "max_concurrent": 1,
  "integration_branch_template": "integration/{title}",
  "integration_branch_auto_land": false
}
```

`max_concurrent: 1` — WIP-лимит на слияния. `on_conflict: assign_back` —
конфликт возвращается автору, а не разруливается машиной.

### 4.2 Слоёная конфигурация проекта

wisp (временный слой, для проб) → метки карточки-идентичности проекта
(постоянные) → умолчания города → вкомпилированные. Настройка проекта живёт
как метки на карточке в трекере — конфиг как данные трекера.

### 4.3 Как роли получают контекст

- На диске лежит **единственный** `~/gt/CLAUDE.md` — минимальный якорь
  идентичности, чтобы агент не забыл, кто он, после компактификации.
- Полный контекст роли, **300–500 строк**, впрыскивается эфемерно командой
  `gt prime` через хук SessionStart. Файлов на роль нет.
- Настройки роли подаются флагом `--settings` из каталогов оркестратора
  отдельным аддитивным слоем — репозиторий клиента остаётся чистым, его
  `.claude/` и `CLAUDE.md` сохраняются и работают одновременно.
- Интерактивные роли (Мэр, Crew) получают почту на `UserPromptSubmit`;
  автономные (воркер, надзиратель, Refinery, Дикон) — на `SessionStart`,
  потому что стартуют без человека.

Их вывод из практики: **пофайловый `AGENTS.md` в подкаталогах никогда не
работал** — Codex обходит дерево вниз от корня git, родительские каталоги ему
не видны. Отсюда правило: не полагаться на файлы-указатели, впрыскивать
контекст командой.

## 5. Выводы для офиса

По итогам разбора приняты три правила — решение Р-37. Ни один механизм Beads
не заимствован: ни граф задач, ни claim, ни гейты-карточки, ни эфемерные
молекулы. Остальное — заметки для будущих развилок.

### 5.1 Что подтверждает наши решения

- Разделение «трекер отдельно, оркестрация отдельно» закреплено у них уставом
  и подтверждено болезненной чисткой кода в 0.62. Наш Р-30 идёт в ту же
  сторону.
- Отсутствие у них лизы со сроком и всё, что из этого выросло — claim без
  срока плюс внешний сторож, три хранилища пульса, состояния Stalled/Zombie,
  штормы порождения, — довольно сильный аргумент за то, что одна лиза с TTL
  проще и надёжнее их связки.
- Цена их автономности без гейтов (вливаемые падающие тесты, «постоянное
  подруливание») работает как эмпирика в пользу нашей ставки на гейты
  владельца.

### 5.2 Взято сейчас (Р-37)

Три правила, ноль механизмов.

- **Терминальный переход пробуждения** → закон 15. У них «сделал и молча ушёл»
  давало до семи исполнителей на одной карточке. У нас та же дыра открывается
  на шаге 4 вместе с лизой: работа сделана, но срок лизы истёк, и следующее
  пробуждение сделает её второй раз.
- **Один источник истины о состоянии** → правило стройки §7. У них три
  хранилища пульса давали ложные тревоги «агент завис»; у нас на шаге 4
  появляются карточка, журнал пробуждений и лок крона.
- **«Заводи карточкой, но сам не чини» и запрет расширять объём своей
  карточки** → закон 9. Анти-расползатель объёма; в полную силу заработает
  на Разработчике, сейчас держит Уточнителя.

Плюс бесплатная практика: сохранённый фильтр «ждёт меня» в Jira собирает
в один список всё, что стоит на владельце, — минимальная форма их очереди
человеческих решений, без механизма.

### 5.3 Что стоит рассмотреть на будущих шагах

- **Очередь человеческих решений как объект**
  (`bd human list/respond/dismiss/stats`) со своей статистикой — если
  сохранённого фильтра перестанет хватать.
- **Типизированная связь «обнаружено при работе над»** — правило уже взято,
  типизированное ребро в трекере остаётся на потом.
- **Разделение идентичности, песочницы и сессии.** Наши роль и участок — про
  то же; слоя истории работ у нас нет вовсе, а он несёт и атрибуцию,
  и маршрутизацию по способностям.
- **Впрыск контекста роли командой вместо файлов** — применимо к нашей
  упаковке в плагин, включая находку про `AGENTS.md` и обход дерева.
- **Разделение постоянной и испаряющейся работы** (wisp): операционная рутина
  не должна засорять след аудита.
- **Ограничение параллелизма и стратегия конфликта в конфиге**
  (`max_concurrent`, `on_conflict: assign_back`) — к WIP-лимитам и Разработчику.
- **Гейты качества в worktree**: pre-commit хуки могут не сработать, прогонять
  руками — к Разработчику.
- **Сохранение находок на карточку по ходу длинной роли**: код переживает
  смерть сессии в git, анализ и выводы — нет.

### 5.4 Чего брать не стоит

- Принцип движения без человека — противоречит замыслу офиса целиком.
- Семь ролей: при потолке около восьми задач на шаг это заведомо сверх меры.
- Три хранилища пульса — их собственный документ объясняет, почему.
