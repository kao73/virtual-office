# Этап 1. Окружение для запуска агента в заданной роли

Инструкция для Claude Code. Перед началом прочитай `docs/DESIGN.md` — это источник истины по архитектуре.
Этап 1 не касается JIRA, lease, reaper и графа переходов. Его цель — одна команда, которая
запускает агента в нужной роли над указанной рабочей папкой и возвращает машиночитаемый результат.

## Цель этапа (definition of done)

Команда вида

    ./bin/run-agent --role implementer --workdir /tmp/task-123 --backend local

1. читает спецификацию роли из `roles/implementer/`;
2. собирает входной пакет для агента из содержимого `workdir` (см. контракт ниже);
3. запускает Claude Code в headless-режиме с промптом роли, нужными скиллами и ограничениями инструментов;
4. дожидается завершения и получает `result.json` по контракту;
5. печатает исход (`done|needs_human|blocked|failed`) и код возврата 0/1/2:
   0 — валидный результат с исходом `done|needs_human|blocked`, 1 — `failed`,
   2 — инфраструктурная беда. Уточнено на шаге 0 этапа 2: изначально было «0/1»,
   где ноль означал только `done`, и раннер этапа 2 не мог отличить неудачную
   попытку агента от сломанного окружения.

То же самое работает с `--backend sbx` (агент внутри песочницы Docker Sandboxes,
рабочая папка отдана ей как workspace).

Порядок бэкендов изменён по ходу этапа. Изначально пятым шагом стоял докер, потому что
его «проще отладить», а sbx откладывался. К пятому шагу это перестало быть верным:
контур уже отлажен на `local`, и роль известной величины досталась ему, а у sbx пути
внутри совпадают с хостовыми — значит трансляция путей не нужна и работы меньше, чем
с докером. Докер отложен до появления машины без KVM; `DESIGN.md` §2.6 и так называет
его фолбэком, а sbx — предпочтительным бэкендом.

## Общие правила работы

- Работай по шагам ниже. В конце каждого шага: короткий отчёт (что сделано, что проверено, что не получилось),
  коммит с осмысленным сообщением, **остановка и ожидание подтверждения** перед следующим шагом.
- Не полагайся на память о флагах Claude Code. Перед использованием любого флага проверь его через
  `claude --help` (и подкоманды) и/или официальную документацию https://code.claude.com/docs/en/.
  Если флаг отсутствует — найди актуальный эквивалент, зафиксируй в `docs/notes/claude-cli.md`.
  `--help` неполон: часть работающих флагов в нём не перечислена, сверяй три источника —
  `--help`, документацию и эмпирическую проверку.
- Минимализм: никаких плагинных систем, DI-контейнеров, конфиг-фреймворков. Один язык для runner'а —
  **Go** (1.26, модуль `github.com/kao73/virtual-office` в корне репозитория). Зависимости — только
  по необходимости и поимённо; на этом этапе ожидается ровно одна: YAML-парсер для `role.yaml`.
- Язык раннера и язык проекта-клиента — разные вещи. Раннер на Go, а учебная задача smoke-теста
  (шаг 4) намеренно питоновская: так сразу видно, что раннер не завязан на стек проекта-клиента.
- Секреты только через переменные окружения. Никаких ключей в файлах репо, в промптах, в логах.
- Всё, что создаётся агентом внутри workdir, должно быть воспроизводимо: любой шаг можно повторить командой из README.
- Если что-то в этой инструкции противоречит `docs/DESIGN.md` — остановись и спроси.

## Шаг 0. Разведка

1. Проверь наличие и версии: `claude`, `git`, `docker`, `go`, а также `uv`/`python` — последние нужны
   не раннеру, а учебной задаче smoke-теста. Запиши в отчёт.
2. Проверь способ авторизации Claude Code в этой среде: есть ли `ANTHROPIC_API_KEY`; если нет — какой
   механизм доступен для неинтерактивного запуска по подписке (изучи в документации `claude setup-token`
   и переменную окружения для OAuth-токена; не угадывай — проверь). Зафиксируй в `docs/notes/auth.md`
   оба пути: API-ключ и подписка, с точными командами.
3. Составь список флагов `claude -p`, которые понадобятся: системный промпт роли (добавление/замена),
   формат вывода (JSON / stream-json), ограничение инструментов, режим разрешений, подключение
   скиллов/плагинов из локальной папки, изоляция пользовательского конфига (проверь `CLAUDE_CONFIG_DIR`
   или актуальный аналог, чтобы агент не читал хостовые `~/.claude` настройки), рабочая директория.
   Зафиксируй в `docs/notes/claude-cli.md` с примерами. Это документ, к которому будем возвращаться.
4. Проверь текущее содержимое репо: что из уже написанного относится к этому этапу. Не удаляй ничего.
   Отчёт → стоп.

## Шаг 1. Структура репозитория и контракт роли

Создай (или приведи к виду):

    go.mod                  # модуль github.com/kao73/virtual-office
    roles/
      _base/                # общее для всех ролей
        base.md             # общие правила поведения агента (отчёт, честность, когда сдаваться)
      implementer/
        role.yaml           # машиночитаемая спецификация роли
        role.md             # системный промпт роли (человекочитаемый)
    skills/                 # кастомные скиллы (формат SKILL.md), пока пусто или 1 тестовый
    adapters/
      claude/               # Go-пакет: превращает role.yaml + workdir в вызов claude
    runner/                 # Go-пакет: загрузка роли, сборка входа, запуск бэкенда, разбор результата
    backends/
      local/                # Go-пакет: запуск claude на хосте
      docker/               # Go-пакет + Dockerfile: запуск в контейнере
    bin/run-agent           # точка входа
    docs/
      DESIGN.md
      notes/
      contracts/agent-io.md # контракт входа/выхода агента

`role.yaml` (минимум, не расширять без нужды):

    name: implementer
    prompt: role.md                 # относительный путь
    includes: [../_base/base.md]    # склеивается перед role.md
    skills: []                      # имена папок из skills/
    tools:
      allow: [Read, Edit, Write, Bash(git *), Bash(uv *), Bash(pytest *)]   # проверь синтаксис у claude
      deny:  []
    hooks:                          # детерминированные ограждения, скрипты из репо
      stop: [hooks/require-result.sh]   # не даёт завершиться без валидного result.json
    limits:
      max_turns: 50                 # --max-turns существует, проверено (docs/notes/claude-cli.md)
      timeout_sec: 1800             # флага таймаута нет — держит бэкенд
    result_file: .agent/result.json # где агент обязан оставить результат

Принцип разделения (см. обсуждение ролей): всё, что агент вправе решить сам, — в скилл;
всё, что он решать не вправе, — в `role.md` (безусловный системный промпт) или в код (tools/hooks).
Роль — не скилл: скилл подгружается по усмотрению агента, роль действует всегда.

`role.md` для implementer на этом этапе — короткий: «ты получаешь задачу из `.agent/task.md`, контекст из
`.agent/context.md`, работаешь в текущей папке, коммитишь в текущую ветку, в конце обязан записать
`.agent/result.json` по схеме из `docs/contracts/agent-io.md`». Без JIRA, без комментариев — это позже.

Отчёт → стоп.

## Шаг 2. Контракт «runner ↔ агент» (`docs/contracts/agent-io.md`)

Опиши и реализуй:

**Вход** (runner кладёт в `workdir/.agent/` перед запуском):
- `task.md` — постановка задачи (пока — берётся из файла, переданного флагом `--task`, или уже лежит в workdir);
- `context.md` — собранный runner'ом контекст (на этом этапе: содержимое `STATE.md`, если есть; имя роли; run_id; ограничения);
- `run.json` — `{run_id, role, config_sha, started_at}`; `config_sha` = `git rev-parse HEAD` конфиг-репо.

**Выход** (агент обязан записать `workdir/.agent/result.json`):

    {
      "outcome": "done | needs_human | blocked | failed",
      "summary": "1-3 предложения",
      "details_md": "опционально, длинный текст в markdown",
      "artifacts": ["относительные пути / commit sha / ветка"],
      "questions": [ {"text": "...", "options": ["..."]} ],   # только для needs_human
      "blocker": "кто/что блокирует",                        # только для blocked
      "next_owner": "human | <role-name> | none"
    }

**Правила runner'а**: если файла нет или он невалиден → `outcome=failed`, причина в `summary`;
runner никогда не «додумывает» исход за агента. Runner также пишет `workdir/.agent/run.log`
(stdout/stderr агента) и `workdir/.agent/result.json` не трогает.

`.agent/` добавь в `.gitignore` целевого репо *или* явно решаем коммитить — предложи и обоснуй, я выберу.

Отчёт → стоп.

## Шаг 3. Адаптер claude + local backend

1. `adapters/claude`: функция, которая по `role.yaml`, workdir и `.agent/run.json` возвращает готовый
   запуск: команду `claude -p ...` (список аргументов + env), сгенерированный `settings.json` роли
   (разрешения из `tools`, хуки из `hooks`), изолированный конфиг-каталог с копиями только тех скиллов,
   что перечислены в роли. Промпт = склейка `includes` + `role.md` + короткая инструкция
   «начни с чтения `.agent/task.md` и `.agent/context.md`». Агент ничего не знает о `role.yaml` —
   всю трансляцию в нативные механизмы Claude Code делает адаптер.
2. `backends/local`: запускает команду в workdir с таймаутом из `limits`, пишет `run.log`,
   возвращает код выхода.
3. `runner`: `load_role → prepare_input → backend.run → parse_result → print & exit code`.
4. `bin/run-agent` — CLI: `--role`, `--workdir`, `--backend {local,docker}`, `--task <file>`, `--dry-run`.
   `--dry-run` печатает не только команду, но и весь собранный контекст: итоговый системный промпт,
   сгенерированный `settings.json`, список видимых агенту скиллов, env (с замаскированными секретами).
   Это основной инструмент проверки «агент получает то, что задумано» — без запуска и трат токенов.
5. Граница ответственности: `run-agent` не клонирует репозитории и не знает, откуда взялся workdir.
   Workdir — любой git-репозиторий (в проде — worktree проекта, который создаст runner на этапе 2).
   Никаких `--repo-url`, никакого `git clone` внутри `run-agent`.
6. Изоляция конфигурации: агент не должен подхватывать хостовые пользовательские настройки/скиллы/плагины,
   только то, что задано ролью. Проверь, как это делается (config dir), и задокументируй.

Проверка: `--dry-run` показывает корректную команду; затем реальный запуск (см. шаг 4).

Отчёт → стоп.

## Шаг 4. Smoke-тест на локальном бэкенде

0. Самая первая проверка роли: `task.md` = «Ответь, кто ты, что на входе, что на выходе, какие исходы
   и какие инструменты тебе доступны; ничего не делай; запиши ответ в result.json как `outcome=done`».
   Ответ должен совпадать с `role.yaml`/`role.md`. Если нет — проблема в адаптере, а не в промпте.
1. `scripts/smoke.sh`: создаёт временный git-репо с `README.md`, кладёт `task.md`:
   «Создай файл `hello.py`, печатающий 'hello from <role>', добавь `tests/test_hello.py`, прогони pytest,
   закоммить», запускает `bin/run-agent --role implementer --workdir <tmp> --backend local`,
   проверяет: exit 0, `result.json` валиден, `outcome=done`, коммит существует, тест проходит.
2. Второй сценарий: `task.md` с намеренно неоднозначной задачей («сделай интеграцию с платёжной системой») —
   ожидаем `outcome=needs_human` с `questions`. Если агент вместо этого начинает что-то делать —
   правь `role.md`/`base.md`, а не runner.
3. Запиши в `docs/notes/smoke.md`: сколько заняло, сколько стоило (если доступно из вывода claude), что ломалось.

Отчёт → стоп.

## Шаг 5. Бэкенд sbx

1. `backends/sbx`: песочница на прогон — `sbx create` с рабочими пространствами,
   `sbx exec` с командной строкой из `Launch`, `sbx rm --force` в любом исходе.
   Именно `exec`, а не `run`: `sbx run claude` подставляет свои дефолты, включая
   `--dangerously-skip-permissions`, и перекрывает режим разрешений роли.
2. Запуск: рабочая папка отдаётся на запись, материалы роли — с суффиксом `:ro`,
   каталог конфигурации агента — на запись. Пути внутри совпадают с хостовыми,
   поэтому команда агента не меняется. Секреты — только переменными окружения,
   и только те, что задал сам запуск: окружение неизолированного запуска внутрь
   не передаётся. Значение креда идёт не в аргументах, а в окружении процесса `sbx`
   (форма `--env ИМЯ`): командная строка видна в `ps`.
   Сеть пока обычная; закрывается неинтерактивно через `sbx policy set-default deny-all`
   и `sbx policy allow network` — не в этом этапе.
3. Тот же `runner` с `--backend sbx` должен пройти все smoke-сценарии шага 4
   без изменений в роли.
4. Заметки: устройство песочницы и грабли — в `docs/notes/sbx.md`, передача
   авторизации — в `docs/notes/auth.md`.

Отчёт → стоп.

## Чего НЕ делать на этом этапе

- Не подключать JIRA, не писать поллинг/lease/reaper, не делать несколько ролей.
- Не делать докерный бэкенд, пока нет машины без KVM: изоляцию закрывает sbx.
- Не изобретать формат скиллов — использовать SKILL.md как в Claude Code.
- Не давать агенту сетевые/деструктивные инструменты сверх необходимого для smoke-теста.
- Не «оптимизировать промпт» роли до того, как smoke-тест покажет конкретную проблему.
- Не делать роль скиллом и не полагаться на то, что агент сам «прочитает и применит» role.yaml.
