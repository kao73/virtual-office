# Подпроект 1а «Шов» — профиль клиента, адаптер трекера, конформанс-сьют

> Статус: **утверждён владельцем 2026-07-28** (брейншторм этапа 1).
> Родитель: [конституция](../concept.md) §5 (жизненный цикл), §6 (профиль и адаптер),
> §12 (дорожная карта); решения Р-04, Р-15, Р-19, Р-20, Р-25.

## Рамки

Этап 1 разбит на два подпроекта (решение владельца, брейншторм 2026-07-28):

- **1а «Шов»** (этот документ): схема профиля клиента + валидатор, интерфейс
  адаптера трекера, адаптеры `yougile` и `jira`, конформанс-сьют с YouGile-полигоном,
  смоук-прогон jira-адаптера в CRM3.
- **1б «Роль и раннер»** (отдельная спека после 1а): Делопроизводитель, лизы, журнал,
  cron-раннер с локом (Р-22), `office-init`, проверка селективной загрузки контекста (Р-21).

Развилки, зафиксированные владельцем на брейншторме:

1. Два подпроекта, 1а первым.
2. Адаптер — **Python CLI** (исполняемый код, не промпты): конформанс-сьют и
   безусловная маркировка Р-25 промптами не гарантируются.
3. **YouGile — полигон разработки**: сьют в дев-цикле гоняется против отдельной
   YouGile-доски; jira-адаптер проверяется тем же сьютом против песочной метки
   в CRM3 — вручную, минимум один раз до боевого цикла этапа 1.
4. Транспорт — **прямой REST** в обоих адаптерах; проект под **uv**
   (Python 3.12+, зависимости PyYAML, requests, pytest, jsonschema).

## Архитектура

Раскладка по §11 конституции (`adapters/`, `templates/` — в корне плагина):

```
adapters/
  pyproject.toml            # uv-проект "office-adapter", Python 3.12+
  office_adapter/
    cli.py                  # точка входа: uv run office-adapter <команда>
    profile.py              # поиск и загрузка .office/profile.yaml, валидация по схеме
    interface.py            # абстракция: типы Card/State + контракт провайдера
    base.py                 # обвязка: фенс-контроль, маркировка Р-25, read-back
    providers/
      yougile.py            # YouGile REST API v2, Bearer-токен
      jira.py               # Jira Server REST v2, basic auth
  tests/
    unit/                   # base/profile на in-memory фейке, без сети
    conformance/            # контрактные тесты против живого трекера
templates/
  profile.schema.json       # JSON-схема профиля клиента (§6)
  profile.example.yaml      # закомментированный пример профиля
```

**Принцип «сэндвича»:** роль → CLI → `base.py` → провайдер → REST. Всё, что
конституция требует делать *безусловно*, живёт в `base.py` — провайдер не получает
управления раньше этих проверок, роль не может их обойти иначе как отказавшись от
адаптера целиком (что запрещено контрактом роли и оставляет след):

- **Огораживание (§5):** `list_cards` возвращает только карточки участка; любая
  операция над карточкой вне фенса — ошибка `fence_violation`. Немаркированные
  карточки для офиса не существуют — ни читать, ни комментировать.
- **Маркировка (Р-25):** `comment` и `create_card` вшивают структурный маркер
  до вызова провайдера.
- **Read-back:** каждая запись верифицируется обратным чтением (урок jira-cli:
  Jira Server «разрешающий, не валидирующий» — exit 0 не значит записано).

## CLI-контракт

Команды повторяют интерфейс §6 один в один; всегда JSON на stdout — роли-скиллы
вызывают через Bash и парсят машинно:

```
uv run office-adapter list-cards --state <abstract-state>
uv run office-adapter read-card <id>
uv run office-adapter move <id> --state <abstract-state>
uv run office-adapter comment <id> --role <role> --body-file <file>
uv run office-adapter create-card --role <role> --title ... --state ... [--body-file ...]
uv run office-adapter link <id-a> <id-b>
uv run office-adapter attach <id> <file>
uv run office-adapter capabilities          # что умеет адаптер (для матрицы «сделано/пропущено»)
uv run office-adapter validate-profile      # проверка .office/profile.yaml по схеме
```

- Профиль ищется от текущей директории вверх (роль просыпается в директории клиента);
  `--profile <path>` — явное переопределение.
- `--role` обязателен для публикующих команд — уходит в маркер.
- Креды — **только из окружения**: `YOUGILE_API_KEY` (имя — по существующей
  конвенции машины владельца); `JIRA_API_TOKEN` + `JIRA_LOGIN`.
  В профиле, репозитории и выводе CLI секретов нет; значения токенов не логируются.

## Интерфейс адаптера и модель данных

**Абстрактные состояния** (§5): `idea`, `analysis`, `design_gate`, `ready_for_dev`,
`in_dev`, `ai_qa`, `merge_gate`, `bookkeeping`, `external_qa`, `done`, `needs_input`.
Профиль обязан отобразить в трекер только те состояния, которые использует текущий
этап; неотображённое состояние при обращении — явная ошибка конфигурации.

**Модель карточки** (JSON, который видят роли): `id`, `key` (человекочитаемый,
например `CRM3-80`), `title`, `description`, `state` (абстрактное; `null` +
`raw_state`, если представление не отображается назад), `url`, `labels`,
`comments[]` (`author`, `created`, `body`, `office_marker`: `null` | `{role}`),
`links[]`, `attachments[]`.

**Контракт провайдера** — семь операций §6: `list_cards(state)`, `read_card(id)`,
`move(id, state)`, `comment(id, body)`, `create_card(...)`, `link(a, b)`,
`attach(card, file)`. `attach` и `link` — заявляемые способности: `capabilities()`
возвращает матрицу; отсутствие способности — явная ошибка `capability_missing`
при вызове, деградацию (например, ссылки вместо вложений) решает роль, и она
видна в пакете гейта (Р-12).

**Маркер офисного контента (Р-25):** первая строка публикуемого текста —
`[ai-office:<role>]` (например `[ai-office:clerk]`). Детекция — регулярка по
первой строке; правило доверия Р-20: доверенный вход = «автор — владелец **и**
первая строка не матчится маркером». Поле `office_marker` в модели комментария —
результат этой детекции, роли не парсят маркер сами. При появлении у клиента
техаккаунта (`office_account` в профиле) правило апгрейдится до чистого авторства;
маркировка при этом не отключается (след остаётся человекочитаемым).

**Read-back:** `move` перечитывает состояние, `comment`/`create_card` перечитывают
и находят опубликованное по маркеру и содержимому, `attach` проверяет появление
вложения. Расхождение — ошибка `verification_failed`, не молчаливый успех.

## Провайдеры

### yougile

- REST API v2 YouGile: база `https://yougile.com/api-v2`, Bearer-токен
  (подтверждено исходником локального yougile-mcp; MCP-инструменты — справочник
  форм данных, но адаптер ходит в REST напрямую).
- Маппинг: абстрактное состояние → колонка доски (`states.<state>.column`);
  фенс — `board:<id>` (доска целиком = участок офиса).
- `comment` → сообщение в чате задачи; `attach` → загрузка файла.
- `link` → нативных связей у YouGile нет: `capabilities().link = false` в v1.

### jira

- Jira Server REST v2 (`/rest/api/2`), basic auth `JIRA_LOGIN` + `JIRA_API_TOKEN`
  (Bearer на этом инстансе не работает). Базовый URL берётся из `tracker.url` профиля; создание карточек — в `tracker.project` с типом `tracker.issue_type`.
- Маппинг: абстрактное состояние → статус (+ опционально метка):
  `states.<state>: {status: "...", label: "..."}`; фенс — `label:<name>`.
- `move` — через discovery `/transitions`: ищется переход, ведущий в целевой статус;
  прямого перехода нет — ошибка с перечислением доступных (многошаговые цепочки
  в v1 не строим: неявный проезд через промежуточные статусы — сюрприз для владельца).
- `comment` — тело уходит **как есть** (plain text безопасен в wiki-разметке;
  Markdown→wiki конвертация не делается — это источник молчаливой порчи).
- `link` → issue link типа Relates; `attach` → `/attachments` (заголовок
  `X-Atlassian-Token: no-check`).
- Уроки jira-cli-скилла вшиты в код: обязательный read-back; select-поля читаются
  объектом, пишутся значением; имена статусов/типов копируются из discovery,
  не из памяти (look-alike символы: тип `Вug` с кириллической «В»).

## Профиль клиента и схема

- `templates/profile.schema.json` — JSON Schema (draft 2020-12), покрывает полную
  форму §6; подпроект 1а *использует* только секцию `tracker`, но схема едина,
  чтобы `office-init` (1б) и роли следующих этапов не перекраивали её.
- `tracker.fence`: `label:<name>` (jira) | `board:<id>` (yougile).
- `tracker.states`: объект «абстрактное состояние → представление провайдера»
  (формы выше). Валидатор проверяет, что представления соответствуют провайдеру.
- Провайдер-специфичные ключи tracker: jira требует url (базовый URL сервера), project (ключ проекта), issue_type (тип создаваемых карточек); для yougile дополнительных ключей нет. Валидатор проверяет их вместе с формой фенса и представлений.
- Неизвестные ключи верхнего уровня и внутри `tracker` — **ошибка** валидации
  (опечатка в ключе не должна тонуть молча); расширение схемы едет вместе с
  версией плагина.
- `validate-profile` — та же валидация из CLI; её же зовёт визард `office-init` в 1б.

## Конформанс-сьют

Контрактные тесты (`tests/conformance/`), параметризованные провайдером:
«проверяем шов, а не заглушки» (§6). Один и тот же набор гоняется против любого
адаптера; выбор — `OFFICE_TEST_PROVIDER=yougile|jira` + конфиг полигонов
(id досок/проектов и маппинг состояний полигона — не секреты, лежат в
`tests/conformance/polygons.yaml`; токены — из env).

- **Полигон YouGile** — отдельный проект в аккаунте владельца (создаётся один раз;
  bootstrap-скрипт в сьюте), дев-цикл: сьют бежит свободно, коллеги его не видят.
- **Полигон Jira** — песочная метка `ai-office-sandbox` в CRM3; прогон **ручной**
  (сьют по умолчанию его не трогает), обязателен минимум один раз до боевого
  цикла этапа 1. Карточки создаются с меткой песочницы и никогда не попадают
  в участок офиса (`ai-office`).
- Каждый прогон несёт уникальный run-id в заголовках карточек; teardown обязан
  убрать за собой: YouGile — удаление/архив, Jira — перевод в терминальный статус
  и снятие песочной метки (удаления у обычных прав нет).
- Секции сьюта: CRUD-операции интерфейса; **фенс** (карточка вне участка невидима
  для `list_cards` и неприкасаема для операций); **маркировка** (всё опубликованное
  детектируется правилом доверия Р-20); **read-back честность** (записанное
  действительно читается назад); **capabilities** (адаптер без `attach`/`link`
  проходит сьют с явным skip секции — как §6 велит для опциональных способностей).
- Юнит-тесты (`tests/unit/`) — логика `base.py` и `profile.py` на in-memory
  фейк-провайдере, без сети: фенс, маркировка, коды ошибок, разбор профиля.

## Обработка ошибок

- Структурная ошибка — JSON на stderr: `{error, message, details}`;
  коды выхода: `0` успех; `1` usage/профиль; `2` ошибка трекера/сети (после ретрая);
  `3` `verification_failed` (read-back разошёлся); `4` `fence_violation`;
  `5` `capability_missing`.
- Сетевые ошибки и 5xx — **один** ретрай (принцип §8: «инфра-сбой ≠ провал, один
  ретрай»); дальше — честная ошибка, роль решает про `needs_input`.
- Молчаливых деградаций нет: всё, что не сделано, видно в коде выхода и JSON ошибки.

## Критерий готовности 1а

1. Конформанс-сьют зелёный: `yougile`-адаптер против YouGile-полигона.
2. Тот же сьют зелёный: `jira`-адаптер против песочницы CRM3 (ручной прогон,
   с уборкой за собой).
3. `validate-profile` принимает `templates/profile.example.yaml` и отклоняет
   профили с опечатками/чужими представлениями состояний.
4. Секреты не встречаются ни в репозитории, ни в выводе CLI, ни в тестовых логах.

## Вне скоупа (YAGNI)

- Механизм запоминания состояния-источника при парковке `needs_input` (§5) — в 1б,
  вместе с ролью, которой он нужен.
- Протокол перечитывания Р-19 (базис карточки) — обязанность ролей 1б+; `base.py`
  лишь оставляет для него место (операции принимают ожидаемое состояние опционально).
- Атомарный claim/CAS — маркер конституции при параллельности > 1.
- Markdown→wiki конвертация, форматированные комменты.
- Облачные раннеры, `office_account`-техаккаунт (поле в схеме есть, аккаунта нет).

## Риски

- **Workflow CRM3** может требовать многошаговых переходов или обязательных полей
  на транзишнах — вскроется на смоуке; митигация: discovery транзишнов и честная
  ошибка с перечислением, дальше — правка маппинга профиля, не кода.
- **Поведение YouGile API** (лимиты, чат задач) — проверяется сьютом в первые дни;
  расхождения фиксируются в спеке провайдера.
- **Права в CRM3**: предполагается право ставить/снимать метки и двигать карточки
  под аккаунтом владельца — то, чем он и так пользуется руками.
