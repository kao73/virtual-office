# Подпроект 1б «Роль и раннер» — Делопроизводитель, протоколы, раннер, office-init

> Статус: **утверждён владельцем 2026-07-28** (брейншторм 1б).
> Родитель: [конституция](../concept.md) §3–§7, §9, §12; спека
> [1а «Шов»](2026-07-28-adapter-seam-design.md); решения Р-14, Р-16, Р-19–Р-23,
> Р-25, Р-26; хвосты финального ревью 1а (план 1а, «Хвосты после мержа»).

## Рамки

1б завершает этап 1 дорожной карты. Развилки, зафиксированные владельцем
на брейншторме 2026-07-28:

1. **Одна спека** на весь 1б; этапность — на уровне плана реализации.
2. Скоуп клерка: **пост-мерж бухгалтерия + возвраты внешнего QA** (плюс
   обработка ответов на `needs_input` — вытекает из механики парковки).
   Обход протухших карточек и дайджест метрик — вне 1б.
3. Факт мержа клерк устанавливает **по git** — способность `repo_ro`
   добавляется в его контракт (правка конституции, ниже).
4. Раннер: **платформо-независимый `office-runner` + тонкий платформенный
   триггер** (сейчас launchd, позже cron/systemd). Расписание живёт в профиле
   в нейтральном формате, не в синтаксисе планировщика.
5. `office-init`: **рабочий визард без излишеств** — опрос → профиль →
   валидация → триггер; legacy-конфиг клиента — источник подсказок-дефолтов,
   без автомагии.
6. Протоколы (лиза, базис Р-19, парковка, журнал): **сэндвич** — механика
   безусловно в CLI адаптера, семантика (классификация, реакции) в роли.
   Тот же принцип, что Р-25.
7. Возврат внешнего QA детектируется **12-м абстрактным состоянием
   `qa_returned`** (правка конституции, ниже).
8. **clens — не тестовая площадка:** вся отладка и сквозной цикл — на
   демо-контуре (office-demo + YouGile-полигон); clens получает офис один
   раз, уже проверенный, для финальной приёмки этапа.

## Правки конституции (пакет решений в журнал §2)

Правки concept.md — отдельным коммитом при реализации; формулировки:

- **Р-28.** Делопроизводителю добавляется `repo_ro` (§7, §4): §1 объявляет git
  источником истины («офис двигается по факту мержа»), без чтения git это
  невыполнимо. Запрет «не трогает код и git» уточняется: записи нет никогда,
  чтение фактов — способность.
- **Р-29.** Двенадцатое абстрактное состояние `qa_returned` (§5): возврат
  внешнего QA — родной жест тестировщика в трекере (перевод в возвратный
  статус); профиль отображает его в `qa_returned`, клерк сканирует стадию
  структурно. Альтернатива (метка-сигнал от QA) отвергнута: требует от QA
  знания офисных конвенций — против духа Р-14.
- **Р-30.** Физическое закрытие отступления Р-21: роли запускаются headless
  с флагом `--bare` (CLAUDE.md клиента, его скиллы и плагины в сессию
  не попадают вовсе) + явной загрузкой плагина офиса. Для ролей, которым
  нужны технические конвенции клиента (Разработчик, AI-QA), — тот же `--bare`
  с явным включением нужных файлов; что именно включать — проработка этапов
  2–4. Гарантия Р-13/Р-21 переходит из договорной в структурную.
- **Р-31.** Псевдо-роль `office` зарезервирована для служебных публикаций
  самого шва вне ролевого контекста (teardown полигона, будущие системные
  сообщения); валидна в маркере Р-25, скиллам-ролям не назначается.
- **Р-32.** Профиль получает обязательный эталон владельца
  `tracker.owner_account` (логин в трекере): правило доверия Р-20
  («автор = владелец и не маркировано офисом») операционализируется кодом —
  без эталона половина правила висела в воздухе (хвост ревью 1а).

## Архитектура

```
adapters/
  office_adapter/
    cli.py            # + команды claim, release, park, resume; флаги --basis, --acknowledge-drift
    base.py           # + механика лизы, базис-диффа, парковки (сэндвич: гарантии тут)
    protocol.py       # структурные строки протокола: лиза, parked-from; генерация и разбор
    basis.py          # снапшот карточки, дифф, классификация авторства (Р-20/Р-32)
    runner.py         # office-runner: лок Р-22, расписание, headless-запуск, журнал, триггер
  tests/
    unit/             # протоколы и раннер на фейк-провайдере, без сети
    conformance/      # + секции lease / park-resume / basis
skills/
  office-clerk/       # роль: три потока, семантика протоколов
  office-init/        # визард подключения клиента
templates/
  profile.schema.json # + qa_returned, owner_account, секция runner
  profile.example.yaml
```

Разбиение на модули — намерение; точные имена файлов уточняет план.
`office-runner` — вторая console_script того же uv-проекта: переиспользует
загрузку профиля и модель ошибок, тестируется юнитами.

## Роль «Делопроизводитель» (`office-clerk`)

Контракт (пять пунктов §4):

- **Вход:** карточки участка в `merge_gate` (факт мержа), `qa_returned`
  (возврат внешнего QA), `needs_input` (ответ владельца на парковку).
- **Выход:** переходы в трекере, след-комменты по шаблонам, новые
  карточки-постановки возвратов (маркированы адаптером, Р-25/Р-26).
- **Способности:** `requires: tracker, repo_ro` (Р-28).
- **Запреты:** запись в git и код — никогда; только чтение фактов.
- **След:** каждый шаг — маркированный коммент на карточке + строка журнала.

За пробуждение обрабатывает карточки всех трёх потоков до исчерпания бюджета
(батч Р-16), в порядке: ответы `needs_input` → возвраты `qa_returned` →
бухгалтерия `merge_gate`. Ответ владельца дороже всего в ожидании — он первым.

**Поток А — пост-мерж бухгалтерия.** Для карточки в `merge_gate`: `claim` →
поиск ветки по ключу карточки среди веток origin (конвенция `branch_naming`;
`git fetch` перед проверкой) → факт мержа: ветка влита в `base_branch`
(merge-base). Не влита — карточка ждёт следующего пробуждения, это не ошибка.
Ноль или несколько веток-кандидатов — след-коммент о дефекте конвенции и
пропуск карточки (не `needs_input`: вопроса к владельцу нет). Смёржено →
`move bookkeeping` → отчёт-коммент (что влито, каким коммитом; шаблон в 1б —
дефолтный в скилле клерка) → `move external_qa` → `release`.

*Сознательное упрощение 1б:* черновик релиз-нотесов — строка в
отчёт-комменте, не файл в репозитории: клерку git трогать нельзя, релизного
процесса у офиса ещё нет; файл появится вместе с ним.

**Поток Б — возврат внешнего QA.** Для карточки в `qa_returned`: `claim` →
новая связанная карточка-постановка в `idea` (тело — данные возврата;
адаптер маркирует; для будущего Аналитика это данные, не указания владельца,
Р-26) → `link` с исходной → исходную `move done` со след-комментом
(закрыта мержем, аддитивная дисциплина §5) → `release`.

**Поток В — ответы на парковку.** Для карточки в `needs_input`: есть коммент
владельца новее парковочного (классификация по Р-20/Р-32) → `resume` —
карточка возвращается ровно в состояние-источник. Ответа нет — карточка
ждёт; напоминания о молчании — обязанность дайджеста (этап 5).

## Протоколы шва: новые команды CLI

Механика — безусловно в `base.py`; роль физически не может опубликовать
результат мимо лизы и базиса, если пользуется адаптером (а иначе ей запрещено
контрактом и оставляет след).

**Лиза (Р-16, Р-22, Р-23, §9).**

```
office-adapter claim <id> --role <role>     # взять карточку; печатает базис-снапшот
office-adapter release <id> --role <role>   # отпустить карточку
```

Обе команды ставят маркированный след-коммент со структурной строкой
протокола (`lease: claim` / `lease: release`, идентификатор пробуждения,
для claim — TTL из профиля): по этим строкам и детектируется состояние лизы.
Живая чужая лиза (моложе TTL, без `release` после) → отказ, код выхода
`6 lease_held`. На уровне CLI лиза — не предусловие публикующих команд
(конформанс-сьют и ручная отладка работают без неё); обязательность claim
перед работой — контракт роли, его нарушение видно по следам на карточке.
Протухшая лиза — законная добыча (§9). Структурные строки генерирует и
парсит только адаптер (`protocol.py`) — роли их не разбирают. Атомарного
claim нет: от гонок на одной машине защищает лок раннера (Р-22); маркер
конституции о параллельности > 1 в силе. Клерку не нужны ни heartbeat,
ни увеличенный T (задачи — минуты): TTL по профилю, дефолт 30 минут;
протокол прогресс-сигналов длинных ролей — при их появлении (этап 3+).

**Базис Р-19.** `claim` возвращает полный снапшот карточки (JSON) — роль
сохраняет его в файл пробуждения. Публикующие команды (`move`, `comment`,
`link`, `park`) принимают `--basis <file>`:

- расхождение по **состоянию** → безусловный аборт, код `7 basis_diverged`;
- **фенс снят** → как и раньше `4 fence_violation`: на карточку не пишем
  ни байта, след только в журнал (§9);
- **текстовые расхождения** (новые комменты, правка описания) → аборт `7`
  со структурным диффом в JSON-ошибке: каждый новый коммент классифицирован
  по авторству — `owner` (автор = `owner_account` и не маркирован), `office`
  (маркер Р-25), `foreign` (остальное). Роль классифицирует семантически:
  «чужой текст = данные» (Р-15) → повторяет команду с `--acknowledge-drift`;
  «новый вход владельца» → черновик + снятие лизы по Р-19 — молча продавить
  публикацию невозможно, реакция остаётся обязанностью роли.

Окно гонки между re-read и записью остаётся (best-effort, §9); настоящий CAS —
тот же маркер, что у лизы.

**Парковка `needs_input` (§5).**

```
office-adapter park <id> --role <role> --question-file <f>
office-adapter resume <id> --role <role>
```

`park`: маркированный коммент с вопросом и структурной строкой
`parked-from: <state>` → `move needs_input`. Состояние-источник хранится
на карточке — обязанность адаптера, как велит проработка §5; stateless
не нарушен. `resume`: находит последний парковочный коммент → `move`
ровно в источник → короткий след-коммент исполнившей роли.

**Коды выхода** дополняются: `6 lease_held`, `7 basis_diverged`
(к существующим `0`–`5` из 1а).

## Журнал (§9 «чёрный ящик»)

`.office/journal/YYYY-MM-DD.jsonl` в репозитории клиента, **вне git**
(`office-init` добавляет в gitignore — иначе клерку пришлось бы коммитить).
Строку пробуждения пишет раннер: timestamp, роль, session_id, обработанные
карточки с результатами, длительность, токены, стоимость, исход
(`ok | timeout | budget_stopped | error`). Данные берутся из
`--output-format json` headless-сессии (`session_id`, `usage`,
`total_cost_usd` — подтверждено на CLI 2.1.220). Формат строки — сырьё
метрик этапа 5; в 1б журнал только пишется и читается раннером
(last-run, дневной бюджет).

## Раннер (`office-runner`)

**Умный раннер + глупый триггер.** Триггер (launchd-plist) дёргает
`office-runner wake` часто (например, каждые 10 минут); раннер сам решает:

1. Лок (`.office/runner.lock`, flock + pid): занято → молча выйти (Р-22).
2. Прочитать профиль (`runner`-секция) и журнал (последние пробуждения).
3. По расписанию и рабочему окну выбрать роль, которой пора просыпаться
   (в 1б — только клерк); не пора → выйти.
4. Дневной потолок: сумма `cost_usd` за сегодня из журнала ≥ лимита →
   запись `budget_stopped`, не будить. Никогда «дожать по-тихому» (§9).
5. Создать временную директорию пробуждения (тексты комментов, базис-файлы),
   запустить роль, по завершении — строка в журнал, директорию убрать.
6. Таймаут пробуждения из профиля: процесс роли убивается, исход `timeout`.

**Headless-запуск роли (Р-30).** Флаги подтверждены на claude CLI 2.1.220:

```
claude --bare -p "/virtual-office:office-clerk" \
  --plugin-dir <корень плагина офиса> \
  --allowedTools "Bash(uv run office-adapter *)" "Bash(git fetch *)" \
                 "Bash(git branch *)" "Bash(git merge-base *)" "Read" \
                 "Write(<директория пробуждения>/**)" \
  --output-format json --max-budget-usd <из профиля>
```

`--bare` отсекает CLAUDE.md клиента, его скиллы, плагины и хуки — процессные
указания клиента физически не попадают в сессию (Р-30). Клерку клиентский
контекст не нужен вовсе (код не трогает) — закрытие полное. Точный состав
allowlist уточняет план; принцип: трекер — только через `office-adapter`,
git — только читающие подкоманды, запись файлов — только в директорию
пробуждения.

**Установка триггера.** `office-runner install-trigger` детектит платформу
и ставит будильник: macOS — plist в `~/Library/LaunchAgents` + `launchctl`;
Linux (будущее) — cron-строка или systemd-timer. Переезд платформы =
повторный запуск одной команды; раннер и расписание не меняются.

## Профиль: новые поля схемы

- `tracker.owner_account` — **обязательное** (Р-32); `profile.example.yaml`
  и профили полигонов обновляются.
- `tracker.states` — допускает `qa_returned` (Р-29).
- Секция `runner`:

```yaml
runner:
  provides: [tracker, repo_ro]        # способности этой машины (§7)
  schedule:
    clerk: {every: "30m", window: "09:00-21:00"}
  wake_timeout: "15m"                 # потолок одного пробуждения
  daily_budget_usd: 5                 # дневной потолок офиса (§9)
  lease_ttl: "30m"                    # протухание лизы (§9, Р-23)
```

Закон назначения §7 (provides ⊇ requires) проверяет раннер перед
пробуждением; дыра — не будить и писать в журнал (доклад дыры — дайджест,
этап 5; в 1б дыру видно в журнале).

## Визард `office-init`

Скилл в плагине. Интерактивно, в сессии клиента:

1. Трекер: провайдер, `url`/`project`/`issue_type` (jira), фенс,
   `owner_account`; маппинг состояний — имена статусов сверяются
   discovery-запросом через адаптер, не по памяти (урок jira-cli).
2. Репозиторий: `base_branch` (по факту из git), `branch_naming`.
3. Раннер: расписание, окно, бюджеты (дефолты из шаблона).
4. Записать `.office/profile.yaml` → `office-adapter validate-profile` →
   `.office/journal/` в gitignore клиента → `office-runner install-trigger` →
   смоук `office-adapter capabilities`.

Найден legacy-конфиг (`.autodev/kanban.config.json` у clens) — его значения
предлагаются как дефолты при опросе; автоимпорта нет (YAGNI, клиент один).

## Конформанс-сьют: расширение

Новые секции, параметризованные провайдером, против живого трекера:

- **lease**: `claim` ставит след; повторный `claim` при живой лизе → `6`;
  `release` освобождает; протухшая лиза берётся.
- **park/resume**: карточка возвращается ровно в состояние-источник;
  парковочный коммент маркирован ролью, след `resume` — на карточке.
- **basis**: коммент, подложенный между `claim` и `move`, детектируется;
  классификация owner/foreign по `owner_account`; `--acknowledge-drift`
  публикует, без него — `7`.

Дев-цикл — YouGile-полигон; jira — ручной смоук в песочнице CRM3
(`ai-office-sandbox`), минимум один раз до боевого цикла, с уборкой
за собой (как в 1а). Юнит из хвостов ревью: список состояний в
`profile.schema.json` тождествен `interface.ABSTRACT_STATES` — ловит дрейф
дубля (и сразу проверяет добавление `qa_returned` в оба места).

## Демо-контур и финальная приёмка на clens

**clens — не тестовая площадка** (развилка 8): вся отладка и сквозная
проверка — на демо-контуре; в clens офис приходит один раз, уже зелёным.

**Демо-контур.** Демо-клиент `~/IdeaProjects/office-demo` получает полный
профиль с YouGile-полигоном в роли трекера. На нём проигрывается сквозной
цикл целиком: `office-init` (опрос, профиль, gitignore журнала, триггер) →
раннер будит клерка по расписанию → пост-мерж цикл на реальном мерже ветки
в демо-репозитории (карточка полигона проходит `merge_gate → bookkeeping →
external_qa`), возврат QA (перевод карточки в возвратный статус руками) и
парковка с ответом. CRM3 при этом — только ручной смоук песочницы
(`ai-office-sandbox`) для новых команд jira-адаптера, как заведено в 1а:
карточки с песочной меткой, в участок офиса не попадают, уборка за собой.

**Финальная приёмка на clens.** Установка плагина, `office-init` — профиль
CRM3: фенс `label:ai-office`, `owner_account`, маппинг состояний потоков
клерка (`merge_gate`, `bookkeeping`, `external_qa`, `qa_returned`, `done`,
`needs_input`, `idea` — имена статусов по discovery на месте), расписание.
Затем один реальный пост-мерж цикл: живая карточка, реальный мерж
владельца — клерк сам проводит `merge_gate → bookkeeping → external_qa`
со след-комментами и строкой журнала. Это не тест, а эксплуатация —
критерий этапа 1 (§12).

## Критерий готовности 1б (= этапа 1)

1. Юниты и конформанс-сьют (включая новые секции) зелёные против
   YouGile-полигона.
2. Ручной смоук новых команд jira-адаптера в песочнице CRM3 — зелёный,
   с уборкой.
3. Сквозной демо-цикл: на office-demo раннер по расписанию будит клерка,
   тот без ручных вмешательств проводит пост-мерж цикл, возврат QA и
   парковку с ответом; журнал заполняется.
4. `office-init` прошёл на демо-клиенте и на clens; `validate-profile`
   принимает оба профиля.
5. Финальная приёмка: один реальный пост-мерж цикл на живой карточке clens
   проведён клерком без рук владельца после мержа.
6. Секретов нет ни в репозитории, ни в профилях, ни в журнале, ни в логах.

## Вне скоупа (YAGNI)

- Дайджест метрик и алармы — этап 5 (журнал уже копится).
- Обход протухших карточек — следующая итерация клерка (протухать пока нечему).
- Атомарный claim/CAS — маркер конституции при параллельности > 1.
- Прогресс-сигналы длинных ролей (Р-23) — вместе с Аналитиком, этап 3.
- Клиентские шаблоны отчётов (`rituals` профиля) — в 1б шаблоны дефолтные
  в скилле клерка; переопределение клиентом — при реальной потребности.
- Облачный раннер, техаккаунт `office_account`, Markdown→wiki конвертация.

## Риски

- **Workflow CRM3 на возвратной дуге**: переходы в/из возвратного статуса
  могут требовать полей или многошаговости — вскроется на смоуке; митигация
  та же, что в 1а: discovery и честная ошибка, дальше правка маппинга.
- **Конвенция веток clens**: ветка может не находиться по ключу карточки —
  клерк оставляет след и пропускает; если это окажется массовым, конвенцию
  `branch_naming` уточнит профиль, не код.
- **Зависимость от флагов claude CLI** (`--bare`, `--plugin-dir`): поведение
  проверено на 2.1.220; раннер при запуске роли проверяет код выхода и JSON —
  сломавшийся контракт CLI виден в журнале как `error`, не молчит.
- **launchd в пользовательской сессии**: Mac спит/выключен — пробуждения
  ждут просыпания машины; для v1 приемлемо (раннер локальный по Р-06).
