# Этап 0 «Фундамент» — скелет плагина и маркетплейс-манифест

> Статус: утверждён владельцем 2026-07-27 (брейншторм этапа 0).
> Родитель: [`docs/office.md`](../office.md) §1 «Что это»; [`docs/decisions.md`](../decisions.md)
> §11 «Упаковка и дистрибуция», §12 «Дорожная карта проработки», Р-08.

## Цель

Репозиторий `virtual-office` становится валидным плагином Claude Code и одновременно
собственным маркетплейсом (Р-08). Критерий готовности этапа — плагин устанавливается
в проект-клиент с локального пути и его скилл виден в сессии клиента.

По решению владельца проверка установки идёт на **демо-проекте** (гипотетический
клиент), не на clens: боевой клиент №1 не трогается до этапа 1, когда появится
первая живая роль. Критерий §12 «плагин устанавливается в клиента (пусть пустой)»
выполняется на демо-клиенте как репетиция подключения.

## Сверка механики с документацией

Проведена двумя путями: эмпирически (живые манифесты установленных плагинов,
`claude plugin validate --strict` на пробном скелете, CLI `--help`) и по официальной
документации (code.claude.com/docs, справка агента-исследователя). Ключевые факты,
на которые опирается дизайн:

- `plugin.json` лежит в `.claude-plugin/`; единственное обязательное поле — `name`
  (kebab-case). Пустой плагин без скиллов валиден.
- Скиллы автообнаруживаются в `skills/<имя>/SKILL.md` **в корне плагина**
  (не внутри `.claude-plugin/`); после установки именуются `<plugin>:<skill>`,
  то есть `virtual-office:office-about`.
- `marketplace.json` лежит тоже в `.claude-plugin/`; обязательные поля: `name`,
  `owner`, `plugins[]`. Плагин в том же репозитории описывается `source: "./"`
  (путь — от корня маркетплейса).
- Версия резолвится по приоритету: `plugin.json` → запись в `marketplace.json` →
  commit SHA. `claude plugin tag` создаёт релизный тег `{name}--v{version}` и
  проверяет согласованность манифестов.
- `claude plugin marketplace add` принимает локальный абсолютный путь;
  `claude plugin install <plugin>@<marketplace>` поддерживает `--scope local`,
  который не пишет в отслеживаемые git-файлы клиента.
- `claude plugin validate <path> --strict` валидирует оба манифеста и frontmatter
  скиллов, warnings трактует как ошибки (режим CI).

## Артефакты

### 1. `.claude-plugin/plugin.json`

```json
{
  "name": "virtual-office",
  "displayName": "Виртуальный IT-офис",
  "description": "Команда AI-агентов, ведущая разработку проекта-клиента через конвейер с фиксированными гейтами контроля владельца",
  "version": "0.1.0",
  "author": {"name": "kao73"}
}
```

Закон версии: **версия живёт только в `plugin.json`**. В записи маркетплейса она
не дублируется — исключаем рассинхрон двух источников. Схема — semver (§11):
`0.x` до боевой обкатки этапа 1; bump минора на этап дорожной карты, патчи — на
исправления внутри этапа.

### 2. `.claude-plugin/marketplace.json`

```json
{
  "name": "virtual-office",
  "description": "Маркетплейс виртуального IT-офиса: репозиторий одновременно плагин и его дистрибуция",
  "owner": {"name": "kao73"},
  "plugins": [
    {
      "name": "virtual-office",
      "source": "./",
      "description": "Команда AI-агентов, ведущая разработку проекта-клиента через конвейер с фиксированными гейтами контроля владельца"
    }
  ]
}
```

Имя маркетплейса совпадает с именем плагина; адрес установки —
`virtual-office@virtual-office`.

### 3. `skills/office-about/SKILL.md`

Скилл-маркер с двумя назначениями:

- **проверочное** — прогоняет весь путь «установка → автообнаружение → загрузка
  скилла в сессии клиента», на который обопрётся этап 1 (`office-init` — тоже скилл);
- **справочное** — честный ответ на «что такое установленный virtual-office»:
  назначение офиса, текущий этап дорожной карты, чего офис пока **не** умеет
  (роли не реализованы), ссылка на справочник в репозитории офиса.

Скилл ничего не делает с проектом клиента — только рассказывает. Не выбрасывается
на следующих этапах: остаётся справкой офиса и обновляется вместе с версией.

### 4. `CHANGELOG.md`

Формат keep-a-changelog, первая запись `0.1.0` — скелет плагина. Ведётся с этапа 0,
как велит §11 («semver + CHANGELOG»).

### 5. Правка `README.md`

Секция «Статус» дополняется фактом: этап 0 реализован, репозиторий — устанавливаемый
плагин; следующий шаг — этап 1.

## Проверка готовности

1. `claude plugin validate . --strict` в корне репозитория — зелёный.
2. Демо-клиент: создаётся `~/IdeaProjects/office-demo` — минимальный git-репозиторий
   (README, ни строчки кода — «пусть пустой»).
3. Из директории демо-клиента:
   `claude plugin marketplace add /Users/aleksejkolesnikov/IdeaProjects/virtual-office`
   → `claude plugin install virtual-office@virtual-office --scope local`.
4. `claude plugin list` показывает плагин; `claude plugin details virtual-office`
   показывает скилл `office-about` в инвентаре компонентов.
5. Финальная проверка — в новой сессии Claude Code в демо-клиенте скилл
   `virtual-office:office-about` виден и отвечает по назначению.
6. `git status` демо-клиента чист (scope `local` не наследил в отслеживаемых файлах).

## Вне скоупа (YAGNI)

`adapters/`, `templates/`, скиллы ролей и `office-init`, hooks/agents/commands,
лицензия, публикация на GitHub, схема профиля клиента — всё по своим этапам
дорожной карты. Подключение к clens — этап 1.

## Риски и открытые хвосты

- Обновление плагина у клиента после правок офиса: `claude plugin marketplace update`
  + `claude plugin update virtual-office` (перезапуск сессии). Войдёт в инструкцию
  подключения на этапе 1.
- Поведение локального маркетплейса при переносе/переименовании папки офиса
  не документировано; путь фиксируется в `known_marketplaces.json` пользователя —
  при переезде папки маркетплейс переподключается заново. Для v1 приемлемо
  (раннер v1 — локальная машина владельца, Р-06).
