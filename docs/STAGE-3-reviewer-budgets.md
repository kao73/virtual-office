# Этап 3. Вторая роль: reviewer, передача между ролями, бюджеты, сеть песочницы

Инструкция для Claude Code. Перед началом прочитай `docs/DESIGN.md`, `docs/contracts/agent-io.md`,
`docs/contracts/tracker-protocol.md`, `docs/notes/stage-2-retro.md`. Этапы 1–2 дали `run-agent`
и runner с одной ролью. Этап 3 добавляет вторую роль и всё, что она вскрывает: передачу задачи
между ролями, разные учётки агентов, круги «правки → ревью», бюджеты и закрытую сеть.

## Цель этапа (definition of done)

Сценарий, который обязан пройти живьём на `mock` и на `jira`:

1. задача в `Ready` → **implementer** делает работу → `Review`;
2. **reviewer** берёт её из `Review`, читает diff и отчёт implementer'а, гоняет тесты,
   не меняет код; исход `done` с `next_owner: implementer` и списком замечаний → задача
   возвращается в `Ready`; implementer при следующем прогоне видит замечания в контексте
   и правит; снова `Review`;
3. reviewer доволен: `done` с `next_owner: human` → задача в `Approved` — конечная колонка
   этапа, дальше человек делает merge; worktree убирается, ветка запушена;
   доска: `Backlog → Ready → In Progress → Review → Approved` + `Blocked`; рабочая колонка —
   опция роли: у implementer'а есть (`In Progress`), у reviewer'а нет — он проверяет
   в `Review` с живой арендой (см. шаг 1);
4. круги «правки → ревью» ограничены: после `max_review_rounds` без одобрения — `Blocked`
   и человек с объяснением;
5. учётки настраиваются: по умолчанию все роли ходят под одной (`accounts.default`),
   и это штатный режим; отдельная учётка на роль — опция. Проверить оба: под одной учёткой
   роли различаются по маркеру, а не по автору, и ответ человека распознаётся; под двумя —
   комментарий reviewer'а не принимается за ответ человека implementer'у и наоборот;
6. каждый прогон пишет стоимость в реестр (всегда); лимиты — опция с режимом на каждый:
   `warn` (запись в лог и в тикет, работа продолжается, по умолчанию) или `stop`
   (задача/роль приостанавливается с объяснением, не молча); без лимитов — только учёт;
7. агент в песочнице не имеет сети, кроме явно разрешённых ролью доменов; прогон
   без разрешения на `github.com` не может ничего скачать, и это видно в логе.

## Общие правила работы

Как на этапах 1–2: шаг → отчёт → коммит → **стоп**. Не забегать вперёд. Всё новое —
сначала тестами на `mock` с поддельным агентом, потом живьём. Флаги `sbx`/`claude` —
проверять, не помнить; записывать в `notes/`. Секреты — только окружение.

Отдельно на этом этапе: **не менять контракт `agent-io.md`** (четыре исхода, `next_owner`,
схема результата) — всё, что нужно reviewer'у, в нём уже есть. Если кажется, что нужен
пятый исход, — остановись и обсуди.

## Шаг 0. Долги этапа 2

0. **Ответ человека после раннерского `Blocked`.** Сейчас `HumanReply` требует, чтобы последний
   маркер роли был `outcome:needs_human`; задачи, заблокированные раннером (`attempts`
   исчерпаны, серия `lease-expired`), человеком не разблокируются никогда. Новое правило
   («Ответ человека» в `tracker-protocol.md`): ответ = не-агентский комментарий после
   **последней записи офиса** при поднятом флаге ожидания, кто бы и чем ни заблокировал.
   Разбор ответов — **отдельный проход** в начале `tick` (один на цикл, системной учёткой),
   не внутри цикла роли. Маршрут — роль из последнего маркера офиса → её `reads_from`;
   роли в графе нет → `human_reply.fallback`. Тесты: блокировка попытками, серией смертей,
   вопросом роли — все три возвращаются ответом человека; ответ до записи офиса — нет.
1. **`Ensure` до `Claim`.** Сейчас `tick` захватывает, потом берёт замок worktree; на одной
   машине второй победитель успевает перезаписать аренду первого, прежде чем упереться
   в flock. Переставить: `Ensure` (замок) → `Claim`; при `ErrClaimLost` — `Unlock`, задачу
   пропустить. Тест: занятая папка → в трекере ничего не изменилось. Обновить
   `tracker-protocol.md`, раздел про барьеры («flock спасает и аренду на одной машине»).
   Два следствия записать как решения: проект вне `projects.yaml` отсеивается до захвата
   (плюс); `Ensure` делает `fetch` и может завести worktree для задачи, которую проиграем
   (принято — папка ключуется задачей и достанется победителю).
2. `stage-2-retro.md` — строка про четыре закрывающих коммита, если ещё нет.

Отчёт → стоп.

## Шаг 1. Граф под две роли; рабочая колонка — опция роли

**Решение этапа: рабочая колонка задаётся на роль, и она необязательна.** Есть — захват
переводит статус (как на этапе 2); нет — «в работе» означает живую аренду в той же колонке,
из которой роль читает. Доска делается для людей: `In Progress` — статус, который на доске
ожидают, поэтому у implementer'а он есть; отдельная колонка под ревью, длящееся минуты, —
шум, поэтому у reviewer'а её нет. Асимметрия намеренная.

Колонки: **Backlog** — куча задач до триажа, вне графа: runner её не читает и в неё не пишет,
это территория человека (или будущей роли planner: `reads_from: Backlog`, `done → Ready`);
**Ready** — очередь implementer'а; **In Progress** — implementer работает; **Review** —
очередь reviewer'а и его же работа; **Approved** — терминальная; **Blocked** — ждёт человека.

Что это стоит: без рабочей колонки JIRA не может быть арбитром для двух раннеров *одной*
роли на одном проекте — для reviewer'а такой режим не поддерживается и записывается как
непредусловие; для implementer'а дверь остаётся (рабочая колонка есть), но не открывается.
Несколько раннеров на проект **с разными ролями** — поддерживается: они читают разные колонки.

Что меняется в контракте (`tracker-protocol.md`, обновить):
- `Claim` записывает `agent_owner / run_id / lease_until` и перечитывает; статус меняет
  **только если** `WorkingStatus != "" && WorkingStatus != текущий`; иначе переход no-op.
  (Не «`!= ExpectStatus`»: для роли без рабочей колонки это дало бы перевод в пустой статус.)
- `reap` и возвраты по исходам: переход делается только если задача не в `reads_from` роли;
  для reviewer'а reap = снять аренду + `event:lease-expired`, переводить некуда.
- Проверка `CheckWorkflow`/`SelfEntry` при старте: только для ролей с `working`, и только
  как информация в лог; вызов можно оставить, но он не должен шуметь про роли без `working`.
- В контракте, «Сколько раннеров на проект»: для ролей без рабочей колонки несколько
  раннеров одной роли не поддерживаются вовсе; для ролей с рабочей колонкой — как было
  (предусловие: захват переходом с полями, отложено).
- DESIGN.md §2.2: «захват = поля + перевод статуса» → «захват = поля; перевод статуса —
  если у роли задана рабочая колонка».
- `jira-setup.sh`: статусы `Backlog`, `Ready`, `In Progress`, `Review`, `Approved`, `Blocked`
  (`Done` в JIRA системный, заводить не нужно); учётка `office-reviewer` — с правами писать
  поля аренды и делать переходы (роль проекта Developers), иначе первый захват под ней —
  403 в рантайме, а не при настройке.
- Доске показать «кто работает» там, где рабочей колонки нет: поле `agent_owner` на карточке
  и/или быстрый фильтр `cf[lease_until] > now()` — описать в `jira-setup.md`, это настройка,
  не код.

`workflow.yaml` (проверка при загрузке остаётся строгой):

    columns: [Backlog, Ready, InProgress, Review, Approved, Done, Blocked]
    terminal: [Approved]                # тут worktree убирается, ветка уже запушена
    # Backlog и Done — вне графа: человеческие колонки «до триажа» и «смержено»;
    # ни одна роль их не читает и не пишет; перечислены ради `runner ls` и валидатора
    tick_order: [reviewer, implementer] # обязателен при >1 роли: сначала разгрузить конвейер
    roles:
      implementer:
        reads_from: Ready
        working: InProgress             # рабочая колонка — опция роли
        outcomes:
          done:        { to: Review }
          needs_human: { to: Blocked, human: true }
          blocked:     { to: Ready, attempts: +1 }
          failed:      { to: Ready, attempts: +1 }
      reviewer:
        reads_from: Review
        outcomes:
          done:
            to: Approved                # по умолчанию
            by_next_owner:              # маршрут по полю next_owner из result.json
              implementer: Ready
              human: Approved
          needs_human: { to: Blocked, human: true }
          blocked:     { to: Review, attempts: +1 }
          failed:      { to: Review, attempts: +1 }
    limits:
      max_attempts: 3
      max_review_rounds: 3              # отчётов reviewer'а с next:implementer подряд
      max_push_failures: 3              # серия event:push-failed подряд → Blocked + человек
      lease_margin_sec: 300
    human_reply:
      fallback: Ready                   # маршрут — reads_from роли из последнего маркера офиса;
      reset_attempts: true              # fallback — если этой роли в графе больше нет


Правила:
- **Переход в текущий статус не делается.** Общее правило runner'а, не частный случай reap:
  цель перехода совпадает со статусом задачи → перехода нет (у reviewer'а `blocked`/`failed`
  ведут в `Review`, откуда он читает; в JIRA перехода `Review → Review` может не быть).
  `mock.Claim` не должен писать `Status = WorkingStatus`, если тот пуст.
- `tick_order` — явный, валидатор требует каждую роль ровно один раз; порядок YAML-карты
  не сохраняется, «по алфавиту» — совпадение, а не правило.
- `working` необязателен: отсутствует — `Claim` без перехода, задача остаётся в `reads_from`
  с живой арендой (reviewer); задан — статусный переход, как на этапе 2 (implementer).
  Тест графа и конвейера на оба варианта — на этом этапе оба живые.
- Колонка из `columns`, на которую не ссылается ни одна роль (`Backlog`), допустима:
  валидатор не должен на неё ругаться, `runner ls` — показывать.
- `by_next_owner` допустим только у `done`; значение `next_owner`, которого нет в карте, —
  маршрут по умолчанию `to`. `next_owner: none` у reviewer'а — тоже по умолчанию.
  Карта явная (маршрут задаёт граф, а не агент — DESIGN §2.1), но валидатор закрывает
  расхождение: ключ, совпадающий с именем роли графа, обязан вести в её `reads_from`;
  `human`/`none` — свободные значения.
- **Маркер получает необязательный ключ `next:<owner>`** у отчётов с `outcome:` — иначе
  «вернул на доработку» и «одобрил» в переписке неразличимы. Разбор остаётся строгим,
  ключ известный; маркеры этапа 2 без него разбираются как раньше.
- Круги считаются по маркерам в переписке, с конца: отчёты `role:reviewer outcome:done
  next:implementer` подряд, пока не встретится `next:human`/`next:none`, отчёт другого рода,
  **`event:human-reply` любой роли** или комментарий человека — человек вмешался, старые круги
  к новому разговору не относятся (та же логика, что `reset_attempts`). В отличие от
  `LeaseExpiries`, счётчику кругов нужны агентские учётки — передать их явно.
  Серий по маркерам теперь три (смерти, круги, пуши), и обрываются они **по-разному**:
  смерти — только записью той же роли (чужие роли и комментарии без маркера не обрывают,
  так записано в «Два счётчика»); круги — ещё и комментарием человека и `human-reply` любой
  роли. Один обобщённый `Streak(comments, role, matches, breaks)` допустим, но параметром
  должно быть «что обрывает», а не только `kind` — иначе обобщение тихо поменяет уже
  обоснованное поведение счётчика смертей. Тесты на все три с их правилами обрыва.
- Колонки ожидания человека для безролевого прохода — множество `to` у всех исходов
  с `human: true` (раннерские блокировки ведут туда же). Раньше колонка бралась из роли;
  теперь роли у прохода нет, и правило нужно явно.
- Следствие нового правила ответа: **любая реплика человека в задаче с поднятым флагом
  перезапускает её** — включая «давайте отложим». Записать в контракт прямо. Отложить задачу
  человек может, убрав её из колонки ожидания или сняв флаг руками.
- Известный предел для ролей без рабочей колонки: истёкшая аренда видна и `ListReady`,
  и `ListExpired`; под `loop` порядок (`reap` первым) спасает, под голым `tick` из cron
  серия смертей такой роли не сосчитается — записать в контракт, не чинить.
- Ответ человека возвращает задачу роли из **последнего маркера офиса** (шаг 0.0): спросил
  reviewer — в `Review`; заблокировал раннер после провалов implementer'а — в `Ready`
  со сбросом `attempts`; после `review-rounds-exhausted` — в **`Review`** (запись пишется
  с `role:reviewer`): решение человека первым видит тот, кто оценивает — «принять» он одобрит
  сразу, «делать иначе» вернёт implementer'у с `next:implementer`. Выбор явный, с тестом. Человек ничего не «передаёт» — он пишет комментарий, всё остальное
  делает runner. `fallback` — если роли из маркера в графе больше нет.
- Terminal-колонка: после перехода runner зовёт `workspace.Remove` (работа запушена).
  Если задачу вернут из `Approved` руками — `Ensure` заведёт worktree заново от ветки.

`tracker.yaml`: статусы `Backlog`, `Approved` добавляются к имеющимся; `scripts/jira-setup.sh`
заводит их; `jira-setup.md` — глобальные входы.

Тесты на разбор графа и маршрутизацию. Отчёт → стоп.

## Шаг 2. Роль reviewer

`roles/reviewer/`:
- `role.yaml`: `tools.allow` — только чтение и запуск: `Read`, `Grep`, `Glob`,
  `Bash(git diff*)`, `Bash(git log*)`, `Bash(git show*)` — без пробела перед `*`, как
  у implementer'а: пробел значим, и голый `git diff` под спейсовой формой не пройдёт;
  команды тестов — тот же общий список, что у implementer'а. **Ни `Edit`, ни `Write`**, ни `git commit/add`. Проверить, что
  `--tools` сужает состав, а не только автоодобрение (заметки этапа 1).
- `context.md` (runner, `input.go`) получает две строки для **обеих** ролей: ветка задачи
  (`agent/<KEY>`) и базовая ветка проекта (`origin/<default>`) — без базы `git diff` показывает
  не то, а reviewer'у неоткуда её взять.
- `role.md`: вход — worktree на ветке задачи и `context.md` с отчётом implementer'а
  и именами веток;
  задача — сверить сделанное с постановкой, прогнать тесты, оценить качество; **никаких
  правок**; выход — `done` с `next_owner: implementer` и конкретными замечаниями
  (что, где, почему; списком, каждый пункт проверяем) либо `done` с `next_owner: human`
  и коротким одобрением; `needs_human` — если постановка противоречива и решать
  не implementer'у; `blocked` — если нельзя проверить (тесты не запускаются по внешним
  причинам). Замечания — в `summary`/`details_md`, они уедут в тикет; implementer прочтёт
  их из хвоста переписки.
- `_base/base.md`: дополнить общим правилом передачи — «отчёт для следующей роли пишется
  так, чтобы её агент мог действовать без вопросов: что сделано / что не так / что
  делать дальше».
- Учётка: роль про трекер **не знает** (`roles/` не трогается сменой трекера — чек-лист
  этапа 2). Привязка «роль → учётка» живёт в `tracker.yaml`, см. шаг 3.
- Инструменты reviewer'а — тот же общий список запуска тестов, что у implementer'а
  (`uv`, `pytest`); `test_cmd` из `projects.yaml` не подключать: роль грузится до выбора
  задачи и статична. «Роль + проект → эффективная роль» — идея этапа 4.

Smoke как на этапе 1: «кто ты и что тебе можно» → в ответе нет `Write`; задача «в коде
есть баг, найди и **исправь**» → reviewer отказывается править и возвращает `done`
с `next_owner: implementer` и описанием бага, а не патчем. Второе — главный тест роли.

Отчёт → стоп.

## Шаг 3. Учётки на роль

`tracker.yaml`:

    accounts:
      default:  { user_env: JIRA_USER,          secret_env: JIRA_PASSWORD }
      roles:                                    # опционально, роль → учётка
        reviewer: { user_env: JIRA_REVIEWER_USER, secret_env: JIRA_REVIEWER_PASSWORD }
    also_agents: []                             # чужая автоматизация (боты), чья проза — не человек

- `default` обязателен, `roles` — опция. **Одна учётка на всех агентов — штатный режим**:
  runner различает роли по маркеру в первой строке комментария, а не по автору, поэтому
  общая учётка ничего не ломает. Отдельные учётки дают только читаемость истории тикета
  для людей и раздельные права в JIRA. Записать это в `tracker-protocol.md`, «Кто человек».
- Список агентских учёток **выводится** из `accounts` (имена из `user_env` при открытии)
  плюс `also_agents`; ручного полного списка нет — иначе однажды забудут дописать роль,
  и её комментарий станет «голосом человека». Объединение собирается **один раз при сборке
  офиса**, не `Whoami` на каждом тике.
- `mock` конфигурации не имеет: учётка роли — соглашение `office-<роль>`, системные
  операции — `office`.
- Трекер открывается **на роль**: `tick --role R` ходит под учёткой роли (или `default`);
  `reap` и разбор ответа человека — под `default`. `Whoami` каждой возвращает своё.
- «Кто человек» — не из выведенного списка агентов; проверить, что записи обеих ролей
  не считаются ответом человека ни для одной из них, а ответ второй учётки-человека —
  считается для обеих.
- Полигон: см. шаг 1 (статусы, учётка `office-reviewer` с правами).
- Нарезка истории по своей роли теперь работает всерьёз: reviewer видит отчёт implementer'а
  (после последнего маркера reviewer'а), implementer — замечания reviewer'а. Тест
  на конвейере: implementer→reviewer→implementer, у каждого в `context.md` ровно то,
  что ему нужно, и не больше.

Отчёт → стоп.

## Шаг 4. Runner: две роли, передача, уборка, `ls`

- Проход разбора ответов человека (шаг 0.0) — **всегда**, и при `tick --role R`, и без роли:
  он один на цикл, под `default`; cron с одной ролью не должен оставлять задачи в ожидании
  навсегда. `tick` без `--role`: проход, затем роли в порядке `tick_order`; `loop` — то же.
- `ErrWorktreeBusy` в новом порядке (`Ensure` до `Claim`) обнаруживается при переборе
  кандидатов → взять следующего, а не кончать тик.
- Передача = обычный переход по исходу; ничего специального, кроме `by_next_owner`
  и подсчёта кругов. При `max_review_rounds` — `Blocked` + человек + системная запись
  `event:review-rounds-exhausted` с числом кругов и ссылкой на последний отчёт reviewer'а.
- Terminal-колонка → `workspace.Remove`, если пуш **не провалился** (`pushErr == nil`, а не
  «пуш состоялся»: у reviewer'а коммитов нет никогда, и по `pushed` папка не убралась бы ни разу).
  Порядок строго `Release → Unlock → Remove`: `Remove` не зовётся внутри `work()`, где на `defer`
  висит `Unlock`.
- Неудачный пуш — **не** синтетический `failed` (он инкрементит `attempts`, а это провалы
  агента; и по `agent-io.md` синтетический исход живёт только в памяти). Вместо этого:
  запись `event:push-failed` **пишет прогон (`ByRun`) до `Release`** — при живой аренде
  системная запись невозможна, а снимать аренду раньше записи значит открыть окно для
  следующего `tick`; `notice()` принимает актора. Затем задача **возвращается в `reads_from`
  роли** (implementer: `InProgress → Ready`; reviewer: перехода нет по общему правилу),
  `attempts` не трогается, аренда снимается, `Remove` нет — задача достанется следующему
  прогону в том же worktree у **обеих** ролей, а не повисает в `InProgress` без владельца.
  Серия `push-failed` подряд ≥ `max_push_failures` → `Blocked` + человек с
  `event:push-failures-exhausted`. В контракте уточнить: «системные записи» — те, что делаются
  без живой аренды (`lease-expired`, `human-reply`, `lease-lost` — потому что аренды уже нет);
  записи раннера внутри прогона (`push-failed`) идут `ByRun`.
- `runner ls [--project P]`: новый метод трекера `List(project, statuses) → []TaskRef`,
  где `TaskRef` расширен владельцем, арендой, флагом, датой обновления — **без комментариев**
  (не `Task` с пустым `Comments`: это тихая полуправда). `ListReady` отбрасывает арендованные,
  а `ls` — как раз про «кто работает». Столбцы:
  ключ, колонка, владелец/аренда, попытки, флаг человека, возраст. Один запрос на проект.
  Столбца «круги» нет — он стоил бы запроса комментариев на задачу; при нужде — `--rounds`
  с честной ценой.
- Сквозной тест с поддельными агентами: полный сценарий DoD 1–4, включая исчерпание кругов.

Отчёт → стоп.

## Шаг 5. Бюджеты

Сначала — учёт, и он пока не существует: стоимость никто не читает, есть только
`--output-format stream-json`.
- Разбор итогового события — деталь Claude CLI, поэтому парсит **адаптер** и отдаёт наверх
  нейтральное `Usage{cost_usd, duration_ms, turns}` через `runagent.Outcome`; конвейер
  формата Claude Code не знает. Нет события/поля — `Usage` пустой, не ошибка.
  **`Usage` не кладётся в `runner.Result`**: разбор `result.json` строгий, а раннер в этот
  файл не пишет. Меняется интерфейс `pipeline.Agent` — возвращает `(Result, Usage)`.
- До лимитов **измерить**, что `total_cost_usd` показывает под подпиской (а не API-ключом)
  на трёх прогонах; записать в `notes/`. Если под подпиской он бесполезен — лимиты в usd
  дополняются лимитами в `turns`.
- Стоимость прогона — строкой в тело отчёта в тикете (не в маркер): человек видит цену
  задачи на доске, а `per_task` через несколько машин когда-нибудь можно посчитать
  из переписки.

Затем:
- реестр `${OFFICE_HOME}/ledger.jsonl`: строка на прогон — `run_id, task, role, project,
  started, cost_usd, duration_ms, turns, outcome, config_sha`. Пишется runner'ом после
  разбора результата; ручной `run-agent` тоже пишет (без task). **Реестр локален для
  машины**: `per_task` на двух машинах видит половину. Принято как ограничение, записать
  в контракт рядом с «сколько раннеров на проект».
- Учёт и ограничение — разные вещи. Реестр ведётся **всегда** и ничего не решает.
  Лимиты — необязательная политика поверх него, отдельный `budgets.yaml` («нет файла —
  только учёт» — естественное состояние; `workflow.yaml` остаётся обязательным и строгим).
  Каждый лимит — значение **и режим**:

      per_task:        { usd: 5,  on_exceed: stop }   # сумма по задаче за всё время
      per_role_daily:  { usd: 20, on_exceed: warn }   # по роли за календарные сутки
      per_run:         { usd: 1,  on_exceed: warn }   # только warn: прогон не прерываем,
                                                      # жёсткая граница — max_turns

  Нет файла или нет лимита — только учёт. Режим по умолчанию — `warn`: тот, кто ничего
  не настраивал, не должен обнаружить, что runner перестал брать задачи.
- Проверка `per_task` и `per_role_daily` — **до `Ensure`**, не просто «до захвата»: иначе
  на пропускаемую задачу всё равно сделаем `fetch` и заведём worktree; `per_run` — после прогона:
  - `warn`: строка в лог + системная запись `event:budget-exceeded` в тикет (для `per_task`,
    `per_run`) — не чаще одного раза на задачу и порог, чтобы не спамить; работа продолжается;
  - `stop` для `per_task`: задачу пропустить, `event:budget-exhausted`, `Blocked` + человек
    (системная операция); `stop` для `per_role_daily`: `tick` этой роли не берёт задач,
    в лог одна строка за день, `loop` продолжает остальные роли и `reap`.
  Ответ человека на `Blocked` по бюджету снимает флаг и возвращает задачу как обычно;
  чтобы она не упёрлась в тот же лимит сразу, человек либо поднимает лимит, либо
  переводит на `warn` — runner это не обходит сам.
- `runner ledger [--since 24h] [--role R]` — сводка: прогонов, сумма, средняя, по исходам.
- Тесты на реестр; на каждый лимит — оба режима с поддельным агентом; на «нет файла —
  только учёт». Записать baseline из `stage-2-smoke.md` в `budgets.yaml` как стартовые
  значения, все в режиме `warn`.
