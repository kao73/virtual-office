# Завести проект

Это делается на каждый проект. Машина к этому моменту подготовлена
([«Подготовка машины»](machine-setup.md)), а трекер отвечает требованиям из
[«Что офис требует от вашей JIRA»](../reference/jira-requirements.md) — или
проект ведётся на файловом трекере `mock` и трекера не нужно вовсе.

## Репозиторий проекта-клиента

Требований три: ветка по умолчанию, `.gitignore` и охват токена.

Годится любой репозиторий, но **пустого не хватает**: ветку задачи раннер
ответвляет от `origin/<default_branch>`, и в репозитории без единого коммита
такой ссылки нет — первый же захват упадёт. Для первого захода заводят локальный,
и вот так:

```sh
rm -rf /tmp/client.git /tmp/client        # чтобы заход можно было повторить
git init --bare -b master /tmp/client.git
git clone -q /tmp/client.git /tmp/client
cd /tmp/client
printf '__pycache__/\n.pytest_cache/\n' > .gitignore
git add .gitignore
git -c user.name=you -c user.email=you@local commit -q -m init
git push -q origin master
cd -
```

`git add` здесь не для красоты. Соблазнительное `commit -am … --allow-empty`
новый файл не проиндексирует — `-a` берёт только уже отслеживаемые, — а
`--allow-empty` проглотит отказ, и коммит уедет пустым. Заметить это трудно:
в рабочем клоне `.gitignore` лежит и работает, а в репозиторий не попал, значит
в рабочей папке агента его не будет.

- [ ] **Ветка по умолчанию** совпадает с `default_branch`, который вы назовёте
      в записи о проекте (ниже).

      Проверка: `git -C /tmp/client.git symbolic-ref --short HEAD` печатает ту же
      ветку. Расхождение раннер обнаружит первым же захватом — ответвлять будет
      не от чего.

- [ ] **`.gitignore` лежит в репозитории** и закрывает мусор прогонов и тестов:
      агент коммитит сам, и `__pycache__`, `.pytest_cache`, артефакты сборки
      поедут в ветку задачи.

      Проверка — три команды, и важнее всех первая:
      `git -C /tmp/client.git ls-tree master .gitignore` показывает файл
      **в самом репозитории**; `git -C /tmp/client ls-files --error-unmatch
      .gitignore` — что он отслеживается; `git -C /tmp/client check-ignore -v
      __pycache__/x` — что правило работает. Одной последней мало: она читает
      рабочее дерево и не знает ни про коммит, ни про пуш. Раннер клонирует
      репозиторий, а не ваш клон, — смотреть надо туда.

- [ ] **Токен из [«Подготовка машины»](machine-setup.md), раздел «Креды»,
      даёт право именно на этот репозиторий.** Сам токен заведён на машине
      и на каждый проект не перезаводится — проверить надо охват.

      Проверка: `curl -fsS -H "Authorization: Bearer $GITHUB_TOKEN"
      https://api.github.com/repos/<владелец>/<имя> | python3 -c "import
      json,sys; print(json.load(sys.stdin)['permissions'])"` печатает объект,
      где `push` — `True`. Одного успешного ответа мало: токен, которому дали
      только чтение, репозиторий покажет, а на первом же пуше откажет. Токен
      без охвата вовсе отвечает `404`, а не `403`, — приватный репозиторий
      для него не существует.

      Право открывать pull request этим не проверяется. У классического токена
      оно приходит вместе с `repo`, у мелкозернистого — отдельным разрешением
      `Pull requests: write`, и увидеть его в ответе нечем. Узнаете на первом
      же PR-проходе; проект без forge этого не касается вовсе.

Проект без forge — законный и обычный для первого захода случай: локальный
bare-репозиторий, ключ `forge` не задан, PR-проход вырождается и уводит задачу
в `Done` записью `pr-skipped`.

## Запись о проекте

Проекты — свойство инстанса: в репозитории офиса их нет и не будет. Каждый
описывается одной записью в `${OFFICE_HOME}/projects.local.yaml`, которую
делают копией образца:

```sh
cp "${OFFICE_HOME:-$HOME/.office}/projects.local.example.yaml" \
   "${OFFICE_HOME:-$HOME/.office}/projects.local.yaml"
```

Править в копии нужно ровно четыре значения: ключ проекта, `repo_url`,
`default_branch` и `tracker`. Остальные ключи в образце закомментированы, у
каждого своя строка-подсказка. Слои, перекрытия и переменные окружения —
[«Конфигурация»](../reference/configuration.md); подключение к JIRA —
раздел [«Подключение к трекеру»](#подключение-к-трекеру) ниже.

## Подключение к трекеру

Только для проекта на JIRA — файловый трекер `mock` этого шага не требует
вовсе. Копия образца, тем же приёмом, что и `projects.local.yaml`:

```sh
cp "${OFFICE_HOME:-$HOME/.office}/tracker.example.yaml" \
   "${OFFICE_HOME:-$HOME/.office}/tracker.yaml"
```

- [ ] Правлены ровно пять значений: `base_url` и четыре `customfield_NNNNN`.
      Остальное — как в образце `${OFFICE_HOME}/tracker.example.yaml`: у
      каждого ключа своя строка-подсказка, здесь их не повторяют. Чему сами
      пять значений обязаны отвечать на инстансе — [«Что офис требует от
      вашей JIRA»](../reference/jira-requirements.md), разделы «Инстанс»
      и «Четыре поля аренды».
- [ ] Учётки в файле — только имена переменных окружения (`accounts.default`,
      `accounts.roles.*`), не значения. Сами значения — кред на машине, а не
      про проект: [«Подготовка машины», «Креды»](machine-setup.md#креды).
      Что каждая учётка должна уметь на инстансе и сколько их нужно —
      [«Что офис требует от вашей JIRA», «Учётки»](../reference/jira-requirements.md#учётки).

## Проверка: четыре по возрастанию цены

Первые три не тратят ни токенов, ни денег и **ничего в трекере не меняют** —
не пропускайте их. Читать трекер первая и третья всё же будут: раннер сверяет
каждую учётку с `/myself` и смотрит очередь.

**Первая — откуда взята конфигурация.** Её печатают команды, которые собирают
офис целиком: `tick`, `loop`, `reap`, `ls`, а из хозяйственных — `worktree rm`,
которому нужен список проектов. Обходятся без неё `ledger`, `worktree ls`
и `mock`. Возьмите `ls`:

```sh
runner ls
```

```
конфигурация:
  офис: <версия> → …/.office/office/<версия>
  workflow.yaml          …/.office/office/<версия>/workflow.yaml (офис, есть)
  projects.local.yaml    …/.office/projects.local.yaml (машина, есть)
  tracker.yaml           …/.office/tracker.yaml (машина, есть)
  budgets.yaml           …/.office/office/<версия>/budgets.yaml (офис, есть)
  budgets.yaml           …/.office/budgets.yaml (машина, нет)
```

- [ ] Пути ведут туда, куда вы клали файлы. «Нет» у машинных бюджетов — законный
      ответ: они необязательны.
- [ ] Список **дошёл до конца**. Строка печатается сразу, как путь разрешён,
      поэтому оборвавшийся список сам показывает, на чём раннер встал: отказ идёт
      следующей строкой. Если ни один проект не назвал `jira`, строки `tracker.yaml`
      не будет вовсе — файл не открывается. С двумя трекерами доска каждого
      печатается под заголовком `== трекер <имя> ==`.

**Вторая — что получит агент.** Токенов не тратит, агента не запускает:

```sh
rm -rf /tmp/probe && mkdir -p /tmp/probe && git -C /tmp/probe init -q -b master
git -C /tmp/probe -c user.name=probe -c user.email=probe@local commit -q --allow-empty -m init
echo 'Создай hello.py и закоммить.' > /tmp/task.md
# без --backend возьмётся sbx; машина без него — добавьте --backend local
run-agent --role analyst     --workdir /tmp/probe --task /tmp/task.md --dry-run
run-agent --role implementer --workdir /tmp/probe --task /tmp/task.md --dry-run
run-agent --role reviewer    --workdir /tmp/probe --task /tmp/task.md --base master --dry-run
```

- [ ] Все три печатают роль, `config_sha`, рабочую папку, платформу и путь
      к ограждению, а следом — команду и список доменов сети роли.
- [ ] Вы понимаете, что означает `config_sha`. Это HEAD конфиг-репозитория,
      а суффикс `-dirty` — что его рабочее дерево не чисто: незакоммиченные
      правки или неотслеживаемые файлы. Чистый клон его не получает: в репозитории
      нечего править под себя. Появился — разбор в [«Эксплуатация», «Симптомы
      конфигурации»](operations.md#симптомы-конфигурации).

Ролей ровно три. `--base` нужен `reviewer`'у по делу, а не по отказу: свою ветку
рабочая папка называет сама, а базу назвать некому — без флага строка про базовую
ветку просто не поедет в контекст, и разбирать роль будет вслепую.

**Третья — цикл вхолостую.**

```sh
runner tick
```

- [ ] Печатает раскладку конфигурации и завершается с кодом 0, ничего больше
      не сказав: очередь пуста, брать нечего.

      Отказ здесь бывает двух родов, и они звучат по-разному. Отказ **конфигурации**
      называет файл и ключ — его писал загрузчик. Отказ вида «поиск задач не удался…
      Field 'cf[NNNNN]' does not exist» пришёл от JIRA: это перепутанный номер поля
      аренды из [«Что офис требует от вашей JIRA»](../reference/jira-requirements.md),
      раздел «Четыре поля аренды», и до этой проверки он не всплывает (почему —
      сказано там же).

**Четвёртая — учебная задача.** Заведите **новую** и переведите её в `Analysis` —
этим человек говорит «берите»; `Backlog` офис не читает вовсе. Пробную задачу из
[«Пробная задача»](../../bootstrap/jira/README.md#пробная-задача) переиспользовать
можно (она лежит в `Backlog`, и ход `Backlog → Analysis` есть), но не стоит: у неё
нет постановки, а есть комментарий «проверка прав» — аналитик получит пустую
задачу и справедливо спросит, что делать.

```sh
runner tick      # аналитик напишет план
runner tick      # разработчик сделает
runner tick      # ревьюер разберёт
runner tick      # системный проход откроет PR и уберёт папку
```

- [ ] После третьего тика задача в `Approved`, в тикете лежат отчёты трёх ролей,
      а в ветке — каталог `docs/changes/<KEY>/` с `brief.md`, `design.md`, `tasks.md`.
- [ ] Четвёртый тик развилка, и она зависит от того, есть ли у проекта forge.

      **С forge:** в тикете появляется комментарий со ссылкой на pull request,
      задача остаётся в `Approved`. Дальше — по настройке проекта: по умолчанию
      **сливает человек**, и после слияния следующий тик уводит задачу в `Done`
      и убирает рабочую папку. С `auto_merge.enabled`
      ([«Роли и путь задачи»](roles-and-flow.md), раздел «Возвраты и круги»)
      человека ждать не нужно: следующий тик сам сольёт PR, если гейт чист
      (ни конфликта, ни продвинувшейся базы), и тем же тиком уведёт задачу
      в `Done`.

      **Без forge** (локальный bare-репозиторий из раздела «Репозиторий
      проекта-клиента» выше): сливать негде, и тот же тик уводит задачу
      прямо в `Done` записью `pr-skipped`, а папку убирает сразу. Пятого
      тика не нужно.

Не больше одной задачи на роль за цикл — так проще и останавливать, и разбирать.
Что происходит прямо сейчас — `runner ls`; во что обошлось — `runner ledger`.
