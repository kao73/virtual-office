# Автоматизированная система разработки на AI-агентах — design brief

Документ фиксирует решения, принятые на этапе исследования (август 2026).
Он предназначен для чтения агентом (Claude Code) и человеком перед началом работы в репозитории.
Всё, что здесь помечено как «отложено», не реализуем в MVP, но держим в уме при проектировании.

## 1. Суть системы

- Задачи живут в таск-трекере (первая реализация — JIRA), организованы в колонки kanban-доски (статус = узел графа).
- Агенты (первый — Claude Code, но интерфейс агент-нейтральный) запускаются периодически с определённой **ролью**, выполняют одну задачу и завершаются.
- Роль определяет: из какой колонки читать, как захватить задачу, правила отбора, правила выполнения и ожидаемый результат, правила завершения и передачи дальше.
- Граф состояний: узлы — колонки, рёбра — допустимые исходы каждой роли.
- Весь диалог (агент↔агент, агент↔человек) — комментарии к тикету. Запрос человеку — атрибут задачи + комментарий; ответ человека — комментарий.
- Всё состояние выполнения задачи (контекст, спецификации, планы, подзадачи, тесты) — в git, в worktree на задачу.

## 2. Ключевые архитектурные решения

### 2.1 Runner (обёртка) vs агент — жёсткое разделение
- **Runner** (детерминированный код, не LLM): поллинг трекера, отбор задачи, захват (claim/lease), создание worktree, сборка входного контекста, запуск агента, разбор результата, смена статуса, публикация отчёта, reaper.
- **Агент** (LLM): получает уже захваченную задачу и готовый пакет контекста, делает работу в worktree, возвращает машиночитаемый результат.
- Агент **не** меняет статус тикета напрямую и **не** ищет работу сам. Граф переходов контролируется кодом runner'а, а не промптом.
- Причина: экономия токенов (пустой поллинг не должен стоить LLM-вызова), предсказуемость переходов, воспроизводимость.

### 2.2 Захват задачи (claim) и смерть агента
- Захват = запись кастомных полей `agent_owner`, `run_id`, `lease_until`; перевод статуса — **если у роли задана рабочая колонка**. Она необязательна: без неё «в работе» означает живую аренду в той же колонке, из которой роль читает (этап 3, роль reviewer). После записи — перечитать тикет и убедиться, что владелец — мы (в JIRA нет атомарного CAS).
- **Lease, а не lock**: аренда с истечением. Reaper по cron возвращает задачи с истёкшим lease в исходную колонку и пишет комментарий «зависла, возвращаю».
- Каждый запуск имеет `run_id`; все комментарии и мутации подписываются им (`[run:abc123 config:9f2e1c]`).
- На старте агент/раннер сверяет состояние worktree с состоянием тикета (идемпотентность).

### 2.3 Финальная диспозиция — обязательна
- Каждый запуск обязан закончиться явным исходом: `done | needs_human | blocked | failed` (+ данные исхода). Runner требует его от агента в машиночитаемом виде (JSON в конце вывода / отдельный файл в worktree).
- Раз отчёт обязателен, право записать его даёт обвязка, а не роль: адаптер добавляет к разрешениям роли ровно один путь — файл результата. Иначе роль без инструментов записи (reviewer, этап 3) не может закончиться ничем, кроме синтетического `failed`, — проверено прогоном.
- Если агент умер без исхода — reaper проставляет `failed`, снимает lease.
- «В работе» может оставаться только задача с живым lease.

### 2.4 Комментарии как протокол
- Для людей — проза; для машин — структурированная шапка (маркер роли/исхода в первой строке, при необходимости YAML-блок). Всё многословное — в git, в тикете — ссылки на путь + commit SHA.
- Каждый прогресс-комментарий: что сделано, что осталось, кто владеет следующим шагом.
- Runner собирает агенту компактный контекст: описание тикета + комментарии после последнего маркера данной роли + `STATE.md`/`PLAN.md` из worktree. Агент не перечитывает всю историю тикета.

### 2.5 Конфигурация как код (один репозиторий)
- В репо: роли (`roles/<role>/role.md`, разрешённые инструменты, список скиллов/плагинов), скиллы/плагины (формат Claude Code plugin/marketplace, SKILL.md — кросс-агентный стандарт), адаптеры под агентов, runner, bootstrap (Docker/sbx kit), документация.
- Роль — агент-нейтральная спецификация + адаптер (`adapters/claude`, позже `adapters/codex` и т.д.), который превращает её в флаги конкретного CLI.
- Роль **не устанавливается на машину**, а передаётся runner'ом в момент запуска (промпт роли, настройки, папка скиллов из репо). Машина не хранит «состояние роли»; любая машина может выполнить любую роль.
- Обновления: runner делает `git pull` конфиг-репо перед запуском (или берёт закреплённый тег). Прод — тег/ветка `stable`, канарейка — `main`. SHA конфига пишется в комментарий каждого запуска → трассировка и откат одной командой. При незакоммиченной правке SHA помечается суффиксом `-dirty`: он больше не описывает то, что ушло агенту, и опираться на него нельзя.
- Секреты (ключ Anthropic, токен JIRA, GitHub PAT) — **не в репо**: env / secret store / `sbx secret`.

### 2.6 Изоляция выполнения

Раздел переписан по итогам этапа 1: ниже то, что реализовано и проверено, а не замысел.

- Бэкенд по умолчанию — Docker Sandboxes (`sbx`): microVM, изоляция от `~/.claude` из коробки, deny-by-default сеть с allowlist.
- **Сеть роли — `network.allow` в `role.yaml`**, добавлено на этапе 3. Роль называет хосты, куда ей нужно ходить сверх того, что нужно самому агенту; раннер выдаёт их своей песочнице правилом на неё одну, между созданием и запуском. Пусто — ничего сверх.
- **Домены самого агента добавляет адаптер, а не роль.** Роль про устройство конкретного агента не знает ничего. Знание это оказалось обязательным: встроенный кит песочницы открывает Claude Code три домена, но не его API, и при закрытой сети агент не проходит авторизацию вовсе. Измерено, см. `docs/notes/sbx.md`.
- **Закрытое умолчание не в руках раннера**: запрещающее правило сильнее разрешающего, поэтому «закрыть всё и открыть названное» на уровне песочницы не собирается — закрыв всё, закроешь и API агента. Базовая политика глобальная и ставится на машине человеком. Раннер обещает ровно то, что делает: добавляет разрешения, а не создаёт изоляцию. Бэкенд `local` не делает и этого и говорит об этом при старте роли с непустым списком.
- **Раз закрыть нельзя — раннер проверяет.** Перед каждым прогоном он спрашивает у политики машины, пустят ли в хост, которого нет и не будет ни в одной роли (`example.com`, зарезервирован IANA под документацию). Ответ «пустят» означает, что базовая политика открыта настежь и список роли не ограничивает ничего, — тогда в лог уходит строка с тем, чем это чинится. Прогон не отменяется: гарантию даёт машина, раннер о ней только рассказывает. Неудача самой проверки говорится отдельно и за закрытую сеть не выдаётся — «не узнал» и «закрыто» не одно и то же. Добавлено на этапе 4, шаг 0.
- Второй бэкенд — `local`, запуск прямо на хосте, без изоляции. Он отлаживает контур и выбирается явно. Границей он не является и не может ею быть: агент бежит в файловой системе владельца машины. Что там сделано — подменённый `HOME`, отобранные у git ssh-личности, перечисление разрешённых подкоманд — ограждает от случайности, а не от намерения.
- `docker` **отложен** и не реализован: изоляцию закрывает sbx, а докер понадобится только на машине без KVM. Написанный на этапе 1 `Dockerfile` выброшен.
- Схема — **песочница на прогон**: `create` → `exec` → `rm`, свежая файловая система каждый раз. Накладные ~5–6 с при закэшированном образе. Долгоживущая песочница на роль остаётся запасным вариантом, если накладные вырастут.
- Авторизация — **готовый токен через окружение**, а не OAuth-логин внутри песочницы: подмена `CLAUDE_CONFIG_DIR` уносит подписочный вход, поэтому изолированный запуск обязан получать кред явно. Значение передаётся формой `--env ИМЯ` без значения, чтобы не светиться в `ps`.
- Ограничения sbx: KVM на bare metal (обычный VPS не подойдёт) или Apple Silicon; продукт молодой — пиннить версию. Версию агента в образе задаёт sbx, а не мы: закрепление — открытый вопрос.
- Runner имеет интерфейс `run_agent(role, workdir, prompt) -> result`; кроме модуля бэкенда от sbx не зависит ничего. Роль от бэкенда не зависит вовсе — все сценарии прошли и на `local`, и в песочнице без единой правки в `roles/`.
- Для фермы из многих параллельных агентов вероятнее API-ключ, чем подписка — проверить актуальные условия перед продом.

### 2.7 Учёт расхода и пределы

Раздел добавлен на этапе 3.

- **Учёт и ограничение — разные вещи.** Реестр прогонов `${OFFICE_HOME}/ledger.jsonl` ведётся всегда, строка на прогон, и ничего не решает. Пределы (`budgets.yaml`) — необязательная политика поверх него: нет файла — нет лимитов, и это нормальное состояние офиса, а не недонастроенное. Тем и отличается от `workflow.yaml`, без которого раннеру решать нечем.
- **Расход — наблюдение раннера, а не заявление агента.** В `result.json` его нет и не будет: файл результата пишет агент, и цену он называл бы себе сам. Читается расход из лога прогона; разбирает **адаптер** и отдаёт наверх нейтральное `Usage{cost_usd, duration_ms, turns}` — конвейер формата конкретного агента не знает. Нет итогового события — расход пустой, и это законно: прогон, убитый на середине, о цене не отчитывается. Выдуманный ноль был бы враньём.
- **Реестр локален для машины.** Два раннера на один проект видят каждый свою половину расхода; `per_task` на двух машинах посчитается неверно. Принято как ограничение: общий реестр означал бы общее хранилище, а единственное общее хранилище офиса — трекер. Цена каждого прогона всё же попадает в тикет строкой в отчёте, так что задачу можно посчитать и по переписке.
- **Три предела, три места проверки, и места выбраны по смыслу.** `per_role_daily` — в начале тика: он про роль, а не про задачу. `per_task` — до `Ensure`, иначе на пропускаемую задачу заводится клон проекта и worktree. `per_run` — после прогона, и только в режиме `warn`: цена известна, когда работа уже сделана и оплачена. Жёсткая граница прогона не в деньгах, а в шагах — `limits.max_turns` в роли.
- **Режим по умолчанию — `warn`.** Тот, кто вписал одно число, не должен обнаружить, что раннер молча перестал брать задачи. Режим `stop` для `per_task` отдаёт задачу человеку обычным путём; обойти предел сам раннер не может и не станет — человек либо поднимает его, либо переводит в `warn`.
- Под подпиской `total_cost_usd` — цена по прайсу API, а не выставленный счёт; настоящий ограничитель подписки — не деньги, а окно (пятичасовое, недельное).
- **Окно поставщика — наблюдение, как и расход.** Его состояние читается из того же лога и тем же адаптером, а наверх идёт нейтральным `Limit{State, Window, ResetsAt}`: `allowed`, `nearing`, `reached`. В лог прогона попадают только два последних — открытое окно есть у каждого прогона, и строка о нём ничего не сообщала бы. Решений по окну раннер пока не принимает: отвергнутый прогон по-прежнему считается провалом агента и тратит попытку. Что с этим делать, решается по первому живому отказу, а не по догадке о его формате, — см. `docs/notes/budgets.md`.

## 4. Отложено (перенято у Paperclip / Beads / Gas Town, внедрять по мере надобности)

- Типизированные запросы человеку вместо прозы: `confirmation`, `choice`, `questions`, `suggest_tasks`; идемпотентный ключ; поздний комментарий человека автоматически снимает ожидающий запрос.
- Блокеры как first-class связи (JIRA Issue Links «is blocked by»), а не текст; автопродолжение зависимой задачи; антиспам — не комментировать blocked-задачу повторно без нового контекста.
- Планы как документ с ревизией (у нас — файл в worktree + commit SHA в комментарии; «утверждено» относится к конкретной ревизии).
- Правило «не проси человека сделать то, что может сделать агент»: перед `needs_human` агент перечисляет, что уже попробовал; при возможности эскалирует другой роли.
- Эфемерное состояние (черновики, промежуточные попытки) — только в worktree, не в трекере.
- Каждая роль должна уметь прерваться в любой точке и оставить состояние, с которого следующий запуск продолжит («hand off»).

  **Сделано, этап 3.** Учёт и ограничение разведены: реестр прогонов
  (`${OFFICE_HOME}/ledger.jsonl`) ведётся всегда и ничего не решает, пределы —
  необязательная политика поверх него (`budgets.yaml`), у каждого предела режим
  `warn` или `stop`. Авто-паузы как отдельного состояния нет: задача с исчерпанным
  бюджетом уходит к человеку обычным путём, роль с исчерпанным дневным пределом

## 5. Существующие решения (для ориентира, чтобы не изобретать)

- Kanban + агент на карточку + worktree: Vibe Kanban (закрывается, community), OpenKanban, Cline Kanban, Kangentic, ai-agent-board, Kanbots. Все — свой трекер, интерактивные агенты.
- JIRA-тикет → PR: Claude Agent for Jira (Atlassian Marketplace, Managed Agents), Tembo, ticketagent.dev. Один тикет → один PR, без многоэтапного ролевого конвейера.
- Роли + heartbeat + комментарии + атомарный checkout: Paperclip (свой трекер, JIRA — в roadmap).
- Git как единственное состояние: Beads / Gas Town (work leases, `bd ready`, hooks, hand-off).
- Наша ниша: многоэтапный конвейер с ролями и явным графом, независимость от трекера и агента, состояние в git.

## 6. Первые шаги в репозитории

1. Аудит текущего содержимого репо: что относится к runner'у, что к ролям/скиллам, что к экспериментам. Ничего не удалять — сначала карта.
2. Предложить целевую структуру (`roles/`, `plugins/`, `adapters/`, `runner/`, `bootstrap/`, `docs/`) и план миграции существующего кода в неё.
3. Реализовать п.1–4 из плана MVP.
