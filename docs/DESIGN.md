# Автоматизированная система разработки на AI-агентах — design brief

Документ фиксирует решения, принятые на этапе исследования (август 2026).
Он предназначен для чтения агентом (Claude Code) и человеком перед началом работы в репозитории.
Всё, что здесь помечено как «отложено», не реализуем в MVP, но держим в уме при проектировании.

## 1. Суть системы

- Задачи живут в таск-трекере (первая реализация — JIRA); узел графа — **статус** задачи, то есть узел workflow трекера.
- **Статус — не колонка.** Колонка — свойство доски, представление: она группирует статусы, и досок с разной раскладкой одних и тех же статусов бывает сколько угодно. Раннер оперирует статусами и о досках не знает ничего — ни в конфиге, ни в коде. Раскладка доски живёт в трекере и описана в `docs/notes/jira-setup.md`.
- Агенты (первый — Claude Code, но интерфейс агент-нейтральный) запускаются периодически с определённой **ролью**, выполняют одну задачу и завершаются.
- Роль определяет: из какого статуса читать, как захватить задачу, правила отбора, правила выполнения и ожидаемый результат, правила завершения и передачи дальше.
- Граф состояний: узлы — статусы, рёбра — допустимые исходы каждой роли.
- Весь диалог (агент↔агент, агент↔человек) — комментарии к тикету. Запрос человеку — атрибут задачи + комментарий; ответ человека — комментарий.
- Всё состояние выполнения задачи (контекст, спецификации, планы, подзадачи, тесты) — в git, в worktree на задачу.

## 2. Ключевые архитектурные решения

### 2.1 Runner (обёртка) vs агент — жёсткое разделение
- **Runner** (детерминированный код, не LLM): поллинг трекера, отбор задачи, захват (claim/lease), создание worktree, сборка входного контекста, запуск агента, разбор результата, смена статуса, публикация отчёта, reaper.
- **Агент** (LLM): получает уже захваченную задачу и готовый пакет контекста, делает работу в worktree, возвращает машиночитаемый результат.
- Агент **не** меняет статус тикета напрямую и **не** ищет работу сам. Граф переходов контролируется кодом runner'а, а не промптом.
- Причина: экономия токенов (пустой поллинг не должен стоить LLM-вызова), предсказуемость переходов, воспроизводимость.

### 2.2 Захват задачи (claim) и смерть агента
- Захват = запись кастомных полей `agent_owner`, `run_id`, `lease_until`; перевод статуса — **если у роли задан рабочий статус**. Он необязателен: без него «в работе» означает живую аренду в том же статусе, из которого роль читает (роли `reviewer` и `analyst`). После записи — перечитать тикет и убедиться, что владелец — мы (в JIRA нет атомарного CAS).
- **Рабочий статус — дубль аренды, и берут его не везде.** Занятость выражена арендой; рабочий статус добавляет к ней две вещи: единственный CAS, какой даёт JIRA (переход, доступный ровно из одного статуса, — без него роль нельзя запустить в двух раннерах), и видимость «в работе» тому, кто смотрит в трекер. Роли, чей прогон длится минуты и которую незачем параллелить, он не даёт ни того, ни другого. К доске это отношения не имеет: колонок статус не стоит, доска группирует их сама.
- **Lease, а не lock**: аренда с истечением. Reaper по cron возвращает задачи с истёкшим lease в исходный статус и пишет комментарий «зависла, возвращаю».
- Каждый запуск имеет `run_id`; все комментарии и мутации подписываются им (`[run:abc123 config:9f2e1c]`).
- На старте агент/раннер сверяет состояние worktree с состоянием тикета (идемпотентность).

### 2.3 Финальная диспозиция — обязательна
- Каждый запуск обязан закончиться явным исходом: `done | needs_human | blocked | failed | split` (+ данные исхода). Runner требует его от агента в машиночитаемом виде (JSON в конце вывода / отдельный файл в worktree).
- Раз отчёт обязателен, право записать его даёт обвязка, а не роль: адаптер добавляет к разрешениям роли ровно один путь — файл результата. Иначе роль без инструментов записи (reviewer, этап 3) не может закончиться ничем, кроме синтетического `failed`, — проверено прогоном.
- Если агент умер, не оставив исхода, reaper снимает аренду и возвращает задачу туда, откуда роль её взяла. `attempts` он **не трогает**: смерть прогона — не провал агента, и человеку, которого позвали бы «попытки исчерпаны», сказали бы неправду о причине. Серию таких смертей считает свой счётчик — по маркерам `event:lease-expired` в самой переписке, с пределом `max_lease_expiries`.
- **Проверять причину, а не следствие.** «Агент не отчитался» и «файла результата нет» — разные утверждения, и совпадают они только пока рабочая папка одноразова. На этапе 4 совпадение кончилось: прогон, срезанный пределом шагов, прочитал `result.json`, оставленный прошлым прогоном **другой роли**, и увёл задачу вперёд с чужим «done» в тикете. Поэтому результат прошлого прогона убирается при подготовке входа — правило проверяется по причине. Случай пятый в своём роде (см. «Механизм оказался не тем, чем выглядел» в ретроспективах этапов 1–4), и общий у них один: правило, проверяемое по следствию, однажды проверит не то.
- «В работе» может оставаться только задача с живым lease.

### 2.4 Комментарии как протокол
- Для людей — проза; для машин — структурированная шапка (маркер роли/исхода в первой строке, при необходимости YAML-блок). Всё многословное — в git, в тикете — ссылки на путь + commit SHA.
- Каждый прогресс-комментарий: что сделано, что осталось, кто владеет следующим шагом.
- Runner собирает агенту компактный контекст: описание тикета + комментарии после последнего маркера данной роли + `STATE.md` из worktree + путь каталога изменения. Агент не перечитывает всю историю тикета.
- Замысел задачи — каталог изменения `docs/changes/<KEY>/{brief,design,tasks}.md` в ветке задачи, а не текст в отчёте: следующая роль видит ветку, а не чужую рабочую папку. Каталог создаёт и пишет роль, для которой это описано в её `role.md`; остальным правка плана закрыта тем же текстом, а не технической проверкой. Начиная с этого изменения `analyst` этот каталог не создаёт и не пишет: место для своего спека и плана он выбирает сам, по собственному `role.md`.

### 2.5 Конфигурация как код: репозиторий — фреймворк, инстанс — в `${OFFICE_HOME}`

Граница добавлена на этапе 5 и ужесточена изменением config-cleanup; формулируется одной фразой: **репозиторий — это фреймворк, инстанс настраивается в `${OFFICE_HOME}`.** Ни одного файла репозитория не правят, заводя новую машину или второй инстанс. Причина не в чистоте раскладки, а в том, что репозиторий носил правду одной машины: с неё всё выглядело исправно, а любой другой обязан был переписать закоммиченные файлы, чтобы запуститься, и получал дерево, грязное навсегда, вместе с меткой `config:…-dirty` на каждом прогоне. Метка задумана как ответ на вопрос «тот ли конфиг достался агенту», и всюду, кроме машины-хозяйки, отвечать переставала.

- В репо: роли (`roles/<role>/role.md`, `role.yaml`) и их общие правила — `roles/_base/base.md` (промпт) и `roles/_base/base.yaml` (сеть и инструменты, которые наследует каждая роль), скиллы/плагины (формат Claude Code plugin/marketplace, SKILL.md — кросс-агентный стандарт), адаптеры под агентов, runner, bootstrap (Docker/sbx kit), документация, граф переходов, дефолтные бюджеты, образец `tracker.example.yaml`. **Проектов в репозитории нет.**
- В `${OFFICE_HOME}`: `projects.local.yaml` — каждый проект целиком (где репозиторий, ветка по умолчанию, трекер, forge, auto_merge, добавки к правилам: ключ `defaults` для всей машины и запись для одного проекта), `tracker.yaml` целиком (адрес, учётки, `customfield_*`, карта статусов), перекрытие бюджетов.
- Раннер обслуживает все трекеры, названные проектами: по офису на трекер, обход по имени трекера; флага выбора трекера нет. `tracker.yaml` открывается только когда среди проектов есть `jira`.
- Слои разрешений: базовый (`roles/_base/base.yaml`) → машинный (`defaults` в `projects.local.yaml`) → проектный (запись проекта) → ролевой (`role.yaml`). Каждый слой только добавляет; убрать названное менее специфичным нельзя — и это касается `tools.deny`.
- **Границу держит код, а не память того, кто правит файл.** Загрузчик принимает под `defaults` только `network` и `tools` и называет лишний ключ по имени; `projects.yaml` из прежней раскладки, оставшийся под корнем конфигурации, — отказ при старте с указанием, куда переехало содержимое; один тест проходит по файлам офиса и ловит абсолютные пути и `customfield_*`, другой — что `roles/_base/base.yaml` поставляется и держит запрет на `git push`.
- Раннер печатает при старте, откуда взял каждый файл конфигурации: половина её лежит в репозитории, половина — в хозяйстве, и гадать, какой именно файл он открыл, человеку не должно приходиться.
- Роль — агент-нейтральная спецификация + адаптер (`internal/adapters/claude`, позже `internal/adapters/codex` и т.д.), который превращает её в флаги конкретного CLI.
- Роль **не устанавливается на машину**, а передаётся runner'ом в момент запуска (промпт роли, настройки, папка скиллов из репо). Машина не хранит «состояние роли»; любая машина может выполнить любую роль.
- Версия: у бинарника и офиса она одна. Релиз `vX.Y.Z` несёт офис — роли, скиллы, хуки, граф, дефолтные бюджеты, образцы, кит песочницы — внутри себя и распаковывает его в `${OFFICE_HOME}/office/<версия>/` при первом запуске; распакованная версия больше не переписывается, старые лежат рядом. Личность прогона — эта версия (у сборки из клона без обёртки — commit из build info, с `-dirty` при незакоммиченной правке) — пишется целиком в маркер каждого комментария, в реестр и в паспорт; сокращаются только commit-хеши. Обновление — снова `install.sh` и перезапуск цикла; сам раннер себя не обновляет и `${OFFICE_HOME}` не трогает: рабочие файлы и уже распакованные версии остаются, несовместимость — отказ с адресом, а не миграция. `OFFICE_CONFIG_ROOT` — переключатель разработчика: офис из клона, ограждение собирается `go build`, личность — commit клона; так работают обёртки `bin/*`.
- Секреты (ключ Anthropic, токен JIRA, GitHub PAT) — **не в репо**: env / secret store / `sbx secret`.

### 2.6 Изоляция выполнения

Раздел переписан по итогам этапа 1: ниже то, что реализовано и проверено, а не замысел.

- Бэкенд по умолчанию — Docker Sandboxes (`sbx`): microVM, изоляция от `~/.claude` из коробки, deny-by-default сеть с allowlist.
- **Сеть роли — `network.allow` в `role.yaml`**, добавлено на этапе 3. Роль называет хосты, куда ей нужно ходить сверх того, что нужно самому агенту; раннер выдаёт их своей песочнице правилом на неё одну, между созданием и запуском. Пусто — ничего сверх.
- **Слоистая модель разрешений сети и инструментов**, добавлена этапом
  sandbox-network-and-permissions. `network.allow`/`tools.allow`/
  `tools.deny` прогона — объединение (union) четырёх уровней: базовые
  правила ролей (`roles/_base/base.yaml`), машинные умолчания (ключ
  `defaults` в `projects.local.yaml`), проект (его запись там же) и роль
  (`role.yaml`, как и было). Ни один уровень не может убрать то, что назвал менее
  специфичный — это касается и `tools.deny`, единственной реальной
  границы: `permissions.allow` не ограничивает Bash технически (агент
  решает сам, что не описано ни в allow, ни в deny), измерено 2026-08-27.
  Резолюция уровня 1 — в `runner.LoadRole` (база кладётся в роль при
  загрузке), уровней 2–3 — внутри `tracker.LoadProjects`, уровня 4 —
  `tracker.MergeProjectRules`, вызывается конвейером после того, как
  `claim()` узнал проект задачи. Подробности
  типов, алгоритма слияния и проверенных формулировок —
  `docs/contracts/role-sandbox-permissions.md`.
- **Домены самого агента добавляет адаптер, а не роль.** Роль про устройство конкретного агента не знает ничего. Знание это оказалось обязательным: встроенный кит песочницы открывает Claude Code три домена, но не его API, и при закрытой сети агент не проходит авторизацию вовсе. Измерено, см. `docs/notes/sbx.md`.
- **Закрытое умолчание не в руках раннера**: запрещающее правило сильнее разрешающего, поэтому «закрыть всё и открыть названное» на уровне песочницы не собирается — закрыв всё, закроешь и API агента. Базовая политика глобальная и ставится на машине человеком. Раннер обещает ровно то, что делает: добавляет разрешения, а не создаёт изоляцию. Бэкенд `local` не делает и этого и говорит об этом при старте роли с непустым списком.
- **Раз закрыть нельзя — раннер проверяет.** Перед каждым прогоном он спрашивает у политики машины, пустят ли в хост, которого нет и не будет ни в одной роли (`example.com`, зарезервирован IANA под документацию). Ответ «пустят» означает, что базовая политика открыта настежь и список роли не ограничивает ничего, — тогда в лог уходит строка с тем, чем это чинится. Прогон не отменяется: гарантию даёт машина, раннер о ней только рассказывает. Неудача самой проверки говорится отдельно и за закрытую сеть не выдаётся — «не узнал» и «закрыто» не одно и то же. Добавлено на этапе 4, шаг 0.
- Второй бэкенд — `local`, запуск прямо на хосте, без изоляции. Он отлаживает контур и выбирается явно. Границей он не является и не может ею быть: агент бежит в файловой системе владельца машины. Что там сделано — подменённый `HOME`, отобранные у git ssh-личности, перечисление разрешённых подкоманд — ограждает от случайности, а не от намерения.
- `docker` **отложен** и не реализован: изоляцию закрывает sbx, а докер понадобится только на машине без KVM. Написанный на этапе 1 `Dockerfile` выброшен.
- Схема — **песочница на прогон**: `create` → `exec` → `rm`, свежая файловая система каждый раз. Накладные ~5–6 с при закэшированном образе. Долгоживущая песочница на роль остаётся запасным вариантом, если накладные вырастут.
- Авторизация — **готовый токен через окружение**, а не OAuth-логин внутри песочницы: подмена `CLAUDE_CONFIG_DIR` уносит подписочный вход, поэтому изолированный запуск обязан получать кред явно. Значение передаётся формой `--env ИМЯ` без значения, чтобы не светиться в `ps`.
- Ограничения sbx: KVM на bare metal (обычный VPS не подойдёт) или Apple Silicon; продукт молодой — пиннить версию. Версию агента в образе задаёт sbx, а не мы: закрепление — открытый вопрос.
- Runner имеет интерфейс `run_agent(role, workdir, prompt) -> result`; кроме модуля бэкенда от sbx не зависит ничего. Роль от бэкенда не зависит вовсе — все сценарии прошли и на `local`, и в песочнице без единой правки в `roles/`.
- Для фермы из многих параллельных агентов вероятнее API-ключ, чем подписка — проверить актуальные условия перед продом.

### 2.7 Учёт расхода и пределы

Раздел добавлен на этапе 3.

- **Учёт и ограничение — разные вещи.** Реестр прогонов `${OFFICE_HOME}/ledger.jsonl` ведётся всегда, строка на прогон, и ничего не решает. Пределы (`budgets.yaml`) — необязательная политика поверх него: дефолты офиса в репозитории, накладка машины в `${OFFICE_HOME}`, и оба файла необязательны — нет ни одного, нет и лимитов, и это нормальное состояние офиса, а не недонастроенное. Тем и отличается от `workflow.yaml`, без которого раннеру решать нечем.
- **Расход — наблюдение раннера, а не заявление агента.** В `result.json` его нет и не будет: файл результата пишет агент, и цену он называл бы себе сам. Читается расход из лога прогона; разбирает **адаптер** и отдаёт наверх нейтральное `Usage{cost_usd, duration_ms, turns}` — конвейер формата конкретного агента не знает. Нет итогового события — расход пустой, и это законно: прогон, убитый на середине, о цене не отчитывается. Выдуманный ноль был бы враньём.
- **Реестр локален для машины.** Два раннера на один проект видят каждый свою половину расхода; `per_task` на двух машинах посчитается неверно. Принято как ограничение: общий реестр означал бы общее хранилище, а единственное общее хранилище офиса — трекер. Цена каждого прогона всё же попадает в тикет строкой в отчёте, так что задачу можно посчитать и по переписке.
- **Три предела, три места проверки, и места выбраны по смыслу.** `per_role_daily` — в начале тика: он про роль, а не про задачу. `per_task` — до `Ensure`, иначе на пропускаемую задачу заводится клон проекта и worktree. `per_run` — после прогона, и только в режиме `warn`: цена известна, когда работа уже сделана и оплачена. Жёсткая граница прогона не в деньгах, а в шагах — `limits.max_turns` в роли.
- **Режим по умолчанию — `warn`.** Тот, кто вписал одно число, не должен обнаружить, что раннер молча перестал брать задачи. Режим `stop` для `per_task` отдаёт задачу человеку обычным путём; обойти предел сам раннер не может и не станет — человек либо поднимает его, либо переводит в `warn`.
- Под подпиской `total_cost_usd` — цена по прайсу API, а не выставленный счёт; настоящий ограничитель подписки — не деньги, а окно (пятичасовое, недельное).
- **Окно поставщика — наблюдение, как и расход.** Его состояние читается из того же лога и тем же адаптером, а наверх идёт нейтральным `Limit{State, Provider, Window, ResetsAt}`: `allowed`, `nearing`, `reached`. `Provider` хранит слово самого поставщика — перечисление принадлежит ему, и незнакомое состояние раннер обязан показать человеку, а не проглотить. В лог прогона попадают только два последних — открытое окно есть у каждого прогона, и строка о нём ничего не сообщала бы. Прогон, **отвергнутый до первого шага**, провалом агента больше не считается: работы не было, и раннер видит это по следу, а не по событию — `Termination` вида `not_started`, запись `event:agent-unavailable`, попытка не тратится (этап 5, шаг 0). Отказ, случившийся **после** работы, след оставляет и уходит в `errored`: там попытка тратится по делу — деньги потрачены, а начинать всё равно с нуля. Отложенным осталось одно решение — пауза роли до сброса окна: между тиками у раннера нет состояния, под cron'ом пауза тика не переживёт, и заводить её без живого отказа не по чему. См. `docs/notes/budgets.md`.

### 2.8 Pull request: офис открывает, сливает человек или сам офис — по конфигу

Раздел добавлен на этапе 5.

- **Разбор — не конец задачи.** `Approved` означает «работа принята, pull request открыт»; терминальный статус один — `Done`, и попадает в него задача по факту слияния.
- **Forge — интерфейс рядом с трекером**, а не часть его: `OpenPR(project, branch, base, title, body) → url`, `PRState(url) → open | merged | closed` и `Merge(url) → error`. Первая реализация — GitHub через REST, токен из окружения. Проект, у которого forge не задан, живёт по тому же графу: проход вырождается, пишется `event:pr-skipped`, задача уходит в терминальный статус.
- **Конфликт слияния считается локально** — `git merge-tree --write-tree` по bare-клону, который раннер и так фетчит. Ни сети, ни forge для этого не нужно, и `Mergeable` в интерфейсе нет намеренно: чем меньше обещано, тем дешевле вторая реализация.
- **Маршрут прохода — в графе, а не в коде**: блок `pr` в `workflow.yaml` называет роль, статус входа и три исхода — слито, конфликт, закрыто. Это продолжение §2.1 на шаг дальше: там переходами распоряжается код, а не промпт; здесь — конфигурация, а не код. Общее у обоих правил одно — маршрут задаёт человек, и увидеть его можно, не читая исходников. Имени роли в коде раннера нет; агента у прохода нет вовсе — работу делает раннер.
- **Состояние pull request выводится из переписки**, как всё остальное состояние офиса: по последней записи семейства {`pr-opened`, `pr-closed`} этой роли. Не по факту в истории — иначе PR, закрытый руками, никогда не открылся бы заново.
- **Слияние — по умолчанию человек, на явном opt-in — офис.** Проект, не заведший `auto_merge.enabled` в `projects.local.yaml`, живёт по-старому: PR читает и сливает человек. Проект, заведший его, доверяет слияние офису — тем же PR-проходом, без новой роли, как только гейт (следующий пункт) пройден; вето-окна нет. Целевая ветка слияния — `auto_merge.target_branch`, если задана, иначе ветка по умолчанию; она же теперь база, от которой форкаются задачи проекта (`Project.PRBranch()`), — иначе гейт зависимостей (`depends_on`) молча переставал бы что-то значить для проекта с изолированной интеграционной веткой.
- **Конфликт — работа, а не провал, и триггер шире одного текстового конфликта.** Задача возвращается разработчику, попытка не тратится, и тот же pull request ждёт её возвращения; второй не открывается. Тот же возврат — на любом проекте, не только auto-merge — срабатывает и когда база просто продвинулась вперёд с момента, когда ветка задачи была срублена, даже без единого конфликтного маркера: контекст, в котором работали implementer и reviewer, мог устареть по смыслу.
- **Рабочую папку убирает системный проход, а не прогон.** Папка живёт до слияния — в неё может понадобиться вернуться конфликтом. Проход обходит папки, а не задачи, и грязную не сносит.

## 5. Существующие решения (для ориентира, чтобы не изобретать)

- Kanban + агент на карточку + worktree: Vibe Kanban (закрывается, community), OpenKanban, Cline Kanban, Kangentic, ai-agent-board, Kanbots. Все — свой трекер, интерактивные агенты.
- JIRA-тикет → PR: Claude Agent for Jira (Atlassian Marketplace, Managed Agents), Tembo, ticketagent.dev. Один тикет → один PR, без многоэтапного ролевого конвейера.
- Роли + heartbeat + комментарии + атомарный checkout: Paperclip (свой трекер, JIRA — в roadmap).
- Git как единственное состояние: Beads / Gas Town (work leases, `bd ready`, hooks, hand-off).
- Наша ниша: многоэтапный конвейер с ролями и явным графом, независимость от трекера и агента, состояние в git.
