# Автоматизированная система разработки на AI-агентах — design brief

Документ фиксирует решения, принятые на этапе исследования (август 2026).
Он предназначен для чтения агентом (Claude Code) и человеком перед началом работы в репозитории.
Всё, что здесь помечено как «отложено», не реализуем в MVP, но держим в уме при проектировании.

## 1. Суть системы

- Задачи живут в таск-трекере (первая реализация — JIRA), организованы в колонки kanban-доски (статус = узел графа).
- Агенты (первый — Claude Code, но интерфейс агент-нейтральный) запускаются периодически с определённой **ролью**, выполняют одну задачу и завершаются.
- Роль определяет: из какой колонки читать, как захватить задачу, правила отбора, правила выполнения и ожидаемый результат, правила завершения и передачи дальше.
- Граф состояний: узлы — колонки, рёбра — допустимые исходы каждой роли.
- Весь диалог (агент↔агент, агент↔человек) — комментарии к тикету. Запрос человеку — атрибут задачи + комментарий; ответ человека — комментарий.
- Всё состояние выполнения задачи (контекст, спецификации, планы, подзадачи, тесты) — в git, в worktree на задачу.

## 2. Ключевые архитектурные решения

### 2.1 Runner (обёртка) vs агент — жёсткое разделение
- **Runner** (детерминированный код, не LLM): поллинг трекера, отбор задачи, захват (claim/lease), создание worktree, сборка входного контекста, запуск агента, разбор результата, смена статуса, публикация отчёта, reaper.
- **Агент** (LLM): получает уже захваченную задачу и готовый пакет контекста, делает работу в worktree, возвращает машиночитаемый результат.
- Агент **не** меняет статус тикета напрямую и **не** ищет работу сам. Граф переходов контролируется кодом runner'а, а не промптом.
- Причина: экономия токенов (пустой поллинг не должен стоить LLM-вызова), предсказуемость переходов, воспроизводимость.

### 2.2 Захват задачи (claim) и смерть агента
- Захват = запись кастомных полей `agent_owner`, `run_id`, `lease_until` + перевод статуса. После записи — перечитать тикет и убедиться, что владелец — мы (в JIRA нет атомарного CAS).
- **Lease, а не lock**: аренда с истечением. Reaper по cron возвращает задачи с истёкшим lease в исходную колонку и пишет комментарий «зависла, возвращаю».
- Каждый запуск имеет `run_id`; все комментарии и мутации подписываются им (`[run:abc123 config:9f2e1c]`).
- На старте агент/раннер сверяет состояние worktree с состоянием тикета (идемпотентность).

### 2.3 Финальная диспозиция — обязательна
- Каждый запуск обязан закончиться явным исходом: `done | needs_human | blocked | failed` (+ данные исхода). Runner требует его от агента в машиночитаемом виде (JSON в конце вывода / отдельный файл в worktree).
- Если агент умер без исхода — reaper проставляет `failed`, снимает lease.
- «В работе» может оставаться только задача с живым lease.

### 2.4 Комментарии как протокол
- Для людей — проза; для машин — структурированная шапка (маркер роли/исхода в первой строке, при необходимости YAML-блок). Всё многословное — в git, в тикете — ссылки на путь + commit SHA.
- Каждый прогресс-комментарий: что сделано, что осталось, кто владеет следующим шагом.
- Runner собирает агенту компактный контекст: описание тикета + комментарии после последнего маркера данной роли + `STATE.md`/`PLAN.md` из worktree. Агент не перечитывает всю историю тикета.

### 2.5 Конфигурация как код (один репозиторий)
- В репо: роли (`roles/<role>/role.md`, разрешённые инструменты, список скиллов/плагинов), скиллы/плагины (формат Claude Code plugin/marketplace, SKILL.md — кросс-агентный стандарт), адаптеры под агентов, runner, bootstrap (Docker/sbx kit), документация.
- Роль — агент-нейтральная спецификация + адаптер (`adapters/claude`, позже `adapters/codex` и т.д.), который превращает её в флаги конкретного CLI.
- Роль **не устанавливается на машину**, а передаётся runner'ом в момент запуска (промпт роли, настройки, папка скиллов из репо). Машина не хранит «состояние роли»; любая машина может выполнить любую роль.
- Обновления: runner делает `git pull` конфиг-репо перед запуском (или берёт закреплённый тег). Прод — тег/ветка `stable`, канарейка — `main`. SHA конфига пишется в комментарий каждого запуска → трассировка и откат одной командой.
- Секреты (ключ Anthropic, токен JIRA, GitHub PAT) — **не в репо**: env / secret store / `sbx secret`.

### 2.6 Изоляция выполнения
- Предпочтительный бэкенд — Docker Sandboxes (`sbx`): microVM, deny-by-default сеть с allowlist, подстановка секретов через прокси, worktree на задачу, headless `-- -p`, kits для описания окружения роли.
- Ограничения sbx: KVM на bare metal (обычный VPS не подойдёт) или Apple Silicon; OAuth-логин подписки делается внутри sandbox и живёт только пока жив sandbox → схема «один долгоживущий именованный sandbox на роль, на каждую задачу `sbx exec` в новый worktree»; продукт молодой — пиннить версию.
- Runner имеет интерфейс `run_agent(role, workdir, prompt) -> result` с двумя бэкендами: `sbx` (по умолчанию) и `docker` (fallback). Ничего кроме этого модуля от sbx не зависит.
- Для фермы из многих параллельных агентов вероятнее API-ключ, чем подписка — проверить актуальные условия перед продом.

## 3. План MVP (в этом порядке, не перепрыгивать)

1. Один репо-цель, одна доска JIRA: `Ready → In progress → Review → Done` + `Blocked (needs human)`.
2. Одна роль — **Implementer**. Runner: JQL по `Ready` → claim (lease) → `git worktree add feat/PROJ-123` → сборка контекста → запуск `claude -p` с промптом роли → push ветки → разбор исхода → структурированный комментарий → перевод в `Review`.
3. Роль — файл `roles/implementer/role.md`; граф переходов — `workflow.yaml`.
4. Cron/systemd-timer раз в N минут + reaper для истёкших lease.
5. Только после того, как п.2–4 стабильно крутятся: вторая роль (Reviewer или Planner), переходы между ними, атрибут `needs_human`, шаблон вопроса человеку.
6. Абстракции «любой трекер»/«любой агент» — интерфейсы `Tracker` и `AgentRunner` с одной реализацией; вторую добавляем только когда она реально нужна.
7. Бэкенд изоляции: сначала `docker` (проще отладить), затем `sbx` там, где есть KVM.

## 4. Отложено (перенято у Paperclip / Beads / Gas Town, внедрять по мере надобности)

- Типизированные запросы человеку вместо прозы: `confirmation`, `choice`, `questions`, `suggest_tasks`; идемпотентный ключ; поздний комментарий человека автоматически снимает ожидающий запрос.
- Блокеры как first-class связи (JIRA Issue Links «is blocked by»), а не текст; автопродолжение зависимой задачи; антиспам — не комментировать blocked-задачу повторно без нового контекста.
- Планы как документ с ревизией (у нас — файл в worktree + commit SHA в комментарии; «утверждено» относится к конкретной ревизии).
- Правило «не проси человека сделать то, что может сделать агент»: перед `needs_human` агент перечисляет, что уже попробовал; при возможности эскалирует другой роли.
- Эфемерное состояние (черновики, промежуточные попытки) — только в worktree, не в трекере.
- Каждая роль должна уметь прерваться в любой точке и оставить состояние, с которого следующий запуск продолжит («hand off»).
- Бюджеты и лимиты по стоимости на роль/задачу; авто-пауза при превышении.
- Evals для ролей перед промоутом конфига из `main` в `stable`.

## 5. Существующие решения (для ориентира, чтобы не изобретать)

- Kanban + агент на карточку + worktree: Vibe Kanban (закрывается, community), OpenKanban, Cline Kanban, Kangentic, ai-agent-board, Kanbots. Все — свой трекер, интерактивные агенты.
- JIRA-тикет → PR: Claude Agent for Jira (Atlassian Marketplace, Managed Agents), Tembo, ticketagent.dev. Один тикет → один PR, без многоэтапного ролевого конвейера.
- Роли + heartbeat + комментарии + атомарный checkout: Paperclip (свой трекер, JIRA — в roadmap).
- Git как единственное состояние: Beads / Gas Town (work leases, `bd ready`, hooks, hand-off).
- Наша ниша: многоэтапный конвейер с ролями и явным графом, независимость от трекера и агента, состояние в git.

## 6. Первые шаги в репозитории

1. Аудит текущего содержимого репо: что относится к runner'у, что к ролям/скиллам, что к экспериментам. Ничего не удалять — сначала карта.
2. Предложить целевую структуру (`roles/`, `plugins/`, `adapters/`, `runner/`, `bootstrap/`, `docs/`) и план миграции существующего кода в неё.
3. Реализовать п.1–4 из плана MVP.
