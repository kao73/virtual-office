# Jira — карта провайдера

Провайдер v1 (Р-30). Источник: смоук первой попытки против песочницы **CRM3**
в инстансе клиента №1. Общие уроки шва — в [`README.md`](README.md).

## Инстанс и транспорт

| | |
|---|---|
| Тип | **Jira Server / Data Center**, не Cloud |
| API | **REST v2** — `{base_url}/rest/api/2`. Не v3 |
| Аутентификация | **basic (логин + токен)**. Bearer на этом инстансе **не работает** — проверено |
| Переменные окружения | `JIRA_LOGIN`, `JIRA_API_TOKEN` |
| Доступность | только из локальной сети/VPN владельца (Р-06) — снаружи инстанс недоступен |

Следствие последней строки: вендорские агентные платформы (Agents in Jira, Rovo)
и вебхуки к этому инстансу неприменимы в принципе. Опрос — только поллингом изнутри.

## Чтение

Все нужные поля берутся **одним запросом**, комментарии приходят внутри issue:

```
GET issue/{key}?fields=summary,description,status,labels,comment,attachment,issuelinks
```

Отдельный запрос за комментариями не нужен.

## Состояния: статус плюс необязательная метка

Абстрактное состояние отображается на статус Jira и, опционально, на метку — метка
нужна, когда несколько абстрактных состояний живут в одном статусе воркфлоу.

**Правило дизамбигуации:** кандидатом считается состояние, у которого совпал статус
и (если метка объявлена) метка присутствует. Если кандидатов больше одного —
состояние **не определено**, а не «первый попавшийся». Молчаливый выбор первого
даёт роли ложную уверенность.

## Переходы

```
GET  issue/{key}/transitions        → найти транзишн с to.name == целевой статус
POST issue/{key}/transitions        → {"transition": {"id": ...}}
```

Прямого транзишна может не быть — тогда ошибка со списком реально доступных переходов,
это гораздо полезнее «HTTP 400».

**Главная грабля, найденная в бою (CRM3).** Некоторые транзишны несут обязательные поля
через **post-function валидатор**, и эти поля **не объявлены как required в `editmeta`
транзишна**. Пример: переход в `Cancelled` требует `resolution` и текстовое поле причины.
Без них Jira отвечает HTTP 400, и по метаданным догадаться об этом нельзя.

Профиль клиента такими полями не управляет — это деталь конкретного воркфлоу трекера,
а не конфигурация офиса. Вызывающий код должен иметь возможность передать их явно.

## Метки — точечно, не перезаписью

```
PUT issue/{key}  →  {"update": {"labels": [{"add": "..."}, {"remove": "..."}]}}
```

Перезапись всего списка меток затирает чужие. При смене состояния снимаются только
метки состояний, объявленные в конфиге, — остальные не трогаются.

## Создание карточки

Карточка **рождается в начальном статусе воркфлоу**, а не в том, который запросили.
Целевое состояние приходится доводить транзишном после создания — то есть создание
это всегда две операции, и вторая может упасть.

```
POST issue  →  {"fields": {project, summary, description, issuetype, labels}}
```

Метка участка ставится при создании, вместе с меткой состояния.

## Выборка по стадии

```
project = {PROJECT} AND labels = "{fence}" AND status = "{status}"
  [AND labels = "{state_label}"]
ORDER BY created ASC
```

Сортировка по дате создания даёт приоритет порядком на доске (`docs/decisions.md`, §5).

## Вложения

```
POST issue/{key}/attachments
     multipart, заголовок X-Atlassian-Token: no-check  ← обязателен
```

Нестандартный транспорт: не проходит через общий JSON-клиент.

## Связи

```
POST issueLink  →  {"type": {"name": "Relates"}, "inwardIssue": ..., "outwardIssue": ...}
```
