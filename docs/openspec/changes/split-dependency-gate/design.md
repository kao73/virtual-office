## Context

См. `proposal.md` за мотивацией и `docs/notes/analyst-task-splitting.md`
(раздел «Волна 2 — брейншторм 2026-09-05», подраздел «Change 2») за
историей решения о форме гейта, а также
`docs/superpowers/specs/2026-09-07-split-dependency-gate-design.md` за
глубокой технической проработкой (конкретные сигнатуры, порядок вызовов,
живая верификация направления `issuelinks`) — этот документ переносит уже
принятые там решения в формат Comet Design, не передумывает их заново.

Сегодня: `internal/tracker.Task.DependsOn` пишется `LinkDependsOn`
(Change 1), но читается обратно только на `mock` — `jira.toTask` не
разбирает `issuelinks`, и даже если бы разбирал, `search()`
(`ListReady`/`List`) не запрашивает это поле вовсе. `claim()`
(`internal/pipeline/pipeline.go`) не знает о зависимостях между задачами —
единственный существующий фильтр кандидатов там сегодня — исчерпанные
попытки.

## Goals / Non-Goals

**Goals:**
- `claim()` не берёт кандидата, чей `depends_on` называет задачу не в
  терминальном статусе — одинаково для всех ролей графа.
- `Task.DependsOn` читается корректно на обеих реализациях `Tracker`
  (`mock`, `jira`), не только на файловой.
- `runner ls` показывает, чего ждёт заблокированный кандидат, без
  дополнительной команды.
- `roles/analyst/role.md` даёт критерий, когда `depends_on` уместен между
  детьми `split`.

**Non-Goals:**
- Защита от рекурсивного `split` (ребёнок, от которого что-то зависит, сам
  разбивается дальше) — известный остаточный риск, не эта задача.
- Кэширование запросов к трекеру — на объёме проекта не нужно, тот же
  принцип, что уже принят для Change 1.
- Метка `depends-on:<KEY>` как источник чтения — рассмотрена и отклонена
  (см. решение №1): один факт «X зависит от Y» живёт только в `issuelinks`.
- Изменение того, как и когда `LinkDependsOn` пишет связь (Change 1) —
  меняется только чтение.

## Decisions

**1. Источник чтения — `issuelinks`, не отдельная метка.** Первая версия
этого дизайна предлагала `depends-on:<KEY>` рядом с `issuelink` — по
образцу уже существующих `split-child:<parent>:<id>`/`office-waits-human`,
которые в этом коде тоже управляют реальным ветвлением. Отклонено: один
факт записывался бы дважды, с риском разойтись при частичном сбое
(`POST /issueLink` упал, метка уже написалась, или наоборот). Чинится
единственный источник правды — разбор `issuelinks` в `jira.toTask` — а не
заводится второй.

**2. Направление читается тем же приёмом, каким уже один раз проверялось
направление записи.** «Сверено по `issuelinks`» уже подводило (см.
«Урок» в `docs/notes/analyst-task-splitting.md`, 2026-09-06): форма
запроса — не то же самое, что его смысл на живом сервере. План
верификации для чтения — тот же эталонный тип `Blocks`, что уже
использовался для записи, отдельным пунктом плана до того, как на разбор
станет полагаться гейт.

**3. Статусы зависимостей — один `List(project, statuses)` на проект, не
`Get()` на каждую зависимость каждого кандидата.** `Get()` тянет всю
переписку — лишний вес на каждый тик. `List` — то же самое, что уже делает
`runner ls`; общий помощник (`internal/pipeline`, не `tracker`) строит
`map[string]TaskRef` один раз и обслуживает и гейт, и вывод `ls`. Вызывается
лениво — только когда `ListReady` вообще вернула кандидатов.

**4. Гейт — один код для всех ролей, без исключения `reviewer`.**
Специальный `if role == "reviewer" { skip }` не нужен: тикет попадает в
`Review` только после того, как его `implementer` уже прошёл этот же
гейт, — зависимость к этому моменту разрешена по построению, и общая
проверка для `reviewer` всегда молча проходит. Проще не писать
исключение, чем поддерживать код, который никогда не понадобится.

**5. «Терминальный» — существующее понятие графа
(`Workflow.IsTerminal`), не новая строка `"Done"`.** У раннера уже есть
эта абстракция (`workflow.yaml`, `terminal: [Done]`) — гейт спрашивает её,
а не хардкодит имя статуса, и не ломается, если граф проекта когда-нибудь
определит терминальные статусы иначе.

**6. Отсутствующая в трекере зависимость — не разрешена.** Если задача,
на которую ссылается `depends_on`, не находится в текущем срезе проекта
(удалена, переехала), гейт трактует её как невыполненную, а не как
свободную — падать громко, не молчать. Согласуется с общим принципом
`docs/DESIGN.md` о видимых, а не тихих отказах.

**7. Критерий `depends_on` — правка `role.md`, не `docs/contracts/`.**
Контракт (`docs/contracts/agent-io.md`) уже описывает формат поля и его
валидацию; вопрос «когда связь уместна по смыслу» — эвристика роли
`analyst`, ей место рядом с остальными решениями этой роли в `role.md`.

## Risks / Trade-offs

- **[Risk]** Направление `issuelinks` при чтении может не совпасть с
  ожиданием кода (уже случалось однажды при записи). → Живая верификация
  на полигоне эталонным типом `Blocks` — отдельная задача плана, до того
  как гейт начинает полагаться на разбор.
- **[Risk]** `search()`/`searchFields()` — если забыть добавить туда
  `issuelinks`, гейт на JIRA молчит даже после верного `toTask`
  (кандидаты из `ListReady` получают пустой `DependsOn`). → Отдельная
  задача плана и тест на `search()`, не только на `toTask` в изоляции.
- **[Trade-off]** Рекурсивный `split`: `closeSplitParent` терминирует
  ребёнка сразу после создания его собственных детей, не когда они
  реально готовы — гейт на зависимого от него родителя увидит
  зависимость выполненной раньше времени. Принято как известный
  остаточный риск (редкий случай — разбиение уже зависимого ребёнка), не
  проектируется здесь.
- **[Trade-off]** Один лишний REST-запрос (`List`) на проект за тик, когда
  у роли есть кандидаты, — тот же принцип, что уже принят для Change 1
  («REST-бюджет на объёме проекта сейчас — не проблема»).

## Migration Plan

Аддитивно: новое поле `TaskRef.DependsOn` и новая проверка в `claim()` не
меняют существующий формат данных. Задачи без `depends_on` (сегодня —
все, кроме детей `split`) гейта не замечают вовсе. Тикеты, уже связанные
Change 1 на живом JIRA (`EXP-16…20` и подобные), начинают корректно
читаться сразу после деплоя — без бэкафилла: `issuelinks` уже на месте,
только чтение было сломано.

Откат — реверт коммитов; персистентных форматов, которые нужно было бы
откатывать отдельно, это изменение не вводит.
