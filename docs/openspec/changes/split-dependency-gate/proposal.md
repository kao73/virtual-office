## Why

Волна 2 Change 1 (`pipeline-split-autocreate`, смёржен в `master` #7,
подтверждён живьём) научила раннер создавать тикеты-детей и связывать их по
`depends_on`, но ничто в конвейере эту связь не читает: `analyst` и
`implementer` могут начать работу над зависимой задачей раньше, чем её
предшественник смержен, — Shape-исследование или сама реализация рискуют
опереться на код, которого ещё нет, теряя тот самый параллелизм, ради
которого разбиение затевалось (человек должен вручную следить за
очерёдностью). Предусловие «Change 2 отложен до живой проверки Change 1»
закрыто — это тот самый Change 2.

## What Changes

- Новый детерминированный гейт в `claim()`: кандидат, чей `depends_on`
  называет задачу не в терминальном статусе, пропускается в этот `tick` —
  один и тот же код для всех ролей графа, без специального исключения
  `reviewer` (его зависимость уже разрешена к этому моменту по построению).
- `runner ls` показывает, чего ждёт заблокированный кандидат.
- **Исправление, обязательное для гейта на JIRA**: `Task.DependsOn` сейчас
  пишется (`LinkDependsOn`), но не читается обратно на JIRA-трекере —
  `jira.toTask` не разбирает `issuelinks`, а поиск (`ListReady`/`List`) даже
  после этого не запрашивал бы их без правки `searchFields()`. На `mock`
  уже работает корректно.
- `roles/analyst/role.md`: явный критерий, когда ставить `depends_on` между
  детьми `split` — реальная зависимость по очерёдности слияния кода, не
  «так логичнее по порядку».

## Capabilities

### New Capabilities
- `pipeline-dependency-gate`: поведенческий контракт «раннер не начинает
  работу над задачей, пока её `depends_on`-зависимость не в терминальном
  статусе», единый для `analyst`/`implementer`/`reviewer`, включая
  одинаковое поведение на файловом и JIRA-трекере и видимость в `runner ls`.

### Modified Capabilities
- `role-native-workflow`: добавляется требование к критерию, которым
  `analyst` ставит `depends_on` между детьми `split.children[]` — до этого
  спецификация описывала только формат и валидацию графа, не то, когда
  связь уместна по смыслу.

## Impact

`internal/tracker/jira/jira.go` (`toTask`, `searchFields`),
`internal/tracker/tracker.go` (`TaskRef.DependsOn`, доккомментарий
`Task.DependsOn`), `internal/pipeline/pipeline.go` (`claim()`), новый
`internal/pipeline/deps.go`, `cmd/runner/board.go` (`ls`),
`roles/analyst/role.md`. `internal/tracker/mock` не меняется — уже
соответствует контракту. Поведенческое изменение, не API-breaking: задачи
без `depends_on` (подавляющее большинство) гейта не замечают вовсе.
