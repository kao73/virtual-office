## Context

См. `proposal.md` за мотивацией и `docs/notes/analyst-task-splitting.md`
(раздел «Волна 2 — брейншторм 2026-09-05», подраздел «Change 1») за полной
историей решения — этот документ переносит уже принятые там решения в
формат Comet Design, не передумывает их заново.

Сегодня: `internal/tracker.Tracker` не имеет ни attachment-методов, ни
`CreateTask`, ни понятия связи между задачами. Путь `outcome: split`
(волна 1) рендерит `split.children[]` только человекочитаемым текстом
(`internal/tracker/report.go`, `SplitBlock`) — вложение, которое кусок 5
волны 1 задумал, в код не попало. `roles/analyst/role.md`'s резюме-цикл
после `split` ветвится на три вопроса подряд («разбить как предложено?» →
«подзадачи уже заведены?» → «что дальше с этим тикетом?»), спроектированных
под ручное создание тикетов человеком.

## Goals / Non-Goals

**Goals:**
- Второе подряд подтверждение разбиения запускает автоматическое, идемпотентное
  создание и связывание тикетов-детей и перевод родителя в `Done` —
  без прогона агента на сам шаг создания.
- Данные `split.children[]` доживают от момента предложения до момента
  создания без потерь и без повторного разбора человекочитаемого текста.
- `mock` и `jira`-реализации `Tracker` ведут себя одинаково для новой
  поверхности.

**Non-Goals:**
- Гейт очерёдности в `claim()` — Change 2, отдельный заход, отложенный до
  живой проверки этого изменения.
- Кэширование/бюджет запросов к трекеру — не нужен на объёме проекта сейчас.
- Общий механизм связей произвольного типа — только узкое «зависит от».
- Изменение контракта `result.json` (`internal/runner/agentio.go`) — исход
  `split` не меняется, меняется только то, что раннер делает после второго
  подтверждения.

## Decisions

**1. Узкая поверхность `Tracker`, не общий механизм связей.**
`AddAttachment`/`GetAttachment`, `CreateTask`, `FindByMarker`,
`LinkDependsOn` — каждый метод под один конкретный случай использования, а
не параметризованный «любой тикет ↔ любой, с типом связи». Альтернатива
(общий `Link(from, to, kind)`) ближе к тому, что даёт сама JIRA, но требует
продумывать словарь `kind` и его паритет между `mock`/`jira` уже сейчас,
хотя волне 2 нужен ровно один случай. Меньше поверхности сейчас; другой тип
связи — новый метод тогда и добавится.

**2. Идемпотентность — опрос трекера (`FindByMarker`), не хранимый маркер.**
Перед каждым созданием ребёнка раннер спрашивает трекер: «есть ли уже тикет
с меткой `split-parent:<KEY>`+`split-child:<id>`». Альтернатива (маркер в
теге комментария или во вложении, обновляемый по ходу создания) — источник
рассинхронизации: если раннер умирает между созданием тикета и записью
маркера, тикет уже есть, а маркер про него ещё не знает — ровно то
рассогласование следствия и причины, о котором `docs/DESIGN.md` §2.3
предупреждает («Проверять причину, а не следствие»). Опрос
самоисцеляется: маркер живёт на самом созданном тикете (его метка), не
отдельной записью, которая может отстать.

**3. Метка на созданном тикете (`labels`), не кастомное поле JIRA.**
`split-parent:<KEY>` + `split-child:<id>` — обычная метка. Кастомное поле
потребовало бы настройки конкретного JIRA-инстанса под проект
(`customfield_*`, привязка к `tracker.yaml` — см. `docs/DESIGN.md` §2.5),
чего волна 2 сознательно избегает: метка работает «из коробки» на любом
проекте, `mock` реализует её как обычное поле в YAML задачи без всякой
настройки.

**4. Различение «первое предложение» vs «подтверждено» — по переписке, не
по хранимому флагу.** Раннер считает предыдущие комментарии-маркеры
`outcome:split` от `analyst` на этом тикете: второй — подтверждение. Тот же
приём, что `docs/DESIGN.md` §2.8 уже использует для состояния pull request
(«состояние PR выводится из переписки... по последней записи семейства»).
Хранимый флаг создал бы вторую версию истины, которая может разойтись с
самой перепиской — прецедент того же принципа, что решение №2 выше.

**5. Создание — код раннера, не роль.** Никакой агент не запускается на сам
шаг «создать тикеты и связи». Совпадает с тем, как уже устроены `Archive`
Comet Native и открытие pull request (`docs/DESIGN.md` §2.2, §2.8) — обе
детерминированные операции без диспетчеризации роли. Альтернатива
(отдельный прогон `analyst`, подтверждающий готовность) добавляла бы
оплаченный вызов LLM ровно там, где решать нечего — данные уже есть во
вложении, решение уже принято человеком.

**6. `roles/analyst/role.md`: убрать оба нижних вопроса резюме-цикла, не
только «подзадачи уже заведены?».** Design-документ волны 2 называл только
этот вопрос и соответствующий сценарий спеки как подлежащие удалению — при
детальной проработке здесь выяснилось: третья ветка резюме («что дальше с
этим тикетом?») существовала только как продолжение *этого* вопроса (она
резюмировала после его исхода `needs_human`). Раз вопрос никогда больше не
задаётся, эта ветка тоже осиротела — её удаление в `role.md` идёт вместе, а
не отдельной задачей. Формального сценария в openspec-спеке под неё не
было (сверено с живым `docs/openspec/specs/role-native-workflow/spec.md`
перед написанием этого документа) — только правка `role.md`.

**7. Обработка ошибок: повтор через опрос + системная запись на каждой
попытке, без нового счётчика.** Идемпотентность (решение №2) делает повтор
безопасным всегда — специальный `attempts`-подобный предохранитель не
нужен, это не прогон агента (см. решение №5, тот же довод, что и у
`Archive`/PR: они тоже не тратят `attempts`). Эскалация после N неудач
сознательно не проектируется — решить по факту первого реального сбоя.

## Risks / Trade-offs

- **[Risk]** Тип связи «зависит от» может отсутствовать на локальном
  JIRA Server 8.13. → Проверить в первой Build-задаче, трогающей
  `internal/tracker/jira`'s `LinkDependsOn`, до написания остального кода
  вокруг неё; если типа нет — завести его на инстансе отдельным
  операционным шагом, не блокирующим сам код.
- **[Risk]** Повторный вызов `LinkDependsOn` для уже существующей связи
  может завершиться ошибкой или задвоить связь на стороне JIRA. →
  Проверить эмпирически на полигоне при реализации; если не идемпотентно
  само по себе — добавить проверку существующих `issuelinks` перед
  созданием.
- **[Trade-off]** Нет эскалации после N неудачных попыток пакетного
  создания — принято: идемпотентность и системная запись на каждой
  попытке дают достаточную видимость сейчас; порог вводится по факту
  первого реального затяжного сбоя, не заранее.
- **[Trade-off]** Удаление двух нижних веток резюме-цикла `role.md`
  убирает работающий, только что отревьюженный код. Принято: обе ветки
  становятся недостижимы — их наличие не защита, а мёртвый груз, который
  сбивает будущего читателя `role.md` предположением, что до них можно
  дойти.

## Migration Plan

Миграции данных нет — новая поверхность `Tracker` аддитивна, ничего
существующего не меняет по формату. Тикеты, уже стоящие в `Blocked` с
ранее предложенным (волной 1) разбиением и ожидающие первого ответа
человека, ничего не теряют: детектор подтверждения по переписке (решение
№4) считает существующие комментарии как есть, ничего не бэкафилля — при
следующем ответе человека поведение просто становится новым для *второго*
подтверждения, без миграции старых данных.

Откат — реверт коммитов; закреплённых форматов, которые нужно было бы
откатывать отдельно (схем БД, персистентных флагов), это изменение не
вводит.
