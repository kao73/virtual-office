## Why

Сегодня решение «задача слишком крупная, надо резать» аналитик принимает уже
*после* полного Comet Native Shape-исследования — `comet native new`
выполняется на первом шаге, до любой оценки размера. К моменту, когда
аналитик мог бы сказать «это на самом деле несколько задач», прогон уже
стоит как полноценное исследование одной сущности. У самого Comet Native
есть при этом собственный, несовместимый с конвейером офиса механизм
разбиения — Supervisor Change (`children.yaml`) — и ничто в `role.md` прямо
не запрещает аналитику в него провалиться, если формулировка задачи похожа
на его целевой случай.

Оба пункта уже разобраны и решены в `docs/notes/analyst-task-splitting.md`
(Кусок 6) и подтверждены ревью советом (`council`, Architect/Skeptic/
Pragmatist/Critic) без замечаний — это первый из двух флоу волны 1 того
дизайна. Ревью, однако, отдельно напомнило то, что уже стояло в «Проблеме»
исходного документа: граница «разбить» vs «много мелких, но безопасных
решений» (как в живом EXP-4) никогда не проверялась эмпирически. Перенос
проверки раньше повышает цену ложного срабатывания в обе стороны, поэтому
это изменение добавляет golden-кейсы на обе стороны границы, а не только
меняет `role.md`.

## What Changes

- `roles/analyst/role.md`:
  - явный запрет заводить `children.yaml`/Supervisor Change Comet Native;
    крупную постановку аналитик ведёт только через существующий офисный
    исход `needs_human` («задача крупная, разбить»);
  - оценка размера постановки перемещается на момент **до** вызова
    `comet native new` — дешёвое чтение постановки (без входа в протокол
    Comet Native вообще), а не после полного Shape-исследования, как
    сегодня.
- `evals/analyst/`: два новых golden-кейса —
  - позитивный — постановка описывает несколько явно независимых сущностей
    (по образцу Category+Transaction из `docs/notes/analyst-task-splitting.md`):
    аналитик должен уйти в `needs_human` с предложением разбить, не вызывая
    `comet native new` и не создавая `children.yaml`;
  - негативный — постановка вида живого EXP-4 (одна сущность, несколько
    мелких, но безопасных решений: модель, миграция, CRUD): аналитик не
    должен ложно сработать на разбиение и обязан пройти обычный Shape-путь.

Схема `result.json` и Go-код раннера этим изменением не затрагиваются: исход
разбиения остаётся сегодняшним `needs_human`. Свой пятый исход `split` —
предмет следующего флоу волны 1, `analyst-split-outcome`.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `role-native-workflow`: добавляются два требования, которых у капабилити
  сегодня нет — момент оценки размера постановки относительно
  `comet native new`, и запрет на использование Supervisor Change
  (`children.yaml`) аналитиком. Существующие четыре требования капабилити
  не меняются.

## Impact

- `roles/analyst/role.md` — только текст промпта, без изменения схемы
  раннер↔агент и без Go-кода.
- `evals/analyst/<new-case-1>/`, `evals/analyst/<new-case-2>/` — новые
  директории с фикстурами golden-кейсов (`task.md`, `expect.yaml`),
  структура — как у существующих кейсов в `evals/analyst/`.
- Проверка изменения — ручной прогон `./bin/eval-roles` по этим двум
  кейсам (платный, real API calls; `role-eval-harness` уже требует, что
  запуск харнеса — только вручную, это требование не меняется).
- Прочий код репозитория, `workflow.yaml`, контракт `docs/contracts/agent-io.md`
  не затрагиваются.
