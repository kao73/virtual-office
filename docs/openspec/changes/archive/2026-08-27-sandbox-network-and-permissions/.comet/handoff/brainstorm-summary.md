# Brainstorm Summary

- Change: sandbox-network-and-permissions
- Date: 2026-08-27

## Confirmed Technical Approach

Два открытых вопроса из design.md (открытой фазы) закрыты.

**Вопрос 1 — код-уровень встраивания `defaults` в `tracker/config.go`.**
Подход А: `Projects` остаётся `map[string]officeProject`/`map[string]machineProject`.
`LoadProjects` перед основным циклом валидации вынимает ключ `"defaults"`
(если задан) в отдельную переменную и не подчиняет его требованиям обычного
проекта (`repo_url`, `tracker`, `default_branch`, `branch_prefix`, парность
office/machine). `officeProject`/`machineProject` получают новые поля
`Network []string` и `Tools{Allow, Deny []string}`. Имя `"defaults"`
становится зарезервированным — попытка завести проект с таким именем
отклоняется понятной ошибкой на загрузке.

Отклонённая альтернатива (Б): разбить схему на два поля верхнего уровня
(`defaults:` / `projects:` как разные YAML-ключи вместо плоской карты).
Чище типово, но требует переформатировать оба файла для каждого уже
существующего проекта, включая `projects.local.yaml` на уже поднятых
машинах офиса (вне репозитория, ручная миграция на каждой).

**Вопрос 2 — устойчивые к флагам-префиксам формулировки `tools.deny`.**
Эмпирически проверено (throwaway git-репозиторий + локальный bare remote,
`claude -p --permission-mode dontAsk`, 2026-08-27):

- `Bash(git push*)` (прежняя форма) не ловит `git -c core.pager=cat push`
  — подтверждает прежнюю находку.
- `Bash(*git push*)` (звёздочки по краям буквальной подстроки) тоже не
  ловит — потому что во флаговой форме подряд идущей подстроки «git push»
  физически нет. Паттерн при этом рабочий: тот же прогон подтвердил, что
  `*git push*` ловит обычный `git push origin master`.
- `Bash(git *push*)` (звёздочка **между** «git» и «push», не по краям)
  **ловит** флаговую форму. Подтверждено дважды: как allow-паттерн
  (изолированный тест) и как deny-паттерн поверх широкого `Bash(*)` allow —
  именно предлагаемая конфигурация: push не дошёл до remote (HEAD remote
  не сдвинулся).

Вывод: формулировки `defaults.tools.deny` переносят существующие 7 строк
(`push`/`remote`/`checkout`/`switch`/`branch`/`worktree`/`config`) в форму
с внутренней `*` между git-глаголом и подкомандой (`Bash(git *push*)` и
аналогично для остальных), а не как есть (`Bash(git push*)`).

Побочная находка (не решение этого изменения, зафиксировать как заметку):
составная команда через `;` (`git push ...; echo ...`) была отклонена
отдельным механизмом харнесса Claude Code, не связанным с glob-паттернами
allow/deny — увидено побочно в этом же прогоне.

**Вопрос 3 (найден при подготовке Design Doc, не был в исходном списке) —
где физически происходит слияние роли с проектными слоями.**
`adapter.Build` не знает про `Project` вообще (`runagent/runagent.go:135`
зовёт `claude.Build(opts.Role, ...)` без проекта). Проект резолвится выше
по стеку, и делает это **по двум разным путям**:
- `pipeline/pipeline.go:176` (`Office.tickRole`, реальный конвейер) грузит
  роль ДО того, как проект задачи известен — `claim()` резолвит
  `task.ref.Project` позже (около строк 190/325).
- `runner/cmd/run-agent/main.go` (отдельный ручной/debug CLI) сейчас вообще
  не знает о проектах — флагов `-role`/`-workdir`/`-backend`/`-task`/`-base`,
  но не `-project`.

Решение: чистая функция `runner.MergeProjectRules(role, project) Role`,
вызывается в `pipeline.go` ПОСЛЕ `claim()` (не сразу после `LoadRole`,
это было бы слишком рано — проект ещё не известен); `run-agent` получает
новый необязательный флаг `-project`, применяющий то же слияние при ручном
прогоне — чтобы воспроизведение бага руками не расходилось с тем, что видит
реальный конвейер.

## Key Trade-offs and Risks

- Подход А делает `"defaults"` зарезервированным именем — дешёвая, но
  обязательная проверка на загрузке, иначе тихая коллизия с реальным
  проектом.
- Deny-паттерны с внутренней `*` защищают конкретно от вставки одного
  флага/опции между git-глаголом и подкомандой — не универсальное решение
  класса проблем (составные команды, экзотические формы инвокации
  по-прежнему отдельный разговор).

## Testing Strategy

- Юнит-тесты `LoadProjects`: `defaults` отсутствует в одном из двух файлов;
  `defaults` в обоих; попытка назвать проект `defaults` отклоняется;
  реальный проект без `defaults` ведёт себя как сегодня (регресс).
- Юнит/интеграционные тесты слияния слоёв: union без ослабления `tools.deny`.
- Живая проверка новых `tools.deny`-формулировок на реальном ролевом
  прогоне (tasks.md, группа 6) — тем же способом, что и в этом брейнштормінге,
  но уже в целевой конфигурации ролей, а не в изолированном throwaway-репо.
