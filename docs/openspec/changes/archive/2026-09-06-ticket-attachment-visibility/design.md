## Context

См. `proposal.md` за мотивацией. Сегодня: `tracker.Task` не несёт вложений
вообще; `jira.toTask` выбрасывает `fields["attachment"]`; `mock.AddAttachment`
не хранит имя вложения (только байты под номером); единственное вложение,
которое раннер вообще умеет создавать и читать сам, — `split.json`
(`internal/pipeline/pipeline.go`, `Office.record`). Материализация
`task.md`/`context.md` в рабочую папку идёт через `runner.PrepareInput`
(`internal/runner/input.go`), вызываемую из `Office.work()`
(`internal/pipeline/pipeline.go`), где уже есть и трекер, и свежая задача.

## Goals / Non-Goals

**Goals:**
- Любая роль видит человеческие вложения своего тикета настоящими файлами
  в рабочей папке, без исключения по типу роли.
- Ребёнок подтверждённого split наследует человеческие вложения
  непосредственного родителя, тем же принципом идемпотентности, что уже
  есть у самого факта существования тикета-ребёнка.
- Служебные вложения раннера (`split.json`) никогда не показываются агенту.

**Non-Goals:**
- Не решается наследование вложений через несколько уровней разбиения
  специальным «корневым» механизмом — копия всегда с непосредственного
  родителя, и она уже несёт то, что унаследовал он сам (тот же приём, что
  `childDescription` применяет к тексту описания).
- Не вводится общий механизм чтения агентом произвольных вложений трекера
  по запросу (on-demand) — только то, что раннер сам решил материализовать
  перед прогоном.
- Не решается коллизия двух вложений родителя с одинаковым именем при
  наследовании детьми (докатится только одно) — узкий случай, принятый как
  документированное упрощение.

## Decisions

**Модель данных — расширение `Task`, не отдельный запрос.** JIRA `Get()`
уже тянет вложения в составе всего `issue` (`fields["attachment"]`) — тот
же вызов, без нового round-trip. Значит `tracker.AttachmentRef{ID, Name}` и
`Task.Attachments []AttachmentRef` populate'ятся в `toTask` бесплатно.
Альтернатива (отдельный метод `ListAttachments`) добавила бы контракт и
запрос ради данных, которые уже приходят.

**Мок учится хранить имя — сайдкар-файл, не единый индекс.**
`AddAttachment` пишет вложение под номером (`0001`) и рядом `0001.yaml`
с именем (`attachmentHead{Name}`) — тот же принцип, что уже применяют
комментарии (YAML-шапка + тело), только раздельно: тело вложения —
произвольные байты, а не текст, и текстовую шапку перед ним не приписать
безопасно. Альтернатива (общий JSON-индекс `attachments.yaml` на все
вложения задачи) усложнила бы конкурентную запись без выигрыша на
масштабе этого мока.

**Материализация — настоящие файлы, не текст в `task.md`.** Среди вложений
бывают картинки и PDF, которые агент читает своими инструментами чтения
файлов, а не разбором markdown. `runner.Input` получает
`Attachments []InputAttachment{Name, Data}`; `PrepareInput` пишет их в
`.agent/attachments/`, `task.md` получает только упоминание списком имён —
тем же приёмом, что уже применяет «Метки: …».

**Санитация имени — `filepath.Base` плюс явная проверка `".."`.** Имя
вложения — ввод человека, не раннера. `filepath.Base` само режет
`"../../etc/passwd"` до `"passwd"`, но голое имя `".."` после `Base`
остаётся `".."` буквально, а `filepath.Join(dir, "..")` — это уже
родитель `dir`, не файл внутри него; такое (и `"."`, и пустое имя, и сам
разделитель путей) заменяется заглушкой `"attachment"`.

**Коллизия имён — счётчик-префикс по факту, не заранее объявленная схема.**
Первое вложение с данным именем сохраняет его как есть; каждое следующее
с тем же именем в этом прогоне получает числовой префикс (`2-schema.png`,
`3-schema.png`). Простая, детерминированная в пределах одного вызова
`PrepareInput` схема — этого достаточно, поскольку порядок вложений внутри
одного прогона фиксирован.

**Фильтр служебных вложений — одна функция, три места применения.**
`runner.SplitAttachmentName` называет единственное сегодняшнее служебное
имя; `Office.humanAttachments(task)` — единственное место, решающее, что
из `task.Attachments` увидит агент, — используется и в `taskBody`
(упоминание), и в `fetchAttachments` (материализация своей задачи), и в
`ensureChildAttachments` (наследование детьми). Разъехавшийся по трём
местам список исключений было бы легко забыть обновить в одном из них.

**Наследование детьми — строгая идемпотентность, перепроверка на каждом
проходе.** В отличие от текста описания (пишется один раз при создании
тикета, в том же вызове `CreateTask`), вложения копируются отдельными
вызовами `AddAttachment` уже ПОСЛЕ создания ребёнка — значит прогон может
прерваться между «ребёнок создан» и «вложения скопированы». Решение:
`ensureChildAttachments` перечитывает текущие вложения каждого ребёнка
(`Get`) на **каждом** проходе `CompleteSplits`, а не только когда ребёнок
только что создан, и докатывает по имени то, чего не хватает. Альтернатива
(копировать только в момент создания, как текст) дешевле кодом, но
оставляла бы прерванный ровно на этом шаге прогон без вложений навсегда —
владелец явно выбрал строгий вариант, увидев эту дыру.

## Risks / Trade-offs

- [Родитель с двумя вложениями одного имени] → докатится только одно
  (сверка идёт по имени). Принято как документированное упрощение —
  различить их для человека, читающего результат, всё равно нечем.
- [`ensureChildAttachments` добавляет `Get()` на каждого ребёнка при
  каждом проходе `CompleteSplits`] → для типичного размера разбиения
  (2–5 детей) это несколько лишних запросов раз в цикл, не масштабная
  нагрузка; альтернатива (хранимый флаг «вложения скопированы») вносила
  бы состояние, которое можно рассинхронизировать с трекером.
- [Материализация вложений на каждый прогон перезаписывает
  `.agent/attachments/` целиком] → корректно отражает то, что набор
  вложений тикета мог измениться между попытками, но означает, что агент
  не может полагаться на прошлый прогон, оставивший что-то своё в этом
  каталоге, — тот же принцип, что уже применяют `result.json`/`run.log`.
- [Вложение, которое `ensureChildAttachments` не может залить ни разу
  (постоянная, не временная беда — например, лимит размера вложения на
  инстансе) блокирует `linkChildren`/`closeSplitParent` для этого
  разбиения навсегда, при одном-единственном уведомлении] → принято как
  тот же класс риска, что уже есть у `linkChildren` и `closeSplitParent`
  до этой правки: любой шаг `completeSplit`, обёрнутый `splitFailed`, уже
  мог зависнуть так же при постоянной беде — это не новый риск, а то же
  свойство, распространённое на один дополнительный шаг (независимое
  ревью build-фазы, 2026-09-06).

## Migration Plan

Обратной несовместимости нет: `Task.Attachments` — новое поле, ничего
существующего не меняет. Разворачивается тем же PR, что и остальные
изменения этой ветки; отдельного шага миграции данных не требуется —
существующие вложения (например, уже созданный `split.json` прежних
прогонов) читаются той же логикой без переиндексации.
