## Why

Первый флоу волны 1 (`analyst-early-size-check`) научил `analyst` решать «эту
постановку надо резать» дёшево, до входа в Comet Native Shape. Живой прогон
`EXP-2` (`kao73/expense-tracker`, полная неразрезанная постановка «Трекер
личных расходов») подтвердил: решение принимается верно, а предложение
разбивки на пять зависимых подзадач целиком уходит в комментарий тикета —
ровно так, как задумано. Но обнаружился пробел: аналитик пользуется общим
исходом `needs_human`, у которого нет машиночитаемой структуры разбивки, и
`role.md` не говорит **ничего** о том, что делать, если человек ответит «да»
на предложение. Второй прогон по тому же тикету, где постановка не изменилась
(человек ещё не завёл подзадачи), сегодня — неопределённое поведение: может
повторить тот же вопрос, а может ошибочно попытаться вести Shape по всей
исходной постановке целиком.

## What Changes

- Новый, пятый исход `split` в контракте `result.json` (рядом с
  `done`/`needs_human`/`blocked`/`failed`) — `internal/runner/agentio.go` +
  `docs/contracts/agent-io.md`. Несёт структурированный список подзадач
  `split.children[]` (`id`/`title`/`description`/`depends_on`), не только
  прозу вопроса.
- Валидация `split.children[]`: список непустой, `id` уникальны, каждый
  `depends_on` ссылается только на `id`, существующие в этом же списке, без
  циклов.
- `roles/analyst/role.md`: исход «задача крупная и её надо резать» переходит
  с `needs_human` на `outcome: split`. Добавлена инструкция для резюме после
  ответа человека на split-вопрос: не вести Shape по исходной постановке
  целиком, не вызывать `comet native new` на неё — подзадачи заводит человек,
  аналитику в этом тикете больше нечего делать.
- Обновлён golden-кейс `evals/analyst/escalation-oversized-split`: проверка
  `outcome: split` и структуры `split.children[]` вместо прежней проверки
  `outcome: needs_human`.
- Добавлены Go-юнит-тесты на валидацию `split.children[]` (цикл, дубль `id`,
  висячая ссылка, пустой список) — дёшево и детерминированно, живого прогона
  роли для этого не требуется.

### Modified Capabilities

## Impact

- `internal/runner/agentio.go` — новый исход `split`, структура
  `split.children[]`, валидация.
- `docs/contracts/agent-io.md` — документация контракта (обычный файл вне
  OpenSpec-капабилити, не отдельная делта-спека).
- `roles/analyst/role.md` — раздел «Исходы» и новый параграф о резюме после
  ответа человека.
- `evals/analyst/escalation-oversized-split/expect.yaml` — проверка нового
  исхода.
- **`workflow.yaml`** — маршрут для исхода `split` в `roles.analyst.outcomes`
  обязателен. Раннер маршрутизирует по `flow.Outcomes[outcome]`
  (`internal/pipeline/pipeline.go`, `finish()`); исхода, для которого в графе
  нет записи, — жёсткая ошибка прогона («для исхода %s нет перехода в
  графе»), не тихий обход. Без этой записи `split` немедленно ломает
  пайплайн при первом же живом появлении. Найдено чтением кода при написании
  спеки, не было в исходном объёме сообщения пользователю — фиксирую здесь.
- Раннер (парсер тега `outcome:...` при публикации комментария и при разборе
  ответа человека, `internal/tracker/marker.go` и `questions.go`) —
  подтверждено чтением кода: механизм уже общий для любого исхода с
  `questions`, правки не требует (старое жёсткое правило по буквальному
  `outcome:needs_human` уже снято намеренно — комментарий у `HumanReply`
  прямо это объясняет).
- **`internal/runner/agentio.go`, валидация `Questions`** — сегодня непустой
  `questions` разрешён **только** при `outcome=needs_human`; для любого
  другого исхода валидатор его отклоняет («вопросы только для
  needs_human»). `split` обязан нести вопрос человеку так же, как
  `needs_human`, — правило валидации расширяется на оба исхода.
- **`internal/tracker/config.go`** — пакетный список `outcomes` («исходы, для
  которых граф обязан задать переход») зеркалит контракт и используется для
  **всех** ролей графа, не только для той, что реально его эмитит: добавление
  `split` в контракт означает, что `workflow.yaml` обязан завести маршрут
  `split` не только у `analyst`, но и у `implementer`, и у `reviewer` —
  иначе `Workflow.Validate()` откажет при старте. По смыслу эти две роли
  `split` никогда не эмитят; маршрут для них — тот же `{to: Blocked, human:
  true}`, что и их `needs_human`, чисто для прохождения валидации.

- **`cmd/eval-roles/loadcase.go`, `knownOutcome`** — тот же хардкод четырёх
  исходов, но у самого харнесса golden-кейсов: `expect: split` в
  `expect.yaml` сегодня отвергается на загрузке кейса («outcome-проверка с
  неизвестным expect»). Расширяется тем же способом, что и в
  `agentio.go` — без нового вида проверки, `outcome` уже способен сверять
  любое значение из списка.
- **`cmd/eval-roles/checkers.go`, `outcomeChecker.Run`** — `questions_not_empty`
  сегодня действует только при `want == needs_human`; расширяется на `split`
  тем же условием, что и валидация в `agentio.go` выше. Саму структуру
  `split.children[]` отдельным check kind не проверяем: контракт уже не даст
  прогону вернуть `outcome: split` с невалидными `children` (см. «Валидация
  `split.children[]`» выше) — прохождение `outcome`-проверки уже свидетельствует
  о валидности.

**Важное ограничение маршрута, найденное тем же чтением кода:** `done` для
`analyst` при незнакомом `next_owner` (в т.ч. зарезервированном `none`) едет
по маршруту **по умолчанию** — в `Ready`, то есть implementer получил бы
неразрезанную задачу и начал бы писать код по ней. Значит, ни исход `split`,
ни резюме после ответа человека **не могут** использовать `outcome: done` ни
с каким `next_owner` — только исходы, которые графа маршрутизирует в
`Blocked` (`needs_human`-подобные). Это определяет выбор исхода для резюме
после ответа человека в `design.md` ниже.

Не входит в объём (волна 2, отдельный будущий заход): автоматическое
создание тикетов из `split.children[]`, использование `depends_on`
программно (сейчас — чисто информационное поле для человека), гейт
очерёдности между связанными тикетами.
