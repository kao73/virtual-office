# Этап 5. Бэклог первого не-полигона — `kao73/expense-tracker` (проект `EXP`)

Постановка целиком — от владельца, 2026-08-26 (текст ниже сокращён до сути,
полный — в истории чата и в тикетах). Документ разбивает её на задачи под office:
маленькие, backend-only (фронт вне игры — ограничение шага 5, роли не видят
`registry.npmjs.org`), в порядке зависимостей. Не план работ office'а как
инструмента — план того, что мы просим его сделать.

## Ограничения этого захода

- Только backend (FastAPI/SQLModel). Дашборд и графики из постановки — это
  фронт; ниже они превращены в агрегирующие эндпоинты, которые фронт потом
  будет читать. Сам фронт не трогаем и не заводим на это задач.
- Каждая задача — вертикальный срез (модель + миграция + роуты + тесты),
  небольшой, чтобы через него быстро прогнать весь цикл analyst→implementer→
  reviewer→PR и увидеть, где механика ломается.
- Порядок ниже — по зависимостям (Transaction ссылается на Category, Budget
  агрегирует Transaction и т.д.), не по приоритету исполнения.

## Находки прогона задачи 1

Полный цикл прошёл end-to-end: `Backlog → Analysis → Ready → Review (с одним
возвратом на доработку) → Approved → PR`. Пять прогонов, суммарно **$5.56**
(вместо полигонных $0.37 — объяснимо холодным чтением большого чужого
репозитория плюс один цикл ревью-доработки, не аномалия).

- **`design.md` — контракт, а не предположение.** Живой прогон показал, что
  implementer без специальной инструкции заново эмпирически перепроверяет
  решения, которые аналитик уже обосновал и записал (`CategoryKind` как
  `str+Enum` vs `Literal`, `except A, B:`-синтаксис) — чистое дублирование
  шагов. Правка `roles/implementer/role.md` (`bb55eda`/предыдущий коммит):
  доверять `design.md`, перепроверять только при расхождении с кодом.
  Эффект измерен на этой же задаче: 51 шаг/$1.18 (усечение, без правки) →
  34 шага/$0.79 (с правкой, тот же объём плюс тесты).
- **Implementer прогонял линтеры по своему усмотрению, а не полный набор
  проекта** — пропустил `ty check`, ревьюер поймал реальную ошибку типов.
  Allow-список тут ни при чём (`mypy`/`ty` уже доступны через `Bash(uv *)`,
  раз `.pre-commit-config.yaml` сам вызывает их через `uv run`) — не хватало
  явного требования. Правка role.md: находить и гонять полный набор
  статических проверок проекта (`.pre-commit-config.yaml`/`make lint`) перед
  завершением. Эффект увидим на следующей задаче, писанной с нуля.
- **Postgres недоступна ни `implementer`, ни `reviewer` — системный блокер,
  не починенный.** Причины независимые и от allow-списка Bash не зависят:
  Docker внутри `sbx`-песочницы недоступен/ненадёжен, сети до внешней БД в
  `network.allow` нет, а сам `Makefile` репозитория говорит прямо: `# Tests
  run on the host against Postgres in Docker`. Полный `Bash(*)` не решает
  этого (и опасен отдельно — см. ниже) — весь `pytest`/`alembic
  upgrade`/`downgrade` за всю историю задачи ни разу не был прогнан вживую.
  **Перед мержем PR #9 нужно вручную прогнать `uv run pytest backend/tests -q`
  и `uv run alembic upgrade head`/`downgrade -1` на поднятой Postgres** —
  это не сделано ни одной ролью и остаётся ручным шагом.
- **Полный `Bash(*)` для ролей рассматривали и отклонили.** Уже задокументированная
  дыра в этом же `role.yaml`: allow all + deny specific обходится префиксом
  (`git -c core.pager=cat push` на живом прогоне этапа не тронутого предела).
  Открытие Bash не решило бы и проблему с БД — она сетевая/инфраструктурная,
  не про разрешения Claude Code.
- **`PRPass` (системный проход) не пишет об успехе в консоль раннера** — только
  комментарием в тикет. Разбор одного тика ошибочно принял тишину в stdout
  за то, что PR не открылся, хотя он открылся тем же прогоном. Не баг,
  но стоит когда-нибудь добавить симметричный лог в stdout.
- Среди PR репозитория есть закрытый **PR #8 «Этап 1: Категории расходов и
  доходов»** (ветка `stage-1-categories`) — похоже на более раннюю ручную
  попытку той же темы. Веток не пересекает, но стоит сверить на смысловое
  дублирование перед мержем PR #9.

## Что можно взять в работу дальше

**Пока PR #9 не смержен человеком — фактически ничего.** Задачи 2, 3, 5, 10
зависят от `Category`, а implementer будущей задачи заводит ветку от
`origin/main` — если `Category` там ещё нет, код попросту не увидит её.
Планирование (`analyst`) технически можно запускать и раньше, но реализацию —
только после merge.

После merge — по плану первой партии, в этом порядке:
- **№3 `Transaction` CRUD** — следующая по исходному плану, зависит только
  от 1.
- **№4** (список/фильтры транзакций) — сразу за ней.
- **№2** (удаление категории с переносом) — держим как кандидата на
  «задачу с вопросом» где-то в районе 4–5-й, как и планировали изначально;
  зависит только от 1, так что технически готова хоть сейчас после merge.

№5–11 подождут: они либо агрегируют `Transaction` (ещё не написана), либо
это бонусный CSV-импорт в конце очереди.
