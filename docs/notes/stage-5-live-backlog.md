# Этап 5. Бэклог первого не-полигона — `kao73/expense-tracker` (проект `EXP`)

Постановка целиком — от владельца, 2026-08-26 (текст ниже сокращён до сути,
полный — в истории чата и в тикетах). Документ разбивает её на задачи под office:
маленькие, backend-only (фронт вне игры — ограничение шага 5, роли не видят
`registry.npmjs.org`), в порядке зависимостей. Не план работ office'а как
инструмента — план того, что мы просим его сделать.

## Ограничения этого захода

- Только backend (FastAPI/SQLModel). Дашборд и графики из постановки — это
  фронт; ниже они превращены в агрегирующие эндпоинты, которые фронт потом
  будет читать. Сам фронт не трогаем и не заводим на это задач.
- Каждая задача — вертикальный срез (модель + миграция + роуты + тесты),
  небольшой, чтобы через него быстро прогнать весь цикл analyst→implementer→
  reviewer→PR и увидеть, где механика ломается.
- Порядок ниже — по зависимостям (Transaction ссылается на Category, Budget
  агрегирует Transaction и т.д.), не по приоритету исполнения.

## Бэклог

| № | Задача | Зависит от | Заметки |
|---|---|---|---|
| 1 | `Category`: модель + миграция + CRUD (create/list/get/update), стартовый набор дефолтных категорий при первом входе пользователя | — | по образцу `User` в `models.py` |
| 2 | Удаление категории с переносом связанных записей (`reassign_to`) | 1 | отдельно от базового CRUD — логика деликатнее; вероятный кандидат на «задача с вопросом» (что если переносить некуда) |
| 3 | `Transaction`: модель (сумма, дата, категория, тип expense/income, комментарий) + миграция + create/get/update/delete | 1 | |
| 4 | Список транзакций: пагинация, сортировка по дате, фильтры (период/категория/тип) | 3 | |
| 5 | `Budget`: модель (категория, месячный лимит) + CRUD | 1 | |
| 6 | Эндпоинт статуса бюджета: лимит / потрачено в текущем месяце / остаток по каждой категории с бюджетом | 3, 5 | агрегация по `Transaction` |
| 7 | Эндпоинт сводки за период: расходы, доходы, баланс | 3 | под будущий дашборд |

| 11 | Подтверждение импорта: сохранение отобранных записей, защита от дублей относительно существующих транзакций | 3, 10 | |
