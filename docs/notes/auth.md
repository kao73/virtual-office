# Авторизация Claude Code для неинтерактивного запуска

Проверено 2026-08-16 на `claude` 2.1.233.

**Секреты не хранятся в репозитории.** Ни ключей, ни токенов — ни в файлах, ни в промптах,
ни в логах. Только переменные окружения.

## Состояние машины разработчика

- `ANTHROPIC_API_KEY` — не задан.
- `claude auth status` → `loggedIn: true`, `authMethod: "claude.ai"`, `apiProvider: "firstParty"`,
  `subscriptionType: "max"`.

То есть локально всё работает на подписке, а неинтерактивный изолированный запуск требует
явного кредa в окружении (почему — см. «Изоляция ломает подписочный вход»).

## Путь A. API-ключ

Ключ создаётся в Claude Console и передаётся переменной:

```sh
export ANTHROPIC_API_KEY='sk-ant-...'
```

Поведение: «API key sent as `X-Api-Key` header. When set, this key is used instead of your
Claude Pro, Max, Team, or Enterprise subscription even if you are logged in. In non-interactive
mode (`-p`), the key is always used when present.»

- Оплата идёт по API, а не по подписке.
- Единственный путь, совместимый с `--bare`.
- Ближе всего к будущей ферме параллельных агентов (`DESIGN.md` §2.6).

## Путь B. Подписка (долгоживущий OAuth-токен)

Токен выпускается **вручную владельцем подписки**, командой:

```sh
claude setup-token
```

Требует активной подписки (Pro, Max, Team, Enterprise). Полученное значение передаётся
переменной:

```sh
export CLAUDE_CODE_OAUTH_TOKEN='...'
```

- Прогоны расходуют подписку, а не API-биллинг.
- Токен привязан к подписке того, кто его выпустил, — для общего доступа нескольких машин
  документация советует API-ключ.
- **Не работает с `--bare`**: «In bare mode, Claude Code never reads OAuth credentials or the
  system keychain… bare mode doesn't use your subscription login».

## Изоляция ломает подписочный вход

Проверено эмпирически: при подменённом `CLAUDE_CONFIG_DIR` команда `claude doctor` сообщает
`Not signed in to claude.ai` и `claude.ai subscription auth not active`, а в подменённом каталоге
создаётся пустой `.claude.json`. Подписочный вход живёт в конфиг-каталоге и при изоляции теряется.

Следствие для раннера: **изолированный запуск обязан получать кред явно, через окружение** —
других вариантов нет. Это касается обоих бэкендов, локального и докерного.

## Решение для этапа 1: поддерживаем оба пути

Раннер не выбирает путь за оператора и не угадывает. Правила:

1. Задан `ANTHROPIC_API_KEY` → путь A.
2. Иначе задан `CLAUDE_CODE_OAUTH_TOKEN` → путь B.
3. Заданы оба → путь A (совпадает с поведением самого CLI), выбор пишется в `run.log`.
4. Не задан ни один → раннер падает **до** запуска агента с внятным сообщением, а не отдаёт
   ошибку авторизации из середины прогона.
5. Если бэкенд собирается использовать `--bare`, а доступен только путь B → падать до запуска
   с объяснением несовместимости.

В окружение агента прокидывается **только выбранный** кред: второй не должен попадать
ни в процесс, ни в контейнер. Так прогон воспроизводим, а лишний секрет не путешествует.

В `--dry-run` и в логах значения кредов маскируются; печатается только имя выбранной переменной.

## Передача в контейнер

Секреты попадают в контейнер только из окружения хоста, никогда из файла в репозитории:

```sh
docker run --rm \
  -e ANTHROPIC_API_KEY \
  ...
# или
docker run --rm \
  -e CLAUDE_CODE_OAUTH_TOKEN \
  ...
```

Форма `-e ИМЯ` без значения передаёт переменную из окружения хоста — значение не появляется
в командной строке и не оседает в истории шелла и в списке процессов.

## Проверка

Перед отладкой раннера убедиться, что кред сам по себе рабочий, — документация советует
именно этот порядок: сначала проверить кред локальным вызовом `claude`, потом чинить обвязку.
