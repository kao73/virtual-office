# Чем изолировать прогон агента: чего стоит sbx и что есть кроме него

Кабинетное исследование, 2026-08-22. **Руками не проверялось ничего**: всё ниже —
из документации поставщиков и обзоров, а не из замеров. Числа и требования взяты
из источников; где источник молчит, так и сказано.

Повод — вопрос владельца об упаковке: «чтобы запустить офис на новой машине, нужно
много ручных операций; хочется упаковать в docker». Оттуда вырос второй вопрос —
не зря ли взят `sbx`, — и третий: какие вообще есть варианты, желательно
не только под macOS.

## Что выяснилось первым и меняет остальное

**`sbx` — самый узкий из рассмотренных по переносимости.** По документации Docker:

- macOS 26+ и **только Apple Silicon**;
- Linux — Ubuntu 24.04+, **только x86_64**, с KVM, причём **прямо сказано, что KVM
  требует bare metal и в виртуальной машине не работает**;
- Windows 11, x86_64, с включённым Hypervisor Platform;
- обязателен **аккаунт Docker Hub** (к лицензии Docker Desktop не привязан).

Отсюда следствия, которых мы не учитывали, выбирая бэкенд на этапе 1: офис на `sbx`
нельзя поднять на Linux arm64, на облачной виртуалке и в CI. То есть именно там,
куда его естественно захочется поставить, когда он перестанет быть личным
инструментом.

Аккаунт — вторая половина той же беды: его нельзя запечь в образ, и человеку,
которому офис отдают, придётся заводить учётку Docker прежде, чем что-либо
заработает.

## Три уровня изоляции, и универсальность им обратна

**Микро-ВМ.** Своё ядро на прогон, самая сильная граница. Все упираются в KVM или
Hypervisor.framework, а значит в железо или вложенную виртуализацию: `sbx`,
Firecracker, Kata, [`microsandbox`](https://github.com/superradcompany/microsandbox),
[`matchlock`](https://github.com/jingkaihe/matchlock). Только macOS: Apple
`container` 1.0, `drydock`, `sand`, `bromure`.

**Пользовательское ядро.** gVisor перехватывает сисколлы в userspace: граница слабее
ВМ, но сильнее контейнера; накладные по обзорам 20–50% на I/O-нагрузке. **Только
Linux** — на macOS его нет вовсе.

**Уровень ОС.** Профили Seatbelt на macOS, bubblewrap с seccomp на Linux. Общее ядро,
но **ни виртуализации, ни демона, ни аккаунта**, и потому работает везде, включая
контейнер и облачную виртуалку.

**Контейнер плюс egress-прокси.** Универсально, изоляция контейнерная. Готовых
обвязок этого вида в каталогах десятки.

**Облачные** — E2B (Firecracker), Modal, Beam (gVisor+runc), Daytona (контейнеры;
её открытый репозиторий по обзорам не поддерживается с июня 2026). Отпадают
по существу: офис ведёт разработку клиентского проекта, и отдавать чужой код
в чужую инфраструктуру — отдельное решение, которого никто не принимал.

## Кандидаты, подходящие нам по требованиям

Требования у нас записаны в `DESIGN.md` §2.6 и не абстрактны: сеть по списку доменов
**на прогон**, изоляция от `~/.claude`, кред без утечки в `ps`, песочница на прогон
за секунды.

### `sandbox-runtime` (`srt`), Anthropic

[anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime).
`sandbox-exec` на macOS, bubblewrap с seccomp на Linux, Windows в альфе (отдельная
учётка плюс фильтрация WFP). Обёртка `srt "команда"` накрывает всё дерево процессов.

Сеть: **запрещено всё**, разрешаются названные домены; HTTP и HTTPS идут через
HTTP-прокси, прочий TCP — через SOCKS5. Файлы: чтение по схеме «разрешено, кроме
названного», запись — «запрещено, кроме названного».

Чем ложится на нас почти без зазора: его модель сети — буквально наш `network.allow`
из `role.yaml`; поставщик тот же, что у агента, и `srt` лежит под собственной
песочницей Claude Code — значит, грабля, на которую мы наступили с `sbx` (встроенный
кит не открывает агенту его же API, и авторизация не проходит), у них закрыта
по умолчанию; и **виртуализация не нужна вовсе**, то есть офис становится
переносимым и упаковываемым.

Чего не даёт: это не микро-ВМ, ядро общее. В README названы и границы: трафик
не инспектируется, domain fronting фильтр обходит; слишком широкие права на файлы
дают эскалацию; разрешённый сокет докера отдаёт хост целиком; на Linux есть
ослабленный режим ради совместимости с докером. Статус — research preview,
форматы конфигурации могут меняться.

### `matchlock`

[jingkaihe/matchlock](https://github.com/jingkaihe/matchlock), MIT, v0.2.4, ~612
звёзд, помечен «experimental», основной автор один. Написан на Go — как наш раннер.
Firecracker на Linux, Virtualization.framework на macOS (Apple Silicon); Linux arm64
и macOS на Intel в документации не упомянуты.

Сеть: прозрачный прокси, nftables DNAT на Linux, перехват TCP/IP в userspace через
gVisor на macOS. **Секреты подставляются MITM-прокси на хосте, песочница видит
только плейсхолдер вида `SANDBOX_SECRET_…`** — это сильнее нашей нынешней передачи
токена формой `--env ИМЯ`. Есть Go и Python SDK, поддерживаются OCI-образы.

Самый интересный стратегически и самый рискованный как зависимость: брать 0.2.x
одного автора границей безопасности — ставка, а не решение.

### `microsandbox`

[superradcompany/microsandbox](https://github.com/superradcompany/microsandbox),
Apache 2.0, beta («expect breaking changes»). Микро-ВМ на libkrun. macOS только
Apple Silicon, Linux с KVM, Windows 10+ (x64 и ARM64) с WHP. Allowlist сети
на песочницу, Go SDK, секреты, не попадающие в ВМ, MCP-сервер.

Ближе всех к `sbx` по свойствам и без аккаунта, но то же аппаратное требование —
значит, ту же беду с облачными виртуалками наследует.

## Что это значит для офиса

**Бэкенд — выбор развёртывания, а не архитектуры.** У нас уже есть `backends/local`
и `backends/sbx`, и `DESIGN.md` держит бэкенд подключаемым. Третий — не переписывание
системы, а доиспользование заложенного.

Лестница получается такая:

| Бэкенд | Изоляция | Где работает | Чего требует |
|---|---|---|---|
| `local` | никакой | везде | ничего |
| `srt` | файлы и сеть на уровне ОС | везде, включая контейнер и облачную ВМ | ничего сверх бинарника |
| `sbx` | микро-ВМ | Apple Silicon; Linux x86_64 на железе | аккаунт Docker, KVM |

Упаковку это и чинит: с `srt` внутри контейнера не нужна вложенная виртуализация,
и офис можно отдать образом.

**Порядок работ.** Сначала один замер, и он решает всё: заворачивается ли Claude Code
в `srt` с нашим списком доменов; доживают ли до конца хук `Stop` и ограждение;
не ломает ли bubblewrap запуск **внутри** контейнера — там часто урезаны user
namespaces. Это день. Потом `backends/srt` по образцу `backends/sbx`. `matchlock` —
отдельный спайк, без обязательств.

**Чего замена бэкенда не чинит.** По чек-листу внедрения: 13 квадратиков на машину
и 25 на проект, и почти вся ручная работа во второй половине — инстанс JIRA, поля,
учётки, две половины конфигурации. Бэкенд к ним отношения не имеет. Дешевле всего
здесь `runner init`, и он не зависит от того, чем кончится разговор про изоляцию.

## Предупреждение про сам рынок

Каталоги агентских песочниц сейчас полны проектов возрастом в недели: у большинства
один автор и не указана лицензия. В одном из каталогов проект **прямо помечен как
содержащий сгенерированный ИИ код безопасности с выдуманными номерами версий
и историей коммитов в 48 часов**, с рекомендацией не использовать.

Для границы изоляции происхождение важнее возможностей. Из рассмотренного всерьёз
стоит рассматривать `srt` (Anthropic), `microsandbox` (Apache 2.0) и `matchlock`
(MIT), и последние два — только со спайком.
