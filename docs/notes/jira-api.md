# JIRA REST — что проверено, а что только написано

Целевая версия — **Jira Server 8.13.19**, API **v2**. Всё ниже измерено на полигоне
(`docs/notes/jira-setup.md`), а не взято из документации: там, где документация
и сервер расходятся, прав сервер.

Три источника, как и с `claude`: документация, эмпирика, ответ сервера. Записано
то, что расходилось с ожиданием.

## Чего в REST нет

**Статусы и workflow через REST не создаются.** Ни статуса, ни шага, ни перехода:
в API Server 8.13 таких ручек нет вовсе. Статус заводится формой административной
страницы (`/secure/admin/AddStatus.jspa`), workflow правится только в редакторе.
Это единственная часть настройки полигона, которая не скриптуется.

**Административные формы требуют websudo.** Без «защищённой сессии» Jira отвечает
редиректом на страницу подтверждения пароля, а действие молча не выполняется —
POST возвращает 302 и выглядит успешным. Лечится предварительным
`POST /secure/admin/WebSudoAuthenticate.jspa` с паролем и `atl_token` из cookie.

**`GET /rest/api/2/status` показывает не все статусы.** На полигоне он отдавал
три (`To Do`, `In Progress`, `Done`), тогда как `Ready`, `Review` и `Blocked`
существовали: форма создания отвечала «a status with that name already exists»,
а переходы в них были доступны. Проверять существование статуса этим списком нельзя —
надёжнее спросить переходы конкретной задачи.

## Что скриптуется

**Кастомные поля**: `POST /rest/api/2/field` с `type` и `searcherKey` вида
`com.atlassian.jira.plugin.system.customfieldtypes:datetime` /
`...:datetimerange`. Возвращает готовый `customfield_NNNNN`.

**Экраны**: `POST /rest/api/2/screens/{id}/tabs/{tab}/fields`. Без этого поле
не записать: Jira отвечает «Field cannot be set. It is not on the appropriate
screen, or unknown». Поле, созданное через REST, само на экраны не попадает.

**Учётки**: `POST /rest/api/2/user`.

## Форматы и мелочи, на которых легко ошибиться

**Дата и время** — `2006-01-02T15:04:05.000-0700`: миллисекунды обязательны,
смещение без двоеточия. В этом же виде значение возвращается обратно.

**Числовое кастомное поле приходит числом с плавающей точкой**: `attempts` со
значением 1 читается как `1.0`.

**Очистка поля**: `null` работает; пустая строка тоже попадает под `IS EMPTY`
в JQL — проверено, — но оставляет поле «заполненным пустотой», и глазами это
читается хуже. Раннер пишет `null`.

**JQL по кастомному полю-дате работает** и это главное, на чём держится отбор
кандидатов:

    project = "VO" AND status = "Ready" AND (cf[10003] IS EMPTY OR cf[10003] <= now())

Проверено живьём: задача с живой арендой из выдачи исчезает, после снятия аренды
возвращается. Форма `cf[NNNNN]` предпочтительнее имени поля — имена бывают
неоднозначными.

**Время в `now()` считает сервер, а не раннер.** Поэтому JQL отбирает грубо,
а живость аренды раннер перепроверяет своими часами.

**Идентификаторы переходов зависят и от workflow, и от текущего статуса задачи.**
Держать их в конфигурации — значит однажды соврать: после правки workflow они
поменяются молча. Раннер спрашивает `GET /issue/{key}/transitions` и ищет переход
по имени целевого статуса. Один лишний запрос против конфигурации, которая врёт.

**Автор комментария на Server — `author.name`.** На Cloud там будет `accountId`,
и это первое, что сломается при переносе; отличие записано, но не блокирует.

**Комментарии листаются `startAt`, и первая страница — это начало истории.**
Проверено на тикете со 150 комментариями: `maxResults=100` отдаёт первую сотню,
`total` при этом честно сообщает 150, а `startAt=100` доносит хвост. Раннеру нужен
именно хвост — он отсчитывает от последнего маркера своей роли, — поэтому одной
страницей обойтись нельзя, и трекер крутит их до конца.

Попутно выяснилось, что предположения о пределах сервера были лишними:

- `maxResults=1000` **не режется** — пришли все 150 разом. Наш размер страницы
  в 100 штук выбран нами, а не сервером;
- `orderBy=-created` **работает**: возвращает переписку с конца. Соблазн читать
  назад до первого маркера и на этом останавливаться есть, но это притащило бы
  знание о протоколе маркеров в трекер, которому оно не принадлежит. Пусть лежит
  как запасной ход, если тикеты когда-нибудь вырастут до тысяч комментариев.

## Открытые вопросы
- `pat`-режим авторизации объявлен в конфигурации, но не проверялся: полигон
  ходит по basic-auth.
- Приоритет в сортировке кандидатов (`ORDER BY priority DESC`) на полигоне
  не проверялся — все задачи заводились с одинаковым.
