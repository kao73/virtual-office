# Живая проверка PR-прохода

Шаг 2 этапа 5. Дата — 2026-08-19…20, полигон — приватный репозиторий
`kao73/office-pr-probe`, заведённый ради этой проверки. Трекер файловый
(`--tracker mock`) в отдельном `OFFICE_HOME`, чтобы не задеть полигонные задачи;
forge настоящий.

Проверка шла в два захода. Первый — только сетевой код: задачи заводились сразу
в `Approved`, работу ролей изображали руками. Второй — целиком, живыми агентами:
он понадобился потому, что независимая проверка справедливо не приняла первый
за обещанный маршрут.

## Что прошло, заходом первым (без агентов)

| Шаг | Что сделал офис |
|---|---|
| задача в `Approved` | открыл PR #1, положил ссылку в тикет записью `pr-opened` |
| PR #1 закрыт руками | увёл задачу в `Blocked` с ожиданием человека, запись `pr-closed` |
| ответ человека | вернул задачу в `Approved` штатным unblock |
| следующий проход | открыл PR #2 — **второй, а не тот же**: судится по последней записи семейства |
| холостой проход | второго PR не открыл, дублей в тикет не написал |
| PR #2 слит | увёл задачу в `Done` записью `merged` |
| ветка против ушедшего вперёд `master` | нашёл конфликт локально, вернул задачу в `Ready` записью `merge-conflict`, PR не открыл, попытку не потратил |

## Что прошло, заходом вторым (живыми агентами)

Четыре прогона, $0.79 всего — `implementer` и `reviewer` на двух задачах.
Аналитик не звался: обе задачи заводились в `Ready`.

**PROBE-3 — задача, вернувшаяся с конфликтом.** Агент-разработчик слил
`origin/master` в свою ветку, разрешил конфликт в `shared.txt` и закоммитил
($0.2388). Ревьюер проверил именно слияние — «строка 1 = результат PROBE-3,
строки 2-3 не тронуты, ветка сливается без конфликтов» ($0.2726) — и увёл задачу
в `Approved`. Системный проход открыл PR #3, я слил его за человека, следующий
проход увёл задачу в `Done` и **убрал рабочую папку**.

**PROBE-4 — чистый маршрут без конфликта.** `Ready → InProgress → Review →
Approved` двумя прогонами ($0.1454 и $0.1347), PR #4, слияние, `Done`, папка
убрана.

Каталога изменения у обеих задач не было — они шли мимо аналитика, — и тело PR
собралось из тикета: тема, описание и отчёт разбора.

## Что нашла живая проверка

Четыре дефекта, и все — **во словах**, а не в маршрутах. Маршруты закрывались
тестами с поддельной forge; слова не закрывались ничем.

1. **Маркер отчёта уезжал в тело pull request.** В первом настоящем PR разбор
   начинался строкой `[office run:… role:reviewer outcome:done …]` — служебной
   разметкой раннера в тексте, который читают люди. Починено `WithoutMarker`.
2. **Запись о конфликте обещала открытый pull request, которого не было.**
   Конфликт бывает найден и до открытия — тогда «PR остаётся открытым
   и подхватит задачу» было враньём.
3. **Подсказка `--tracker` человеку по-прежнему говорила «(mock)».** Строка
   у флага была поправлена, а печатается не она, а баннер в `main.go`.
4. **Тело PR у задачи без каталога изменения теряло тему тикета**: уходило одно
   описание.

Первые два нашёл живой GitHub, третий и четвёртый — независимый проверяющий.
Все четыре закрыты тестами.

Отдельно — контракт `docs/contracts/tracker-protocol.md`. Он утверждал неправду
в четырёх местах: «`Backlog` и `Done` человеческие, офис их не читает и в них
не пишет»; «у ревьюера маршрут по умолчанию — терминал, рабочая папка снесена»;
весь раздел «Конец жизни задачи», описывавший снос папки прогоном; и определение
ключа `terminal`. Все четыре исправлены. Правка контрактов целиком объявлена
шагом 3 — здесь поправлено только то, что этот шаг сделал ложным.

Четвёртое место нашлось не сразу: сплошной поиск шёл по слову «терминальный»,
а там ключ назван латиницей — `terminal`. Это и есть рабочая форма всей серии:
одно утверждение живёт в нескольких видах, и поиск по одному из них находит
не все.

## Чего эта проверка не покрыла

- **Отказ GitHub на ветке без коммитов** (422 `No commits between…`). Офис
  до GitHub в этом случае не доходит: «сливать нечего» он видит локально,
  по `rev-list`. Разбор самого отказа проверен поддельным сервером
  в `forge/forge_test.go`.
- **Ключи `tracker` и `forge`** остались в `projects.yaml`, хотя оба машинные
  по природе. Шаг «конфигурация по машинам» отложен владельцем до момента перед
  шагом 5, и перенос обоих ключей войдёт в него.
  **Закрыто там же:** оба ключа уехали в `${OFFICE_HOME}/projects.local.yaml`
  вместе с `repo_url` и `worktree_root`, см. `stage-5-config.md`.
- **Грязная рабочая папка** живьём не встречалась: обе задачи закончились
  чистыми. Пропуск грязной папки проверен тестом конвейера.

## Как повторить

```sh
eval "$(grep -hE '^ *export +CLAUDE_CODE_OAUTH_TOKEN=' ~/.zshrc)"   # кред агента
export GITHUB_TOKEN=$(gh auth token)                                 # forge
export OFFICE_HOME=/tmp/probe-home                                   # своё хозяйство
# в projects.yaml — имя проекта и ветки; в ${OFFICE_HOME}/projects.local.yaml —
# его repo_url, tracker: mock и forge: github (раскладка появилась шагом позже,
# см. stage-5-config.md)
./bin/runner mock add PROBE-1 --status Ready --summary "…" --description "…"
./bin/runner tick --tracker mock --role implementer
./bin/runner tick --tracker mock --role reviewer
./bin/runner tick --tracker mock --role reviewer   # системный проход откроет PR
```

Сеть песочницы для этого открывать не нужно: `default-deny-all` — штатный режим
офиса, домены роли открывает раннер по её `role.yaml`.

Проект `PROBE` в `projects.yaml` не остался, и это не забывчивость: любая команда
раннера падает при сборке офиса без `GITHUB_TOKEN`, если `forge` задан у проекта
**выбранного** трекера, — а полигонам токен не нужен. Первым постоянным проектом с forge станет
`expense-tracker` на шаге 5.
