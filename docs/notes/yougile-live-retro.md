## Находки и follow-up

1. **Конвейер оставляет рабочую папку после Done.** Не зависит от трекера.
   - *Как проявилось:* на T1, C1 и C2 после слияния раннер каждый тик пишет
     «задача закончена, но в папке 1 незакоммиченных путей — оставляю,
     убирать руками (`runner worktree rm --force`)».
   - *Какой путь:* везде один и тот же — ` D .comet/current-change.json`.
   - *Причина:* `comet native archive --confirmed` удаляет файл выбора
     изменения, а `commitArchiveRename` (`internal/pipeline/archive.go`)
     коммитит только `cometArchiveScope` — родителя `docs/comet/changes`.
     Удаление вне этого scope остаётся незакоммиченным, и уборка рабочей
     папки отказывает.
   - *Где не проявилось:* на T2b — там изменение Comet не заводилось.
   - *Follow-up:* change против capability архивирования в конвейере
     (`pipeline-archive-*`): коммитить и удаление
     `.comet/current-change.json`, либо не считать его препятствием для
     уборки. Вероятно, воспроизводится и на JIRA — проверить там.
2. **Сбой скачивания вложения оставляет аренду без следа.** Подтверждение
   пункта, отложенного в PR #25.
   - *Что происходит:* `fetchAttachments` возвращает ошибку после `claim()`,
     тик выходит с кодом 2.
   - *Что видно снаружи:* аренда живёт до `lease_until`, записи в ledger
     нет, комментария нет, карточка не двигается. Человек в интерфейсе не
     видит ничего.
   - *Follow-up:* уже намеченный отдельный change «сбой скачивания вложения
     → вопрос человеку» (из `yougile-dependencies-attachments`, PR #25).
     Добавить к нему: освобождать аренду при этой ошибке.
3. **`runner ls` на чтение требует токен форджа.** Раннер с проектом
   `forge: github` без `GITHUB_TOKEN` отказывается целиком, код 2, даже
   для `ls`. Мелкое неудобство для оператора. Кандидат в follow-up по
   раннеру: для команд на чтение — предупреждение вместо отказа.
4. **Ключ задачи — UUID YouGile.** Ветки выглядят как
   `agent/f8978e23-9fd9-4be2-9690-9ef4b1788a6f`, заголовки PR начинаются с
   UUID. Человекочитаемый `idTaskProject` (`OFF1-1`) раннер не использует.
   Это решение change 1 (`yougile-adapter-core`), а не дефект. Длинные ветки
   читать неудобно — кандидат на обсуждение, не на исправление.
5. **Роль учётки видна не-админу (P2).** Разблокирует отложенный из PR #26
   пункт: `doctor` проверяет роль учётки офиса и предупреждает об
   `observer`. Follow-up против `yougile-wiring-and-docs` (capability
   `doctor`).
6. **Идемпотентность `complete-splits` живьём не доказана.** Второй проход
   пришёлся на уже закрытого родителя. Если нужно доказательство —
   отдельный опыт: оборвать `complete-splits` между созданием детей и
   переводом родителя в Done. Изменения кода это не требует.
7. **Файловый хост YouGile — отдельный IP.** `prod-user-data.yougile.com`
   (`111.88.104.34`) нужно отдельно добавлять в исключения split tunneling
   рядом с `yougile.com`. Это запись для окружения этой машины; в
   `docs/reference/yougile-requirements.md` стоит одна строка о том, что
   вложения идут с другого хоста.

Структурных дефектов адаптера `internal/tracker/yougile` не найдено: ни один
пункт не требует возвращаться в `yougile-adapter-core` или
`yougile-dependencies-attachments` с правкой кода. Пункты 1–3 касаются
конвейера и раннера, а не трекера.
