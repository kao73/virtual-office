# Живая проверка трекера YouGile — `office-wiring` / `kao73/office-pr-probe` (2026-09-30)

Итог change `yougile-live-validation`, последнего в батче `yougile-tracker-adapter`.
Офис прогнан против настоящего API YouGile настоящими ролями:

- **полигон:** проект `office-wiring`, ключ раннера `YGW`;
- **репозиторий:** `kao73/office-pr-probe`;
- **человек:** `kao@uplinesoft.com`;
- **учётка офиса:** `kao@simbirsoft.com`.

Задача была не в проверке адаптера тестами, а в том, чтобы увидеть, как задача
живьём проходит граф. Адаптер кода в этом change не получил.

Дизайн — `docs/superpowers/specs/2026-09-30-yougile-live-validation-design.md`,
план — `docs/superpowers/plans/2026-09-30-yougile-live-validation.md`. Сырой
журнал доказательств лежит вне репозитория, в

## Находки и follow-up

1. **Архивирование оставляет устаревший `.comet/current-change.json` на ветке,
   а после слияния — в `master` клиента.** Не зависит от трекера.
   - *Главное следствие:* удаление файла выбора изменения не коммитится, ветка
     задачи уезжает в PR с прежним файлом. После слияния в `master`
     `office-pr-probe` лежит `.comet/current-change.json` с
     `"change": "roster-cli"` — уже заархивированным изменением. Любая
     следующая задача, ответвлённая от `master`, наследует чужой выбор. А
     `archiveIfReady` берёт имя изменения прежде всего из этого файла
     (`runner.CurrentChangeName`, `internal/pipeline/archive.go:110`).
   - *Второе следствие:* на T1, C1 и C2 после слияния раннер каждый тик пишет
     «задача закончена, но в папке 1 незакоммиченных путей — оставляю,
     убирать руками (`runner worktree rm --force`)». Путь везде один:
     ` D .comet/current-change.json`, рабочие папки не убираются.
   - *Причина:* `comet native archive --confirmed` удаляет файл выбора, а
     `commitArchiveRename` коммитит только `cometArchiveScope` — `docs/comet`
     (`archive.go:262–284`). Удаление вне этого пути остаётся в рабочем дереве.
     Комментарий у `cometArchiveScope`, что это единственный путь, живой
     прогон опровергает.
   - *Где не проявилось:* на T2b — там изменение Comet не заводилось.
   - *Capability:* `role-native-workflow`. Корень — в change, который ввёл
     `archiveIfReady` (шаг архивирования в PR-проходе), а не в батче YouGile.
   - *Второй заход той же причины:* `archive.go:110–113` берёт имя из файла
     выбора и не проверяет, что каталог изменения существует. Путь чтения
     контекста это проверяет (`internal/runner/input.go:301–305`). С выбором,
     унаследованным из `master`, `archiveIfReady` спросит
     `comet native status` о чужом, уже заархивированном изменении.
   - *Follow-up:* `pipeline-archive-selection-commit`:
     - коммитить удаление `.comet/current-change.json` вместе с
       переименованием;
     - в `archiveIfReady` принимать имя из файла выбора, только если каталог
       изменения существует, как в `input.go`;
     - поправить комментарий у `cometArchiveScope`.

     Шаг архивирования живёт в `internal/pipeline`, трекер в нём не
     участвует, поэтому повторять проверку на JIRA незачем. Проверять стоит
     другой режим `isolation` Comet.
2. **Сбой скачивания вложения оставляет аренду без следа.** Подтверждение
   пункта, отложенного в PR #25.
   - *Что происходит:* `fetchAttachments` возвращает ошибку после `claim()`
     (`internal/pipeline/pipeline.go:485`), тик выходит с кодом 2.
   - *Форма шире вложений:* так же устроены все шаги `work()` между захватом
     и стартом агента — `Tracker.Get` (`:464`), `HeadCommit` (`:477`),
     `PrepareInput` (`:496`). Любая их ошибка возвращается из `work()`, а
     `defer` снимает только замок рабочей папки. `Tracker.Release` на этом
     пути не зовётся. Живьём сработал один из четырёх выходов.
   - *Что видно снаружи:* аренда живёт до `lease_until`, записи в ledger нет,
     комментария нет, карточка не двигается. Человек в интерфейсе не видит
     ничего.
   - *Capability:* `ticket-attachment-visibility`; тянется из
     `yougile-dependencies-attachments` (PR #25).
   - *Follow-up:* `attachment-fetch-failure-release`:
     - общее правило: ошибка подготовки после захвата снимает аренду и
       оставляет видимый след (запись в ledger, комментарий);
     - вложения — повод, а не граница;
     - сюда же уже намеченный change «сбой скачивания вложения → вопрос
       человеку».
3. **`runner ls` на чтение требует токен форджа.** Раннер с проектом
   `forge: github` без `GITHUB_TOKEN` отказывается целиком, код 2, даже для
   `ls`. Мелкое неудобство для оператора.
   - *Capability:* `config-boundary`.
   - *Где отказ:* не в `ls`, а в общем конструкторе:
     `cmd/runner/board.go:24` → `newOffices` → `forgesOf`
     (`cmd/runner/office.go:271`) → `forge.NewGitHub`
     (`internal/forge/github.go:52`). Ранний отказ там сделан нарочно: узнать
     об отсутствующем токене посреди прохода поздно (`office.go:266–267`).
   - *Follow-up:* `runner-readonly-without-forge-token` — `newOffices` должен
     различать команды: для команд на чтение предупреждение вместо отказа.
     Для `tick` и PR-прохода ранний отказ остаётся, проверку не убирать.
4. **Ключ задачи — UUID YouGile.** Ветки выглядят как
   `agent/f8978e23-9fd9-4be2-9690-9ef4b1788a6f`, заголовки PR начинаются с
   UUID. Человекочитаемый `idTaskProject` (`OFF1-1`) раннер не использует как
   ключ задачи: ни в ветках, ни в заголовках PR, ни в `ls`. Он виден только в
   заметке о зависимости (`internal/tracker/yougile/depends.go:53`).
   - Это решение `yougile-adapter-core` (capability `tracker-yougile`), а не
     дефект.
   - Design Doc этого change ошибочно ждал ветки `agent/YGW-*`. На то же
     опиралось его «ветки не столкнутся со старыми»: не столкнулись, но по
     другой причине.
   - Длинные ветки читать неудобно — кандидат на обсуждение, не на
     исправление.
5. **Роль учётки видна не-админу (P2).** Разблокирует отложенный из PR #26
   пункт.
   - *Capability:* `office-doctor`; тянется из `yougile-wiring-and-docs`.
   - *Follow-up:* `doctor-yougile-role-check` — `doctor` читает роль учётки
     офиса и предупреждает об `observer`.
6. **Идемпотентность `complete-splits` живьём не доказана.** Второй проход
   пришёлся на уже закрытого родителя. Если доказательство нужно — отдельный
   опыт: оборвать `complete-splits` между созданием детей и переводом
   родителя в Done. Кода это не требует.
7. **Файловый хост YouGile — отдельный IP.** `prod-user-data.yougile.com`
   (`111.88.104.34`) нужно отдельно добавлять в исключения split tunneling
   рядом с `yougile.com`. Это запись для окружения этой машины.
   `docs/reference/yougile-requirements.md` уже называет
   `prod-user-data.yougile.com`, но только как причину отказа от
   `ru.yougile.com`. Как сетевое требование («машине раннера нужен доступ к
   обоим хостам») он там не записан — стоит добавить одну строку.

Структурных дефектов адаптера `internal/tracker/yougile` не найдено: ни один
пункт не требует правки кода в `yougile-adapter-core` или
`yougile-dependencies-attachments`. Пункты 1–3 касаются конвейера и раннера,
а не трекера. Предложения follow-up переданы владельцу; ни одно ещё не
открыто.

## Отступления от дизайна

Design Doc (`2026-09-30-yougile-live-validation-design.md`) расходится с тем,
как прогон шёл на деле:

- **§3 P3, «чисто на пустой доске»:** не показано. К первому успешному
  `runner ls` T1 уже была заведена (раздел P1–P3).
- **§4 «Recorded at each step», число запросов к лимиту 50/мин:** не
  записано. Зафиксировано только отсутствие `429` (раздел «Расход»).
- **§4, `runner tick --tracker yougile`:** флага `--tracker` у `tick` нет —
  трекеры раннер берёт из `projects.local.yaml`. Все тики шли как
  `./bin/runner tick`.
- **§2, `projects.local.yaml`:** для PR-прохода нужен `forge: github`. Без
  него задача уходит в Done без PR (`pr-skipped`).
- **§1, §4 и §6, ветки `agent/YGW-*`:** на деле ветки `agent/<uuid>` (находка 4).
- **§4 шаг 6, «убирает worktree»:** не убирает (находка 1).
- **§4, ответ человека и отрицательный контроль на T1:** `analyst` на T1
  вопроса не задал. Обе проверки прошли на T2b, на вопросе-подтверждении
  разбиения.
- **§5, T2:** `analyst` не разбил T2. Разбиение проверено на T2b с
  постановкой, где две возможности названы прямо.
- **§5 шаг 3, дедупликация через `idempotencyKey`:** условие прохода не
  выполнено. Второй `complete-splits` пришёлся на закрытого родителя
  (находка 6).
- **§5 шаг 4, дети в Ready:** дети переведены в Analysis. Гейт стоит в
  `claim()` для всех ролей, и дети прошли обычный Shape у `analyst`.
- **§5 шаг 6, C2 необязательна:** доведена до Done по решению владельца.
