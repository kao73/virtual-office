# Задание на доработку: права ролей и сеть песочниц

Записано по итогам разбора живого прогона `role-companions` (ветка
`comet/role-companions`, 2026-08-26/27) перед откатом на `master`. Ветка
с реализацией компаньона (`tasks.md` 1–4, частично 5) остаётся в git —
код самой фичи эти находки не отменяют, откатывается только текущая
попытка живого прогона Задачи 17, чтобы переиграть её после доработки
подхода.

## Зачем это писалось

Эксперимент: прогнать задачу на `EXP` (реальный проект,
`kao73/expense-tracker`) через `sbx`-бэкенд и проверить, решает ли фича
`companion` проблему, найденную в EXP-1 (роль не могла поднять тестовую
БД). Живой прогон Задачи 17 упёрся в `403 Forbidden` при `docker pull`
внутри песочницы. Расследование этого сбоя вскрыло два отдельных
вопроса шире, чем сама Задача 17, — про сеть песочниц и про права ролей
на Bash. Их и фиксирует этот файл.

## Находка 1: Docker внутри `sbx` работает — упёрлись не в него

Ранее (по мотивам EXP-1) считалось, что Docker внутри `sbx`-песочницы
недоступен или ненадёжен, и что `office-companion`, возможно, стоило
проектировать как внешний сервис вне песочницы, к которому роль
подключается снаружи.

Проверено заново (2026-08-27) на чистой одноразовой песочнице
(`sbx create claude ...`, образ `docker/sandbox-templates:claude-code-docker`):

- Docker CLI и демон внутри песочницы уже есть и работают из коробки;
  пользователь `agent` состоит в группе `docker`; `docker info` сразу
  отвечает живым сервером.
- `docker pull hello-world` без всякой сетевой политики падает ровно
  той же ошибкой, что и в живом прогоне: `403 Forbidden` от
  `registry-1.docker.io`. Это воспроизводимо и не специфично для EXP.
- После `sbx policy allow network --sandbox <name> registry-1.docker.io,auth.docker.io,*.docker.io`
  манифест резолвится, но скачивание самих слоёв падает на **другом**
  хосте — `production.cloudfront.docker.com` (CDN раздачи blob'ов,
  не `cloudflare.docker.com`, как можно было бы предположить по
  аналогии).
- После разрешения и этого хоста прошёл полный цикл: `docker pull`,
  `docker run --rm hello-world`, и `docker compose up -d --wait` +
  `pg_isready` healthcheck + `docker compose down` на `postgres:16-alpine`
  — без единой ошибки.

**Вывод:** архитектура `office-companion` (роль сама вызывает бинарник
внутри своей же песочницы, раннер ничего не поднимает заранее —
proposal.md, design.md, решение №2/№3) пересмотра не требует. Причина
сегодняшнего сбоя — сетевая политика песочницы, а не размещение
компаньона. Переделывать на «внешний Docker снаружи песочницы» не нужно.

## Находка 2: `permissions.allow` в Claude Code не ограничивает Bash

Отдельно, при разборе прежнего прогона обнаружено и подтверждено
(идентично на голом хосте и внутри `sbx`): в режиме
`--permission-mode dontAsk` поле `permissions.allow` в `settings.json`
**не является техническим ограничением** на вызов Bash — команду,
которую не матчит ни один `allow`, ни один `deny`, модель выполняет или
не выполняет по собственному суждению, а не по детерминированной
проверке рантайма. Реально ограничивает только `permissions.deny`.

Это касается **всего проекта**, а не только `role-companions`: списки
`tools.allow` в `roles/*/role.yaml` в текущем виде — не настоящая
защита, а скорее документация намерения. Это прямо противоречит
комментарию в `adapters/claude/adapter.go:187`.

## Решения по итогам разговора (2026-08-26/27)

**Права на инструменты (Bash).** Раз `allow`-списки и так не дают
реальной защиты, ограничивать ими нечего — договорились расширить их
максимально (снять искусственные рамки на первых порах, отлаживать
разработку, вернуться к ограничениям точечно и по необходимости).
Это общепроектное решение, шире `role-companions` — отдельная задача:
- пройтись по `roles/*/role.yaml` и расширить `tools.allow`;
- поправить неверный комментарий в `adapters/claude/adapter.go:187`;
- решить, нужен ли вообще `permissions.deny` для по-настоящему опасных
  команд (единственное, что реально работает), или на данном этапе
  сознательно оставить и это открытым.

**Сеть песочниц.** В отличие от Bash-прав, deny-by-default в `sbx` —
настоящая, принудительная на уровне песочницы граница (защищает секреты
и Docker-сокет внутри неё), поэтому открывать её целиком не стоит. Но
затраты на «узнать, куда роли понадобится сходить» по одному разу на
каждый новый проект — реальная и растущая работа, тем более что
запросы разных проектов пересекаются (Docker Hub, пакетные реестры,
GitHub — общие для почти любого клиентского проекта). Решение: завести
**один общий базовый список** доменов для типовых нужд разработчика,
разрешённый по умолчанию во всех песочницах, и оставить per-project
конфиг только под нестандартное (внутренние сервисы клиента, приватные
реестры).
