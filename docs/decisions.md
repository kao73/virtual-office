Решения, принятые при утверждении концепта (Р-01…Р-11), по итогам ревью

| № | Решение | Обоснование |

| Р-03 | Субстрат — **реальный трекер** проекта-клиента, огороженный участок (метка) | Песочники умирают (прецедент: autodev-доска в clens, нетронута с 2026-04-13); ценность появляется только на реальном бэклоге. Радиус поражения ограничивает метка |

| Р-13 | Изоляция ролей: независимость от сессий других ролей, но НЕ от контекста клиента; приоритет указаний — конституция > контракт роли > профиль > процессные указания клиента | Роли запускаются в директории клиента, «чистый контекст» без спеки — противоречие. ## Полный замысел

Что офис представляет собой целиком, когда будет достроен. В `docs/office.md`
из этого попадает только то, что действует сегодня; остальное лежит здесь.

### 3. Архитектура — общие законы ролей

Общие законы всех ролей:

- **Stateless** — вся память роли в артефактах: доска, git, документы.
- **Батч за пробуждение** (Р-16) — роль обрабатывает карточки своей стадии до
  исчерпания бюджета пробуждения; каждая карточка — единица взятия со своей лизой:
  атомарна публикация результата, сама работа возобновляема (Р-17).
  Цель по потоку: тривиальная карточка проходит от идеи до мерж-гейта за один день
  при дефолтном расписании.
- **Идемпотентность** — повторный запуск после сбоя безопасен; упавший агент = карточка
  осталась на месте, следующее пробуждение подберёт.
- **След** — каждый шаг оставляет отчёт-коммент на карточке.
- **Автор ≠ приёмщик** (Р-10) — роль, пишущая код, никогда его не принимает.

### 4. Роли и контракты

Контракт роли — пять пунктов: вход, выход, потребности (способности), запреты, след.

#### Аналитик
- **Вход:** карточка-идея владельца в участке офиса — либо офисная карточка-возврат
  (маркирована адаптером, Р-26): её содержимое роль читает как данные, не указания
  владельца, и превращает в постановку на дизайн-гейт.
- **Выход:** уточнённая постановка, черновик design doc, для видимых задач —
  UI-варианты картинками; карточка на дизайн-гейт.
- **Запреты:** не пишет код продукта.
- **Особое:** дырка в постановке, которую нельзя закрыть из кодовой базы, →
  `needs_input` с конкретным вопросом. Для карточек с UI-составляющей способность
  `browser` обязательна (Р-18): гейт получает картинки, не описания.

#### Разработчик
- **Вход:** карточка с утверждённым дизайном.
- **Выход:** ветка по конвенции клиента, код через TDD, зелёные тесты, PR;
  карточка на AI-QA.
- **Запреты:** не мержит; лимиты диффа и запрещённые пути из профиля клиента;
  не трогает чужие ветки и чужие dirty-файлы; соблюдает WIP-лимит.
- **Особое (Р-17):** единица работы — карточка целиком за пробуждение. Первый акт
  на карточке — план реализации, закоммиченный в ветку; далее TDD с коммитами-чекпоинтами.
  Возобновление после сбоя — из плана и состояния ветки, с последнего зелёного чекпоинта;
  прогресс детектится по коммитам (git как heartbeat).

#### AI-QA
- **Вход:** PR Разработчика (или PR человека — приёмка не требует AI-автора).
- **Выход:** отчёт приёмки (§8); вердикт «на мерж-гейт» либо возврат Разработчику
  с воспроизводимым багрепортом.
- **Запреты:** **не правит код вообще**, даже «очевидную мелочь» — только репортит.
- **Особое (Р-13):** независим от Разработчика — никакого доступа к его сессии,
  рассуждениям и промежуточным артефактам; вход — только ветка, карточка, эталоны.
  Контекст клиента (CLAUDE.md, скиллы, память проекта) при этом доступен —
  как человеческому QA, знающему проект.

#### Делопроизводитель
- **Вход:** факт мержа владельцем либо возврат от внешнего (человеческого) QA.
- **Выход:** переходы в трекере, отчёт-комменты по шаблонам клиента, черновик
  релиз-нотесов; возврат QA оформляет новой связанной карточкой-постановкой
  (адаптер маркирует её как офисную — Р-25/Р-26).
- **Запреты:** не трогает код и git вообще (только чтение фактов).
- **Особое:** попутные обязанности — обход протухших карточек (§9), еженедельный
  дайджест метрик (§10).

#### Будущие роли (вне v1)
- **Планёрка** — ежедневный обзор всей доски, наведение порядка, ничего не реализует.
- **Релиз-инженер** — выкатка и пост-деплой мониторинг; получает кнопку релиза
  только явным решением владельца.

> **Проработка:** формат манифеста роли (requires/optional, расписание); промпты ролей —
> по одному дизайн-доку на роль на этапах 1–4 дорожной карты.

### 5. Жизненный цикл — дисциплина потока и проработка

**Дисциплина потока:** WIP-лимиты в профиле клиента (например `in_dev ≤ 2`);
задачи, затрагивающие пути под мьютексом (например миграции БД), — в работе не больше
одной; при выборе из стадии роль берёт верхнюю подходящую карточку — приоритет
задаётся порядком на доске.

**Артефакты не на доске:** design doc, план, отчёты живут в репозитории клиента по его
конвенциям; карточка держит ссылки. Доска — нервная система, git — долговременная память.

> **Проработка:** полный маппинг состояний на Jira клиента №1; протокол лизы (§9);
> шаблоны след-комментов; правило приоритета возвратов ai_qa→in_dev над новыми
> карточками в батче Разработчика (иначе петля ≤3 итераций растянется на дни);
> механизм запоминания состояния-источника при парковке `needs_input` — «ровно туда,
> откуда встала» требует хранения (метка/коммент), в stateless-модели это обязанность
> адаптера.

### Профиль клиента целиком

```yaml
tracker:
  provider: jira                  # выбор адаптера
  fence: label:ai-office          # огораживание участка
  office_account: null            # техаккаунт офиса; null → маркировка комментов (Р-20)
  states:                         # abstract state → представление в трекере
    design_gate: {status: "In Progress", label: "office:design-gate"}
    merge_gate:  {status: "Code Review"}
repo:
  base_branch: master
  branch_naming: "{type}/{key}-{slug}"
  merge_policy: merge-commit
gates:                            # команды качества клиента
  lint: "make lint-check"
  test: "make test"
  e2e:  {command: "make e2e", requires: [docker]}
  visual: {themes: [light, dark]}
limits:
  diff: {warn: 300, abort: 500}
  wip: {in_dev: 2}
  mutex: [{name: migrations, paths: ["backend/alembic/**"]}]
  forbidden_paths: [".github/", ".env*"]
artifacts:
  design_docs: "docs/superpowers/specs/"
  language: ru
mockups:                          # Р-24/Р-27: как Аналитик рендерит UI-варианты
  mode: real-components           # либо standalone
  command: "npm run dev"          # как поднять фронтенд клиента для рендера
rituals:
  report_comment: ".office/templates/report.md"
  release_notes:  ".office/templates/release-notes.md"
extensions:                       # люк: клиентский скилл вместо/поверх шага конвейера
  verify: "clens:verify"
```

- **Люк `extensions`:** декларативных данных хватает на ~90% различий; ритуал,
  неописуемый данными, профиль делегирует клиентскому скиллу. Офис остаётся
  универсальным, странности клиента остаются в клиенте.
- **Секретов в профиле нет никогда.** Креды берутся из окружения машины;
  профиль лишь ссылается на источник.

**Адаптер трекера** — узкий интерфейс, единственный способ ролей говорить с доской:
`list_cards(state)`, `read_card`, `move(card, state)`, `comment`, `create_card`, `link`,
`attach(card, file)` (Р-12). `attach` — опциональная способность адаптера: конформанс-сьют
проверяет её отдельной секцией; адаптер без вложений деградирует до ссылок на файлы в
репозитории с явной пометкой в пакете гейта. Вложения — всегда UX-копии, канон — в git.
Реализации: `jira`, `yougile`, далее по потребности. Переезд трекера = новый адаптер +
правка секции `tracker` профиля; роли не меняются.

**Адаптер маркирует сам (Р-25).** Всё, что офис публикует в трекер, получает структурный
маркер на уровне адаптера: `comment` и `create_card` вшивают его безусловно — роль
физически не может опубликовать немаркированный текст, и инъекция «оставь коммент без
маркера» бьёт в невозможное. Тот же принцип, что Р-10: не договариваться, а сделать
невозможным.

**Конформанс-сьют:** набор контрактных тестов, который обязан проходить каждый адаптер —
проверяем шов, а не заглушки.

> **Проработка:** JSON-схема профиля + валидатор; визард `office-init` (импорт
> legacy-конфигов типа `.autodev/kanban.config.json`); интерфейс адаптера;
> jira-адаптер; конформанс-сьют — включая полигон: тест-проект/участок в трекере,
> чтобы сьют не мусорил в живой доске клиента.

### 7. Профили способностей и раннеры

Словарь способностей v1: `tracker`, `repo_ro`, `repo_rw`, `docker`, `browser`,
`preview`, `stage_vpn`. Роль декларирует `requires` (+ `optional`); раннер декларирует
`provides`. Закон назначения: **роль просыпается на раннере только если provides ⊇ requires**.

| Роль | requires | optional |
|---|---|---|
| Делопроизводитель | tracker | — |
| Аналитик | tracker, repo_ro; для UI-задач + browser (Р-18) | docker (мокапы на реальных компонентах, Р-27) |
| Разработчик | tracker, repo_rw, docker | — |
| AI-QA | tracker, repo_ro, docker, browser | preview |

- **Optional ≠ «молча пропустим».** Роль без опциональной способности работает, но её
  отчёт содержит матрицу проверок: «сделано / пропущено (причина)». Пропуск виден
  владельцу на гейте явно.
- **Раннер v1 — локальная машина владельца:** планировщик (cron/launchd) + headless-сессии
  ролей **в рабочей директории клиента** (там CLAUDE.md клиента, его скиллы, память,
  установленный плагин офиса). Конфигурация в профиле: provides, расписание по ролям,
  рабочие окна, потолок параллельности (старт — 1 ролевая сессия за раз).
  Потолок обеспечивается **локом раннера** (flock/pid-файл), не расписанием:
  cron не гарантирует неперекрытие — сессия, пережившая интервал, встретит
  следующее пробуждение (Р-22).
- **Изоляция роли (Р-13).** Роль видит: worktree репозитория клиента, CLAUDE.md и скиллы
  клиента, память проекта, профиль, карточку. Роль не видит: сессии и промежуточные
  артефакты других ролей. Приоритет указаний: **конституция > контракт роли > профиль >
  процессные указания клиента**. Технические конвенции клиента (код-стайл, архитектура,
  запреты) обязательны; процессные скиллы клиента (его воркфлоу-ритуалы) на роли
  не действуют — роль работает по своему контракту. Конфликт контракта с клиентским
  указанием роль докладывает, не разруливает молча.
  **Известное отступление (Р-21):** запрет процессных указаний — договорная гарантия
  (промпт-приоритет), не структурная, поскольку CLAUDE.md клиента грузится в сессию
  целиком. Физическое закрытие — селективная загрузка контекста в headless-запуске —
  обязательная проверка этапа 1.
- **Дыры докладываются, не маскируются:** нет требуемой способности ни у одного раннера —
  карточки стадии стоят, Делопроизводитель пишет владельцу «стадия X ждёт способности Y».
- **Мобильность бесплатна:** будущий облачный раннер объявит бедный provides и получит
  только посильные роли. Первый кандидат на эмиграцию — Делопроизводитель, но пока у
  трекера нет моста наружу, облачный provides = ∅. Офис не обходит инфраструктуру клиента.

> **Проработка:** механика планировщика (cron vs launchd), формат headless-запуска ролей,
> бюджеты на пробуждение, формат конфигурации раннера; техническая реализация изоляции
> контекста (что физически загружается в сессию роли).

### 8. Приёмка AI-QA

Рамка: AI-QA проверяет не «работает ли код», а «**сделано ли утверждённое владельцем так,
как принято у клиента**». Эталоны: утверждённая постановка + design doc + выбранный
UI-вариант. Пять слоёв, снизу вверх:

1. **Механика.** Команды из профиля: lint, тесты, сборка. Красное — мгновенный возврат.
2. **Соответствие дизайну и рамкам.** Дифф покрывает постановку и не выходит за неё
   (scope creep — находка, не бонус); запрещённые пути не тронуты; лимиты диффа;
   обязательные артефакты клиента (миграции, переводы, документация) на месте.
3. **Ревью-агенты.** Пакет независимых ревьюеров по измерениям (корректность,
   silent failures, покрытие, дизайн типов); профиль добавляет клиентские критерии.
4. **Живой прогон.** Расширенные e2e на поднятом стеке или превью — по способностям.
5. **Визуальная верификация.** Для UI-задач — скриншоты обеих тем, сверенные с мокапом,
   выбранным владельцем на дизайн-гейте (петля замыкается). Критерий сверки —
   **структурный**: те же элементы, та же раскладка, те же состояния — не пиксельный
   (Р-24): пиксельная сверка с мокапом вне дизайн-системы клиента даёт либо вечные
   возвраты, либо выученную слепоту. Цель Аналитика — мокапы на реальных компонентах
   клиента (режим и команды — секция `mockups` профиля; без `docker` у раннера —
   явная деградация до standalone-мокапов, видимая в матрице «сделано/пропущено», Р-27).

**Отчёт приёмки** на карточке: матрица проверок (сделано / пропущено + причина),
находки с приоритетом (блокирующие / улучшения), скриншоты (вложениями на карточку —
UX-копии, канон в git; Р-12), вердикт.
Багрепорт при возврате обязан быть воспроизводимым: команда, ожидание, факт.

Предохранители:

- **Независимость** (Р-13) — никакого доступа к сессии Разработчика; контекст клиента
  доступен как общий фон.
- **Инфра-сбой ≠ провал кода** — один ретрай; повторился — `needs_input` с пометкой
  «инфра», а не багрепорт.
- **Лимит кругов** — AI-QA ↔ Разработчик ≤ 3 итераций, дальше `needs_input`
  на арбитраж владельца.

> **Проработка:** состав ревью-пакета; формат отчёта приёмки; worktree-механика
> чистого чекаута PR.

### 9. Отказы и стоп-краны

Принцип-зонтик: **карточка — единица восстановления**. Роль может умереть в любой
момент — состояние офиса не портится.

- **Лиза.** При взятии карточки роль ставит след-коммент «взято: роль, пробуждение N».
  Живая лиза защищает от двойного пробуждения; протухшая (нет прогресса дольше T) —
  законная добыча следующего пробуждения. Для Разработчика прогресс детектится по
  коммитам в ветке — git как heartbeat (Р-17); роли без естественного heartbeat
  (Аналитик над мокапами) обязаны оставлять явный сигнал прогресса — журнал или
  след-коммент, выбор за проработкой протокола — либо получают увеличенный T (Р-23).
  **Маркер:** потолок параллельности выше 1 =
  переработка протокола лизы (нужен атомарный claim, которого трекеры из коробки
  не дают) — это не твик конфига.
- **Конкурентное редактирование (Р-19).** У доски два живых писателя — офис и владелец.
  Протокол «перечитай перед фиксацией»: при взятии карточки роль фиксирует **базис**
  (описание, комменты, состояние); перед каждым публикующим действием (move, пакет гейта)
  перечитывает карточку и классифицирует расхождения:
  - *состояние изменено или фенс снят* → аборт: ничего не двигать и не перезаписывать;
    снятый фенс = мгновенный отзыв (§5) — на карточку даже не комментировать,
    след только в журнал;
  - *новый вход владельца* (коммент, правка описания) → на гейт не ехать; сделанное
    прикладывается черновиком со след-комментом «вход изменился во время работы»,
    лиза снимается; следующее пробуждение пересобирает с учётом нового входа
    (черновик удешевляет повтор). Закон: **вход владельца не может быть молча
    проигнорирован**. Это пересобираемое расхождение — `needs_input` здесь неуместен;
  - *новый чужой текст* → по Р-15 данные, не инструкции: фиксируется в отчёте,
    базис решений не меняет, работа публикуется как планировалась.
  Оговорка: перечитывание — best-effort; окно гонки между re-read и move остаётся,
  настоящий CAS требует поддержки трекера (тот же маркер, что у лизы).
- **Модель угроз (Р-15).** Поля карточки и комменты — промпт-вход агента с repo_rw и
  сетью владельца. Доверенный вход для решений — только текст авторства владельца;
  чужой текст (комменты коллег, слова внешнего QA в возврате) — данные, не инструкции.
  **Гейты — санитарные кордоны:** недоверенный текст структурно не доходит до кода мимо
  дизайн-гейта (возврат QA → новая карточка → Аналитик → гейт владельца). Офис никогда
  не постит секреты в трекер.
  **Авторство не по полю author (Р-20):** офис работает под кредами владельца, поэтому
  формальное авторство протекает — текст ролей выглядит владельческим, и доверие текло бы
  транзитивно между агентами мимо кордонов. Маркер офисного контента вшивает **адаптер**,
  безусловно (Р-25) — роль опубликовать немаркированное не может; правило доверия:
  **автор = владелец и не маркировано офисом**. Чище — технический аккаунт офиса
  (`office_account` в профиле): при его наличии правило апгрейдится до чистого авторства.
- **Git-гигиена.** Каждая карточка — в **отдельном worktree**, удаляемом по завершении;
  общая рабочая копия неприкосновенна. Правила ролей: абсолютные пути; явный `git add`
  по списку файлов (никогда `-A`); branch-check перед каждым push; чужие dirty-файлы
  не трогать и докладывать. Push — только в свою ветку; push в base_branch запрещён
  всем ролям (рекомендация клиенту: закрепить branch protection).
- **Необратимое — только человеку.** Force-push, переписывание истории, удаление
  веток/данных, миграции вниз — запрещены всем ролям, всегда. Список — в конституции,
  **не** в профиле: клиент не может его ослабить.
- **Бюджеты против runaway.** Три потолка: токены/время на пробуждение; итерации на
  петлях (§8); дневной бюджет офиса в профиле. Исчерпание — остановка с докладом,
  никогда «дожать по-тихому».
- **Протухание.** Делопроизводитель помечает карточки без движения дольше срока:
  на гейтах владельца — мягкое напоминание дайджестом; в работе — флаг «разобраться».
  Тухнуть молча не может ничто.
- **Чёрный ящик.** Каждое пробуждение — строка в журнале (`.office/journal/` у клиента):
  роль, карточка, результат, длительность, токены. Материал разбора инцидентов и сырьё
  метрик. Инцидент офиса → запись + `needs_input`; исправление офиса — работа в
  репозитории офиса по его дорожной карте.

> **Проработка:** протокол лизы (формат, тайминги); протокол базиса и перечитывания
> (что входит в базис, детекция расхождений); формат журнала; перечень
> необратимых операций (исчерпывающий список); схема дневного бюджета — по ролям
> или гарантированные доли (единый бюджет позволяет Разработчику съесть всё и
> заморить AI-QA — карточки скопятся в ai_qa).

### 10. Метрики

Считаются из того, что и так остаётся (журнал, доска, git). В v1 — никаких дашбордов:
еженедельный **текстовый дайджест** от Делопроизводителя. Пять групп:

1. **Поток.** Lead time идея→done по стадиям, с обязательным разделением «время работы
   офиса» vs «время ожидания на гейтах владельца» — без него метрика лжива.
2. **Качество первого прохода.** Доля PR через AI-QA с первого раза (здоровье
   Разработчика); возвраты с гейтов владельца (дизайн-гейт — слаб Аналитик;
   мерж-гейт — **самая тревожная**: брак, пропущенный AI-QA); возвраты внешнего QA —
   внешняя оценка всей пирамиды, сравнимая с ручной базой владельца.
3. **Нагрузка на владельца.** Частота `needs_input`; доля карточек от гейта до гейта
   без единого вмешательства. Метрика главного обещания: не растёт — офис не выполняет
   миссию, как бы хороши ни были остальные цифры.
4. **Экономика.** Токены на карточку по ролям; отдельно — цена брака (токены возвратных
   петель). Тренд важнее абсолюта.
5. **Здоровье механики.** Пробуждения впустую; протухшие лизы; инфра-ретраи.

**Алармы** в дайджесте: возвраты с мерж-гейта выше порога; петля §8 регулярно упирается
в лимит; `needs_input` растёт от релиза к релизу.

**Защита от Гудхарта (Р-11):** метрики — для владельца-наблюдателя. Роли о них не знают,
в промпты они не входят, цели «улучшить метрику» офису не ставятся.

> **Проработка:** формат дайджеста; скрипт подсчёта из журнала; пороги алармов.

### 11. Упаковка и дистрибуция

Офис — **плагин Claude Code**; репозиторий одновременно плагин и маркетплейс (Р-08).

```
virtual-office/
  .claude-plugin/        — манифест плагина (имя, версия) + marketplace.json
  skills/
    office-init/         — визард подключения клиента: опрашивает, пишет профиль,
                           заводит расписание ролей; импортирует legacy-конфиги
    office-analyst/      — роли офиса, каждая — скилл
    office-developer/
    office-qa/
    office-clerk/
  adapters/              — трекер-адаптеры
  templates/             — схема и примеры профиля клиента
  docs/                  — конституция (этот документ), specs/, adr/
  README.md, CLAUDE.md
```

Жизненный цикл:

- **Разработка:** офис — отдельный проект со своими сессиями, semver + CHANGELOG,
  своей дорожной картой.
- **Подключение клиента:** `/plugin marketplace add <путь-или-github>` →
  `/plugin install virtual-office` → `/office-init`. Единственный след в клиенте —
  `.office/` (профиль, шаблоны, журнал).
- **Обновление:** новая версия плагина подтягивается в клиентов; профили не трогаются.
- **До публикации** маркетплейс подключается с локального пути — клиент №1 работает
  с офисом из соседней папки.

> **Проработка (этап 0):** точные форматы манифестов плагина/маркетплейса — сверить
> с актуальной документацией Claude Code; схема версионирования.

### 12. Дорожная карта проработки

> **Для v1 эта карта заменена лестницей мелких шагов (Р-31) — см. `docs/v1-scope.md`.**
> Таблица ниже остаётся описанием полного замысла и ориентиром за пределами v1;
> порядок ролей в ней скорректирован решением Р-33 (первая роль — Уточнитель).

Принцип: **от безопасного к рискованному; каждый этап заканчивается реальной
эксплуатацией на клиенте №1**, не демо. Следующий этап не начинается, пока предыдущий
не пожил в бою. Каждый этап получает свой цикл: брейншторм (при развилках) →
дизайн-док в `docs/specs/` → план → реализация.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **0. Фундамент** | Скелет плагина + маркетплейс-манифест, сверка механики с документацией | Плагин устанавливается в клиента (пусть пустой) |
| **1. Делопроизводитель** | Первая живая роль: jira-адаптер + конформанс-сьют, профиль клиента, `office-init`, лизы, журнал, cron-раннер с локом (Р-22), маркировка комментов (Р-20), проверка селективной загрузки контекста (Р-21) | Один реальный пост-мерж цикл проведён офисом |
| **2. AI-QA** | Приёмка на **ручных PR владельца** — ценность до появления AI-автора; ОТК обкатывается в бою | Отчёт приёмки на реальном PR признан полезным, а не шумом |
| **3. Аналитик + гейты** | **Первым — UX гейтов и жеста ответа на `needs_input`** (Р-14), до промптов Аналитика. Затем постановка → design doc → UI-варианты (цель — на реальных компонентах клиента, Р-24) → первый настоящий дизайн-гейт | Владелец утвердил подготовленный офисом дизайн и взял в работу |
| **4. Разработчик** | Самая рискованная роль — в обкатанное окружение (постановки от Аналитика, приёмка AI-QA, бухгалтерия клерка); модель работы — Р-17: план в ветке, коммиты-чекпоинты, возобновление | Карточка прошла идея→мерж-гейт без рук владельца между гейтами |
| **5. Метрики и тюнинг** | Дайджест, алармы, настройка расписаний (журнал копится с этапа 1) | Первый дайджест с честными цифрами |

**Горизонт** (без обязательств): Планёрка; Релиз-инженер; облачный раннер + мост к
трекеру; второй проект-клиент; вынос журнала решений в ADR.

Обоснование ключевого хода — AI-QA раньше Разработчика: приёмке не нужен AI-автор,
она работает на ручных PR и даёт ценность немедленно; а когда Разработчик появится,
его встречает уже обкатанный ОТК.

### Отвергнутые альтернативы

Отвергнутые альтернативы: центральный оркестратор (Р-09); событийный конвейер на
CI/webhooks — невозможен, пока трекер недоступен извне; слой «потом», не каркас.

Будущая пятая роль «Планёрка» (ежедневный смотрящий за всей доской, ничего не реализует)
может добавить глобальную координацию, не ломая хореографию.
