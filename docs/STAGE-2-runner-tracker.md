# Этап 2. Runner: трекер, захват задач, worktree, конвейер

Инструкция для Claude Code. Перед началом прочитай `docs/DESIGN.md`, `docs/contracts/agent-io.md`
и `docs/notes/stage-1-retro.md`. Этап 1 дал `run-agent` — чистую функцию «роль + workdir → result.json».
Этап 2 строит вокруг неё детерминированный runner: берёт задачу из трекера, готовит worktree,
вызывает `run-agent`, разбирает исход, двигает задачу по графу и пишет отчёт в тикет.

## Цель этапа (definition of done)

    ./bin/runner tick --role implementer          # один цикл: взять ≤1 задачу, выполнить, вернуть
    ./bin/runner loop --role implementer          # то же по расписанию, пока не остановят
    ./bin/runner reap                             # вернуть задачи с истёкшей арендой

работают против двух реализаций трекера — файлового `mock` и `jira` — без единой правки
в `roles/`, `adapters/`, `backends/`. Сценарий, который обязан проходить целиком:

1. в трекере есть задача в колонке `Ready` для проекта, описанного в `projects.yaml`;
2. `tick` захватывает её (аренда), создаёт worktree ветки `agent/<KEY>` из свежего `origin/<default>`,
   собирает `task.md`/`context.md`, вызывает `run-agent`;
3. по `outcome=done` — пушит ветку, пишет структурированный комментарий, переводит задачу
   в `Review`, снимает аренду;
4. по `needs_human` — пушит что есть, пишет комментарий с вопросами, переводит в `Blocked`,
   ставит атрибут «ждёт человека»; после ответа человека комментарием следующий `tick`
   возвращает задачу в `Ready` с ответом в контексте;
5. по `blocked`/`failed` — комментарий, возврат в `Ready` с инкрементом счётчика попыток;
   после N попыток — `Blocked` и человек;
6. если runner убит посреди прогона — `reap` находит истёкшую аренду, пишет комментарий
   и возвращает задачу в `Ready`; следующий `tick` подхватывает существующий worktree.

## Общие правила работы

- Как на этапе 1: шаг → отчёт → коммит → **стоп и ожидание подтверждения**. Не забегать вперёд.
- Runner — детерминированный Go-код, никакого LLM внутри. Всё, что «решает», решается по
  `workflow.yaml` и `result.json`, не по эвристикам.
- Один новый бинарник `bin/runner`; `bin/run-agent` не трогаем, runner зовёт его как пакет
  (`runner.Execute` или аналог), а не подпроцессом, но CLI `run-agent` остаётся для ручной отладки.
- Зависимости поимённо: YAML уже есть; для JIRA — стандартный `net/http`, без клиентских
  библиотек (их API уходит вперёд Server-версий, а нам нужен контроль над каждым запросом).
- Секреты (`JIRA_TOKEN`/`JIRA_PASSWORD`, `GITHUB_TOKEN` для пуша) — только окружение.
- Всё новое поведение сначала проверяется на `mock`-трекере тестами, потом на `jira` вживую.
  Ни один шаг не считается закрытым, пока не проходит на mock.
- Флаги/поведение JIRA REST не помнить, а проверять: `docs/notes/jira-api.md` по образцу
  `claude-cli.md` — три источника: документация, эмпирика, ответ сервера.

## Шаг 0. Долги этапа 1

Оба мешают этапу 2, поэтому закрываем до всего остального.

1. **Коды возврата `run-agent`**: 0 — валидный `result.json` с исходом `done|needs_human|blocked`;
   1 — `failed`, агентский или синтетический; 2 — инфраструктурная ошибка (роль/бэкенд/кред). Обновить
   `smoke.sh`, README, DoD этапа 1.
2. **Хук валидирует то же, что runner.** Вынести `runner.Result.Validate()` в подкоманду
   `run-agent validate-result <path>` (код 0/2 + причины в stderr, как хук ждёт). В песочнице
   хук исполняется на Linux — собрать статический `validate-result` под целевую платформу
   бэкенда (`GOOS/GOARCH` из `sbx`-образа, зафиксировать в `sbx.md`) и класть в `roleDir`
   рядом с хуками; `require-result.sh` зовёт его. На `local` — тот же бинарник, собранный
   под хост. Один источник истины, никакого второго парсера. Проверить живым прогоном:
   результат без `next_owner` → агент получает причину и чинит, а не уходит в `failed`.
3. **Архив прогонов.** Worktree на этапе 2 будут удаляться, а с ними `.agent/`. Runner копирует
   `.agent/` в `${OFFICE_HOME:-~/.office}/runs/<run_id>/` после каждого прогона. Пока просто
   каталог; никакой БД.

Отчёт → стоп.

## Шаг 1. Модель и контракты (без реализации трекеров)

Создай пакет `tracker/` с интерфейсом и типами, `workflow.yaml`, `projects.yaml`, и опиши всё
в `docs/contracts/tracker-protocol.md`.

**Интерфейс `Tracker`** — минимум, что нужен runner'у:

    Whoami() → account                          # учётка runner'а: всё не от неё — человек
    ListReady(project, status) → []TaskRef      # кандидаты в колонке, без живой аренды, отсортированы
    ListExpired(project, now) → []TaskRef       # для reaper
    Get(key) → Task                             # поля + комментарии (все, runner сам режет по маркеру)
    Claim(key, run_id, owner, lease_until, expect_status) → error   # см. семантику ниже
    Renew(key, run_id, lease_until) → error     # продление аренды, только своей
    Release(key, run_id) → error                # снять аренду, статус не менять
    Transition(key, actor, to_status) → error   # смена колонки, см. правило владения
    Comment(key, actor, body) → error
    SetHumanFlag(key, actor, on bool) → error   # атрибут «ждёт человека»
    SetAttempts(key, actor, n) → error

Трекер не знает про роли: сопоставление «роль → колонка» делает runner по `workflow.yaml`.
`tracker.yaml` описывает подключение и маппинг статусов/полей; список проектов — `projects.yaml`.

**Семантика `Claim`** (важнейшее место, см. DESIGN §2.2): записать `agent_owner`, `run_id`,
`lease_until`; перевести в статус «в работе»; **перечитать** и убедиться, что владелец — мы;
если нет — вернуть `ErrClaimLost`, ничего не откатывать. Аренда — lease, не lock: истёкшая
аренда считается свободной.

**Правило владения** для мутаций (`Transition`, `Comment`, `SetHumanFlag`, `SetAttempts`).
`actor` бывает двух видов:
- **прогон** передаёт свой `run_id` и требует, чтобы аренда была *его* и *живой*. Иначе —
  `ErrNotOwner`, **в том числе если аренды нет вовсе**: для прогона «нет аренды» значит
  «у меня её отобрали» (reap уже вернул задачу, её мог взять другой tick);
- **системная операция** (`reap`, обработка ответа человека) передаёт пустой `run_id` и требует,
  чтобы *живой* аренды не было (нет или истекла). Живая чужая аренда → `ErrNotOwner`.

Так reap и human-reply обходятся без `Claim`, а зависший прогон, доживший до конца после
reap, ничего в трекер не пишет. Обязанность runner'а: перед финализацией — `Renew`; на
`ErrNotOwner` результат архивируется, ветка пушится, в трекер идёт только комментарий
«прогон run:<id> завершился после потери аренды» (как системная операция), переходов нет.

**`Task`**: key, summary, description, status, labels, поля аренды, `attempts`, `human_flag`,
`project`, `comments []Comment{id, author, created, body}`.

**Кто человек.** На старте runner зовёт `Whoami()`; ответом человека считается комментарий
от любой учётки, не входящей в `tracker.yaml: agent_accounts` (на этапе 2 там одна запись —
та, что вернул `Whoami`; на этапе 3 роли могут ходить под разными учётками, и комментарий
Reviewer'а не должен считаться ответом человека для Implementer'а). В mock — поле `author`.
Отсюда требование к полигону JIRA: вторая учётка для человека.

**`workflow.yaml`** (граф; runner читает, агент не видит):

    columns: [Ready, InProgress, Review, Blocked, Done]
    roles:
      implementer:
        reads_from: Ready
        working: InProgress
        outcomes:
          done:        { to: Review }
          needs_human: { to: Blocked, human: true }
          blocked:     { to: Ready, attempts: +1 }
          failed:      { to: Ready, attempts: +1 }
    limits:
      max_attempts: 3          # после — Blocked + human
      lease_margin_sec: 300    # аренда = timeout роли + запас
    human_reply:               # что делает runner, увидев ответ человека на Blocked
      to: Ready
      reset_attempts: true     # человек снял причину; старые попытки к новой постановке не относятся

**`projects.yaml`**: `jira_project → {repo_url, default_branch, branch_prefix, worktree_root}`.
Runner отказывается брать задачу проекта, которого тут нет.

**Протокол комментариев** (`docs/contracts/tracker-protocol.md`): первая строка — маркер
`[office run:<run_id8> role:<role> outcome:<outcome> config:<sha8>]`, дальше — `summary`,
затем секции по исходу (вопросы списком, блокер, артефакты со ссылками на ветку/коммит).
Ответ человека — любой комментарий не-агента, созданный **после** маркера с `outcome:needs_human`.
Runner режет комментарии по последнему маркеру своей роли: в `context.md` попадает только хвост.

Отчёт → стоп.

## Шаг 2. `tracker/mock` — файловый трекер

Каталог `${OFFICE_HOME}/mock/<KEY>/task.yaml` + `comments/NNNN.md`. Реализует `Tracker` целиком,
включая гонку: `Claim` через атомарное переименование (`rename` временного файла) — так тест
на два конкурирующих `tick` действительно проверяет CAS, а не эмулирует его.

Тесты (это основа этапа, не экономить):
- два `Claim` одной задачи → ровно один успех;
- `Transition`/`Comment` чужим `run_id` → `ErrNotOwner`; прогон без аренды (после reap) → `ErrNotOwner`;
  системная операция при живой чужой аренде → `ErrNotOwner`, при истёкшей — успех;
- истёкшая аренда видна в `ListReady` и `ListExpired`;
- `human_reply` распознаётся только по комментариям после нужного маркера.

CLI для ручной работы: `bin/runner mock add|ls|show|comment` — чтобы гонять сценарии руками
без JIRA. Отчёт → стоп.

## Шаг 3. Worktree-менеджер и пуш

Пакет `workspace/`:
- bare-клон на проект в `${OFFICE_HOME}/repos/<name>.git`, `fetch` перед каждой задачей;
- `Ensure(task) → workdir`: если worktree ветки `agent/<KEY>` уже есть — переиспользовать
  (после `reap` или `needs_human`), иначе `worktree add` от `origin/<default>`;
- `Push(workdir)`: пуш ветки под токеном из окружения; runner пушит **всегда, когда есть
  новые коммиты**, независимо от исхода — работа не должна жить только в worktree;
- `Archive(run_id)`: копия `.agent/` в архив (шаг 0.3);
- `Remove(task)`: удаление worktree — только по явной команде или при `Done`, не после каждого прогона.

Личность коммитов уже задаёт адаптер; runner не переопределяет. Пуш — единственное место
с сетевым git-доступом, и он вне агента (см. `stage-1-retro.md`, обход deny через `git -c`).

Тесты на локальном bare-репо: создание, переиспользование, пуш, что `.agent/` не в истории.
Отчёт → стоп.

## Шаг 4. Runner: `tick`, `loop`, `reap`, диалог с человеком

`tick --role R`:
1. `ListReady(R)` → первая задача проекта из `projects.yaml`, у которой `attempts < max`;
2. `Claim` с `lease_until = now + role.timeout + margin`; `ErrClaimLost` → взять следующую;
3. `Ensure` worktree; собрать `task.md` (summary + description + acceptance, ссылки на связанные),
   `context.md` (хвост комментариев после последнего маркера роли, включая ответ человека;
   `STATE.md`/`PLAN.md` из worktree; номер попытки), `run.json` (+ поле `task_key`);
4. параллельно с прогоном — `Renew` каждые `timeout/3`;
5. `run-agent`; `Archive`; `Push`, если есть коммиты;
6. по `workflow.yaml`: `Comment` (протокол шага 1) → `Transition` → `SetHumanFlag`
   при `human: true` → `Release`. Порядок именно такой: комментарий раньше перехода, чтобы
   при падении между ними задача не оказалась в новой колонке без объяснения;
7. код возврата: 0 — цикл прошёл (включая «задач нет»), 2 — инфраструктура.

Перед п.1 `tick --role R` обрабатывает **ответы человека по задачам своей роли**: задачи
в `Blocked` с `human_flag`, у которых после последнего маркера `role:R outcome:needs_human`
есть комментарий не-агента, переводятся в `Ready` (системная операция, без Claim), флаг снимается,
`attempts` сбрасывается, пишется комментарий-подтверждение с маркером. `tick` без `--role`
делает то же по всем ролям из `workflow.yaml`, затем по одному `tick` на роль.

`reap`: `ListExpired` по всем проектам → системная операция: комментарий «аренда истекла,
run:<id>, возвращаю» → `attempts+1` → `Transition(Ready)` → снять аренду. Ничего не удалять,
worktree оставить. Если к моменту записи аренда снова жива (задачу успел продлить или
перезахватить кто-то) — `ErrNotOwner`, задачу пропустить.

`loop --every 2m`: `reap` → `tick` → sleep. Остановка по SIGTERM между циклами. Не демон,
не supervisor: запускается cron/launchd/systemd-timer'ом — пример юнита в `bootstrap/`.

Всё это — сначала на `mock` end-to-end тестом с поддельным `run-agent` (записывает заданный
`result.json`), потом живой прогон на `mock` с настоящим `run-agent --backend sbx`. Записать в
`docs/notes/stage-2-smoke.md`. Отчёт → стоп.

## Шаг 5. `tracker/jira`

REST API **v2** (его понимают и Cloud, и Server 8.13; v3 с ADF — только Cloud). Конфиг
`tracker.yaml`: `base_url`, `auth: {mode: basic|pat, user_env, secret_env}`, `project`,
маппинг статусов на колонки, ID кастомных полей аренды (`agent_owner`, `run_id`, `lease_until`,
`attempts`), имя лейбла/поля для `human_flag`, ID переходов workflow.

- `Whoami`: `GET /rest/api/2/myself`;
- `ListReady`: JQL `project=X AND status="Ready" AND (lease_until IS EMPTY OR lease_until < now())`
  с сортировкой по приоритету/дате;
- `Claim`: `PUT fields` + `POST transitions` + `GET` и сверка `run_id`. Атомарности в JIRA нет —
  именно поэтому сверка после записи обязательна, и в тесте на два конкурирующих `tick`
  допускается ровно один победитель;
- комментарии — plain text (v2), маркер в первой строке;
- ошибки 401/403/404/409 — различать и логировать тело ответа.

Разработка и тесты — против бесплатного **Jira Cloud** (создать проект, поля, workflow;
инструкция настройки — в `docs/notes/jira-setup.md`, чтобы повторить на Server 8.13).
Отличия Server 8.13 (basic-auth вместо API-token, отсутствие некоторых полей поиска)
записать в `jira-api.md` как открытые, но не блокирующие: сравнить, когда появится доступ.

Прогнать сценарий DoD целиком на Cloud (две учётки: runner и человек) + тестовом GitHub-репо. Отчёт → стоп.

## Чего НЕ делать на этом этапе

- Не добавлять вторую роль — только `implementer`; `workflow.yaml` обязан *допускать* другие
  роли, но их нет.
- Не делать Review, merge, PR: `Review` — конечная колонка этапа, дальше человек.
- Не делать типизированные интерактивные вопросы (DESIGN §4): вопрос — комментарий, ответ —
  комментарий, распознавание — по маркеру.
- Не делать веб-UI, дашборды, метрики: `runner ls` в терминале достаточно.
- Не закрывать сеть sbx и не трогать `sbx secret` — отдельная работа.
- Не подключать библиотеки JIRA-клиентов и не писать под v3/ADF.
- Не давать runner'у ничего «решать» вне `workflow.yaml` и `result.json`.
