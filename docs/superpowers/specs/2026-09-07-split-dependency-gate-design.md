# split-dependency-gate — глубокий технический дизайн

Волна 2, Change 2 авто-разбиения задач
(`docs/notes/analyst-task-splitting.md`, разделы «Волна 2 — брейншторм
2026-09-05» → «Change 2» и «2026-09-07: pr-converge на PR #7» → «Только
задокументировано, не исправлено»). Change 1 (авто-создание связанных
тикетов) смёржен в `master` (`ecc2ac4`, PR #7) и подтверждён живьём —
предусловие «Change 2 отложен до живой проверки Change 1» закрыто.

Открытые вопросы, которые предыдущий заход сознательно оставил на «начало
Change 2» (обе решены брейнштормом 2026-09-07, ниже — их развёртка до
уровня конкретных сигнатур):

1. `jira.toTask` не разбирает `issuelinks` обратно, поэтому
   `Task.DependsOn` на JIRA сейчас всегда пуст, хотя `LinkDependsOn` его
   честно пишет.
2. `roles/analyst/role.md` не говорит аналитику, когда ставить `depends_on`
   между детьми `split` — критерий нужен раньше, чем связь начинает реально
   блокировать работу.

Форма самого гейта (место — `claim()`, роли — все единообразно, без
специального исключения `reviewer`, видимость — на лету в `runner ls`, без
меток) решена ещё брейнштормом 2026-09-05 и здесь не пересматривается.

## Почему не метка `depends-on:<KEY>`

Первая версия этого дизайна предлагала параллельно с `issuelink`
(для человека) писать метку `depends-on:<KEY>` (для гейта) — по образцу уже
существующих `split-child:<parent>:<id>` (`FindByMarker`) и
`office-waits-human` (`HumanFlagLabel`), которые в этом коде тоже управляют
реальным ветвлением, не только отображением. Отклонено при обсуждении с
владельцем: не сама идея метки-как-маршрутизатора (прецедент есть и
годный), а то, что один факт «X зависит от Y» записывался бы в трекер
**дважды** — `issuelink` и метка — с риском разойтись при частичном сбое
(например, `POST /issueLink` упал, метка уже написалась, или наоборот).
Решение: чинить единственный источник правды (`issuelinks`), а не заводить
второй.

## 1. Чтение `Task.DependsOn` из `issuelinks`

### Разбор в `toTask`

```go
// internal/tracker/jira/jira.go, в toTask(raw issue) рядом с разбором labels/attachment

if links, ok := fields["issuelinks"].([]any); ok {
    for _, raw := range links {
        link, ok := raw.(map[string]any)
        if !ok {
            continue
        }
        typ, _ := link["type"].(map[string]any)
        if text(typ["name"]) != t.cfg.DependsOnLink {
            continue
        }
        // outwardIssue заполнен только у той стороны связи, что была
        // записана как outwardIssue при POST /issueLink — а LinkDependsOn
        // пишет туда dependsOnKey (см. его доккомент про развёрнутое
        // направление). inwardIssue здесь — обратная связь ("кто зависит
        // от меня"), её не читаем: DependsOn — это "от кого зависит эта
        // задача", не "кто зависит от неё".
        if out, ok := link["outwardIssue"].(map[string]any); ok {
            task.DependsOn = append(task.DependsOn, text(out["key"]))
        }
    }
}
```

`GET /issue/{key}` уже возвращает `issuelinks` целиком без дополнительных
параметров. **Но `search()` (JQL, `/search`) — нет**: `ListReady`/`List`
идут через общий `t.searchProject` → `search()` → `t.searchFields()`
(`jira.go:849`), а этот список полей `issuelinks` не включает. Раз §2
читает зависимости кандидата из `TaskRef.DependsOn`, пришедшего именно из
`ListReady` (не из отдельного `Get`), `searchFields()` тоже обязан просить
`issuelinks` — иначе гейт на JIRA молчит: у каждого кандидата `DependsOn`
пуст, хотя `Get(key).DependsOn` его показал бы верно.

Пустой `t.cfg.DependsOnLink` (тип связи не сконфигурирован на этом
инстансе) — `typ.name` ни с чем не совпадёт, `DependsOn` останется пустым.
Тот же режим отказа, что уже есть у `LinkDependsOn` при пустом
`DependsOnLink` (`internal/tracker/jira/jira.go:744`) — падать там, где
это впервые кому-то мешает, не заранее.

### Живая верификация — не повторять прошлую ошибку

Запись «сверено по `issuelinks`» уже подводила один раз (см. «Урок» в
`docs/notes/analyst-task-splitting.md`, 2026-09-06): проверка формы запроса
(`outwardIssue`/`inwardIssue` содержат нужные ключи) не то же самое, что
проверка смысла (что эти поля значат на живом сервере). План верификации
Change 1 для *записи* — эталонный тип `Blocks`, чьё направление все стороны
понимают одинаково; для *чтения* нужен симметричный приём:

1. На полигоне (`10.73.10.235`) создать throwaway-пару тикетов, связать
   штатным `Blocks` через `LinkDependsOn`-подобный вызов с ролями,
   однозначно известными заранее («A blocks B» — не через код этой волны, а
   прямым `POST /issueLink` с руками заданными `outwardIssue`/`inwardIssue`).
2. `GET /issue/A` и `GET /issue/B` — прочитать `issuelinks` обеих сторон,
   убедиться, какая из них несёт `outwardIssue`, какая `inwardIssue`, и
   что это совпадает с тем, что реально показывает UI JIRA («A blocks B»,
   не наоборот).
3. Только после этого — тот же `GET` на паре, связанной настоящим
   `LinkDependsOn` (тип `DependsOnLink` из `tracker.yaml`), сверить с
   пунктом 2 и с ожиданием кода выше (`outwardIssue` populated → это и
   есть `dependsOnKey`).
4. Удалить throwaway-тикеты после проверки.

Это отдельный пункт плана, до того как на разбор `issuelinks` станет
полагаться гейт — не полагаемся на «направление уже проверено при записи
в Change 1», это была проверка другого факта.

### Побочный эффект: `linkChildren` может стать ленивым

`splits.go:359` сейчас шлёт `POST /issueLink` на каждом цикле `Loop` для
незакрытой пачки, полагаясь на серверную идемпотентность (доккомент прямо
называет источником неленивости «не гарантировано читать записанное через
`Get(key).DependsOn`» — тот же вопрос, что и здесь). Теперь, когда чтение
надёжно, `linkChildren` перед `LinkDependsOn` может проверить
`slices.Contains(child.DependsOn-уже-в-Get, depKey)` и пропустить уже
связанную пару. Не обязательная часть Change 2 (серверная идемпотентность
и так работает), но естественная уборка кстати — включить в план как
отдельную, необязательную задачу, не блокирующую остальное.

### Устаревший доккомментарий

`Task.DependsOn` (`internal/tracker/tracker.go`) сейчас прямо утверждает
обратное тому, что делает этот Change: «`Get()` гарантированно отражает
связь... не на всех реализациях... jira — нет». Поправить текстом этого
же Change, не отдельной находкой постфактум — комментарий либо верен,
либо вводит в заблуждение, третьего для документации контракта нет.

## 2. Гейт в `claim()`

### Откуда берутся статусы зависимостей

Не `Get()` на каждую зависимость каждого кандидата (лишний вес — тянет ещё
и всю переписку), а один `List(project, o.Workflow.Statuses)` на проект —
то же самое, что уже делает `printBoard` (`cmd/runner/board.go:36`).

```go
// internal/pipeline/deps.go (новый файл)

// unmetDependencies — зависимости ref, чей статус ещё не терминален,
// по данным уже загруженного среза задач проекта (byKey). Общий помощник
// для claim() (гейт) и printBoard (видимость в ls) — одна реализация,
// не две отдельные.
func unmetDependencies(ref tracker.TaskRef, byKey map[string]tracker.TaskRef, terminal func(string) bool) []tracker.TaskRef {
    var unmet []tracker.TaskRef
    for _, key := range ref.DependsOn {
        dep, found := byKey[key]
        if !found || !terminal(dep.Status) {
            unmet = append(unmet, dep) // found==false: dep — нулевой TaskRef{Key: ""}
        }
    }
    return unmet
}
```

Требует добавить `DependsOn []string` в `TaskRef` (сейчас есть только в
`Task`) — `Ref()` копирует его так же, как остальные поля. `mock.Ref()` и
`jira`-путь `toTask(...).Ref()` — оба уже проходят через общий
`Task.Ref()` (`tracker.go:135`), правки в одном месте достаточно. На
стороне JIRA этого поля в `Ref()` не будет, пока `searchFields()` не
запросит `issuelinks` (см. §1) — правки связаны, но независимо
тестируются: юнит-тест на `search()`/`toTask` с `issuelinks` в теле ответа
и юнит-тест на `Task.Ref()`, копирующий поле как есть.

Отсутствующий в `byKey` ключ (зависимость удалена/не существует) — тоже
`unmet` (пустой `TaskRef` с `found=false` явно виден вызывающему по
`Key == ""`), а не тихо пропущен: падать громко, не считать свободной
зависимость, которую нечем подтвердить.

### `claim()`

```go
// internal/pipeline/pipeline.go, claim()

func (o *Office) claim(roleName string, flow tracker.RoleFlow, role runner.Role) (claimed, error) {
    lease := o.now().Add(...)

    for _, project := range o.projects() {
        refs, err := o.Tracker.ListReady(project, flow.ReadsFrom)
        ...
        byKey, err := o.projectByKey(project) // List(project, o.Workflow.Statuses) → map, только если refs непусты
        ...
        for _, ref := range refs {
            if ref.Attempts >= o.Workflow.Limits.MaxAttempts {
                ...
            }
            if unmet := unmetDependencies(ref, byKey, o.Workflow.IsTerminal); len(unmet) > 0 {
                o.logf("%s: ждёт %s, пропускаю", ref.Key, describeUnmet(unmet))
                continue
            }
            task, taken, err := o.take(ref, roleName, flow, lease)
            ...
        }
    }
    ...
}
```

`o.projectByKey(project)` вызывается лениво — только когда в `refs` вообще
есть кандидаты (пустой `ListReady` не тратит лишний `List`) — тот же
принцип, что уже держит `search()` без лишнего запроса в счастливом пути.

Один и тот же код для всех ролей графа: `claim()` не знает и не спрашивает
`roleName` при проверке зависимостей. Для `reviewer` (`reads_from: Review`)
это не требует отдельного исключения — тикет уходит в `Review` только
после того, как его implementer прошёл этот же гейт и закончил работу,
значит зависимость к этому моменту уже терминальна по построению, и
`unmetDependencies` для него всегда возвращает пустой список. Явная
проверка `roleName != "reviewer"` была бы кодом ради кода — если когда-то
понадобится всё-таки различать роли здесь, это будет видно по упавшему
тесту, а не по спекуляции сейчас.

### `ls` — видимость

```go
// cmd/runner/board.go, printBoard

byKey := toByKey(refs) // тот же List(project, statuses), уже вызван
for _, ref := range refs {
    unmet := unmetDependenciesForDisplay(ref, byKey, workflow.IsTerminal) // экспортируемая обёртка
    fmt.Fprintf(out, "%-10s %-12s %-24s попыток:%d %-16s %s%-10s %s\n",
        ref.Key, ref.Status, lease(ref, now), ref.Attempts, waiting(ref), dependsColumn(unmet), age(ref.Updated, now), ref.Summary)
}
```

`dependsColumn` формирует `"ждёт: EXP-5 (Review)"` — ключ и текущий
статус каждой незакрытой зависимости, пусто если зависимостей нет или все
терминальны. `printBoard` уже вызывает `List(project, statuses)` один раз
на весь список — `byKey` строится из того же среза, ни одного лишнего
запроса.

## 3. `roles/analyst/role.md` — критерий `depends_on`

Добавить рядом с описанием исхода `split` (после текущего абзаца про
`split.children[]`, `docs/notes/analyst-task-splitting.md` ссылается на
контракт `docs/contracts/agent-io.md`):

> `depends_on` ставь только когда одна подзадача не может **начаться**,
> пока не смержен код другой — она опирается на схему, миграцию, модель
> данных или экспортируемый интерфейс, которого без предшественника ещё
> не существует. «Так логичнее по порядку» или «легче ревьюить
> последовательно» — не основание: раннер трактует `depends_on` буквально
> и не даст ни аналитику, ни разработчику начать работу над зависимой
> задачей, пока предшественник не смержен. Лишняя связь не упорядочивает
> работу, а откладывает её — режет тот самый параллелизм, ради которого
> разбиение затевалось.

Правка `docs/contracts/agent-io.md` не нужна: контракт уже описывает
`depends_on` формально (какие `id` допустимы, что раннер с ним делает) —
критерий «когда ставить» это решение аналитика, не формат данных, ему
место в `role.md`, как и остальные эвристики этой роли.

## 4. Известное ограничение — не чиним

Рекурсивный `split`: если ребёнок B, от которого зависит A, сам позже
получает исход `split`, `closeSplitParent` переводит B в терминальный
статус (`Done`) сразу после того, как созданы его собственные дети — не
когда они реально закончены. Гейт на A увидит B терминальным раньше
времени и снимет блокировку преждевременно. Редкий случай (разбиение уже
кем-то зависимого ребёнка) — фиксируется как известный остаточный риск,
отдельная защита не проектируется, по тому же принципу, что уже применён
к другим находкам этой линии (`docs/notes/analyst-task-splitting.md`,
«Остаточные ограничения»).

## Тестирование

- **`jira`**: unit-тест на `toTask` с фейковым `issuelinks` в ответе —
  разные формы (`outwardIssue` есть/нет, чужой `type.name`, несколько
  связей сразу) по образцу существующих тестов `toTask` на `labels`/
  `attachment`. Живая верификация направления — отдельный ручной прогон на
  полигоне (см. §1), не автоматический тест: как и Task 8 Change 1, это
  разовая проверка примитива внешней системы, не часть CI.
- **`mock`**: без изменений — уже честно хранит и читает `DependsOn`
  (не тронуто этим Change).
- **Гейт**: `internal/pipeline/pipeline_test.go`, по образцу существующих
  тестов `claim()`/`take()` — fake-трекер с задачей, у которой `DependsOn`
  указывает на задачу в нетерминальном статусе → `claim()` не берёт её;
  тот же кандидат, но зависимость терминальна → берёт. Кейс отсутствующей
  в трекере зависимости — отдельный тест на `found=false`.
- **`ls`**: тест на `printBoard`/`dependsColumn` — по образцу существующих
  тестов `board.go` (если есть) или ручная проверка вывода, если формат
  тестируется по строке уже сейчас.
- **`go build ./... && go vet ./... && go test ./...`** — как обычно,
  после каждой задачи и в конце.
