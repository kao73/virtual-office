# Конфигурация: что где лежит и что что перекрывает

У офиса два образца конфигурации — `office/tracker.example.yaml` и
`office/projects.local.example.yaml` — и оба хорошо расписывают собственные
ключи в комментариях; разойтись с релизом они не могут, потому что едут
внутри бинарника. Этот документ — не про ключи, а про форму вокруг них: как
складываются три слоя правил, какой файл читается откуда и какая переменная
окружения на что влияет.

## Две половины: репозиторий и `${OFFICE_HOME}`

Граница простая: **репозиторий — это фреймворк, `${OFFICE_HOME}` — инстанс.**
Репозиторий — код раннера, роли, граф статусов `workflow.yaml` — один и тот же
у всех, кто его поднимет, и ничего специфичного для конкретной машины или
проекта в нём нет. `${OFFICE_HOME}` — хозяйство раннера: проекты этой машины,
её учётки, её история прогонов.

Это не вкус раскладки. Правка репозитория под себя пачкает рабочее дерево —
метка `config:…-dirty`, которой раннер подписывает прогоны из грязного
дерева, перестаёт что-либо значить, если «грязь» — это просто локальные
настройки, а не незакоммиченный код. Поэтому всё, что заводят под новую
машину, обязано лежать в `${OFFICE_HOME}`, а не в репозитории. Полная
раскладка хозяйства — `docs/guide/operations.md`, раздел «Хозяйство
`${OFFICE_HOME}`».

## Три слоя правил

Правила песочницы — `network` (разрешённые домены) и `tools` (`allow`/`deny`
инструментов) — складываются из трёх слоёв, снизу вверх:

1. **Базовый** — `office/roles/_base/base.yaml`. Кладёт его в роль
   `runner.LoadRole` при загрузке: то, что нужно для песочницы вообще любой
   роли.
2. **Машинный** — раздел `defaults` в `${OFFICE_HOME}/projects.local.yaml`:
   добавки `network`/`tools`, общие для всех проектов этой машины.
3. **Проектный** — сама запись проекта там же: добавки только для него.

Слои не перекрывают друг друга, а объединяются: `runner.Union` берёт список
каждого слоя и отдаёт объединение без потерь, повторы схлопывает. Один и тот
же приём — и для базового слоя внутри `runner.LoadRole`, и для машинного с
проектным внутри `tracker.LoadProjects`. Из этого следует то, что стоит
сказать прямо: **назвать домен или инструмент можно на любом слое, а убрать
названный нижним слоем — нельзя ни одному из верхних.** Это верно и для
`tools.deny`: запретить инструмент волен любой слой, а отменить чужой запрет
не волен ни один. Отдельного запрета для `network` не существует — сеть
закрыта по умолчанию, и разрешают домены только поимённо.

Раздел `defaults` — не проект: требования к обычным записям (`repo_url`,
`default_branch`, …) к нему не применяются, а его собственные ключи
ограничены явным списком — только `network` и `tools`. Любой другой ключ под
`defaults` — отказ при загрузке, и отказ называет проект (`defaults`), сам
ключ и файл, а не просто «неизвестное поле».

## Какой файл читается откуда

У раннера два разных корня, и они не совпадают:

- **корень офиса** — либо клон (когда задан `OFFICE_CONFIG_ROOT`, тогда офис —
  `<этот путь>/office/`), либо распакованная поставка бинарника
  (`${OFFICE_HOME}/office/<версия>/`). Отсюда читаются `workflow.yaml`,
  `roles/`, `skills/`, `hooks/`, `sbx-kits/` и `office/budgets.yaml`;
- **корень хозяйства** — `${OFFICE_HOME}` целиком. Отсюда — `projects.local.yaml`,
  `tracker.yaml`, необязательная накладка `budgets.yaml`, архив прогонов
  `runs/`, реестр `ledger.jsonl`, bare-клоны `repos/` и рабочие папки
  `worktrees/`. Полная раскладка этого дерева — там же, в
  `docs/guide/operations.md`.

Какой из двух вариантов корня офиса выбрать, решает `ResolveOffice`
(`internal/runner/office.go`) — четыре ветки, первая подошедшая выигрывает:

1. задан `OFFICE_CONFIG_ROOT` → офис — клон по этому пути, личность прогона —
   commit этого клона;
2. иначе — версия релиза, зашитая при сборке через ldflags → офис —
   распакованная поставка, личность — эта версия;
3. иначе — `vcs.revision` из build info (сборка из клона напрямую, без
   обёртки `bin/*`) → личность — этот revision;
4. иначе — отказ: у собранного так бинарника нет ни версии релиза, ни
   commit'а в build info, и подписывать прогоны нечем.

Незакоммиченные правки в дереве сборки — с версией или без — добавляют к
личности суффикс `-dirty`. Текущий рабочий каталог офисом не считается
никогда: чтобы офис нашёлся, один из первых трёх вариантов должен подойти
явно.

## Переменные окружения

| Переменная | Кто читает | Что двигает |
|---|---|---|
| `OFFICE_HOME` | раннер целиком (`internal/runner/archive.go`, `HomeEnv`) | где хозяйство раннера; без переменной — `~/.office` |
| `OFFICE_CONFIG_ROOT` | `internal/runner/office.go` (`ConfigRootEnv`) | брать офис из клона, а не из поставки; выставляют обёртки `bin/*` |
| `OFFICE_INVOCATION_DIR` | `cmd/run-agent/main.go` | каталог, из которого позвали обёртку: без него относительные пути в аргументах (`--workdir`, `--task`) не едут после того, как обёртка перейдёт в корень конфиг-репозитория; выставляют `bin/runner` и `bin/run-agent` |
| `OFFICE_INSTALL_FROM` | `install.sh` | ставить из каталога артефактов, без сети |
| `OFFICE_VERSION` | `install.sh` | какой тег ставить; вместе с `OFFICE_INSTALL_FROM` — отказ, а не выбор одного из двух |
| `OFFICE_BACKEND` | только `scripts/smoke.sh` | бэкенд для smoke-прогонов (`local` или `sbx`). Раннер эту переменную не читает: его собственный бэкенд задаётся флагом `--backend` |
| `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` | `internal/adapters/claude/adapter.go` | кред агента; заданы обе — побеждает `ANTHROPIC_API_KEY` |
| `GITHUB_TOKEN` | раннер при публикации ветки и на PR-проходе | право писать в репозиторий проекта |
| имена из `accounts.*.user_env` / `accounts.*.secret_env` | значения — среда, читает `internal/tracker/jira` | учётки JIRA: в `${OFFICE_HOME}/tracker.yaml` только имена переменных, сами значения в файл не попадают |

## Ключи: где искать

Каждый ключ описан там, где он едет, — в самих образцах, и они ездят внутри
бинарника, так что разойтись с релизом не могут:

- проекты — `office/projects.local.example.yaml`, он же
  `${OFFICE_HOME}/projects.local.example.yaml` после `runner init`;
- подключение к JIRA — `office/tracker.example.yaml`, он же
  `${OFFICE_HOME}/tracker.example.yaml`;
- бюджеты — `office/budgets.yaml` и необязательная накладка
  `${OFFICE_HOME}/budgets.yaml`, разобранные в `docs/notes/budgets.md`;
- граф статусов — `office/workflow.yaml`; его читает раннер, агент его не видит.

Здесь их нет намеренно: два описания одного ключа расходятся при первой правке,
и расходится всегда то, которое не едет вместе с кодом.
