# Outcome

После `Approved` офис открывает pull request и кладёт ссылку в тикет. Человек
сливает. Офис видит слияние, переводит задачу в `Done` и убирает рабочую папку.
Конфликт возвращается implementer'у как работа, а не как провал.

Маршрут описан графом, а не кодом; проект без forge живёт по тому же графу
вырожденным проходом.

# Scope

- Блок `pr` в `workflow.yaml`; `Approved` перестаёт быть терминальным, терминал —
  `Done`.
- Пакет `forge/`: `OpenPR`, `PRState`; реализация GitHub через REST
  (`GITHUB_TOKEN`), и поддельная для тестов.
- Локальная проверка конфликта `git merge-tree --write-tree` по bare-клону.
- Системный проход в `tick`: открыть PR, проследить состояние, развести
  слияние/закрытие/конфликт.
- `Workspaces.Repo(project)` и `Workspaces.TryLock(key)`.
- Уборка рабочих папок переезжает из прогона в системный проход и идёт от папок.
- Ключи `tracker` и `forge` на проект в `projects.yaml`; `--tracker X` обходит
  только свои проекты.
- Маркеры `pr-opened`, `pr-closed`, `merged`, `merge-conflict`, `pr-skipped`.
- `roles/implementer`: разрешение `git merge` и раздел про конфликт.
- `scripts/jira-workflow.sh`: статус `Done` и четыре перехода.
- Живая проверка: пустой репозиторий на GitHub, третий проект, одна задача
  целиком — PR открыт, слит руками, задача в `Done`.

# Non-goals

- Авто-слияние. Сливает человек.
- `Mergeable` в интерфейсе forge: конфликт считается локально.
- Второй forge (GitLab и прочие). Интерфейс заводится так, чтобы второй был
  дешевле, но не заводится сам.
- Перенос конфигурации в `${OFFICE_HOME}`: отложенный шаг «конфигурация
  по машинам», перед шагом 5. `tracker` и `forge` пока живут в `projects.yaml`,
  и это записанный долг, а не решение.
- Уборка к боевому (шаг 3): контракты, `DESIGN.md`, разметка отчёта в JIRA.
- Первый не-полигон (шаг 5).

# Acceptance examples

**A1.** `workflow.yaml` описывает блок `pr` с `role`, `from`, `merged`,
`conflict`, `closed`; `terminal: [Done]`. Валидатор проверяет, что статусы блока
существуют, и не требует `office` в `tick_order`.

**A2.** `Workflow.Role("office")` отдаёт поток с `reads_from = pr.from`,
а `Order()` роль `office` не называет: обход ролей за `roles/office/role.yaml`
не полезет.

**A3.** Имени `office` в коде раннера нет: проход берёт его из `pr.role`.

**A4.** Проект с `forge: github`: задача в `Approved` без записей семейства →
открывается PR, в тикете комментарий с маркером `event:pr-opened` и URL в теле,
задача остаётся в `Approved`.

**A5.** Тело PR — `brief.md` изменения, прочитанный из bare-клона
(`git show origin/<ветка>:…`), плюс последний отчёт ревьюера из переписки тикета.
Рабочая папка для этого не нужна.

**A6.** Задача без каталога изменения (пришла `Backlog → Ready`, мимо аналитика):
телом PR идут summary и description тикета.

**A7.** Ветка без коммитов: forge отказывает, задача уходит в `pr.closed`
с запиской человеку, тик продолжается.

**A8.** Проект без `forge`: задача из `Approved` уходит сразу в `Done`
с `event:pr-skipped`; `merged` не пишется, потому что слияния не было.

**A9.** PR слит: `PRState` → `merged`, задача в `Done`, запись `event:merged`.

**A10.** PR закрыт без слияния: задача в `Blocked`, запись `event:pr-closed`,
задача помечена ожиданием человека.

**A11.** Ответ человека на `pr-closed` возвращает задачу в `Approved` штатным
механизмом, и PR открывается заново.

**A12.** Состояние PR определяется по последней записи роли `pr.role`
из {`pr-opened`, `pr-closed`}, а не по наличию `pr-opened` в истории: PR,
закрытый руками → `Blocked` → ответ человека → `Approved` открывается заново.

**A13.** Конфликт до открытия PR: `merge-tree` находит конфликт, задача уходит
в `Ready` с `event:merge-conflict`, `attempts` не тратится, PR не открывается.

**A14.** Конфликт у открытого PR: задача уходит в `Ready`, PR не закрывается,
и после возврата в `Approved` второй PR не открывается — переиспользуется тот же.

**A15.** Повторный системный проход по той же задаче не открывает второго PR
и не пишет дублей.

**A16.** Уборка идёт от папок: `Workspaces.List()`, просеянный проектами своего
трекера. Папка mock-проекта не трогается проходом `--tracker jira`.

**A17.** Папка задачи в терминальном статусе сносится; занятая пропускается;
**грязная пропускается с записью в лог**, а не сносится.

**A18.** Уборка убирает и папку задачи, которую человек перевёл в `Done` руками.
Снос из `work()` убран: задача, дошедшая до конца в прогоне, теряет папку
на системном проходе.

**A19.** `Workspaces.Repo(project)` заводит и освежает bare-клон без worktree;
`Workspaces.TryLock(key)` берёт замок, не создавая папки.

**A20.** `projects.yaml`: `tracker` обязателен (`mock`|`jira`), `forge`
необязателен; `runner tick --tracker jira` не обходит mock-проекты и не пишет
о них в лог. Подсказка флага называет оба трекера.

**A21.** `roles/implementer/role.md` описывает работу по конфликту, в allow
добавлен `git merge`; `git fetch`, `rebase` и `reset` не добавлены.

**A22.** `scripts/jira-workflow.sh` заводит статус `Done` и переходы
`Approved → Done`, `Approved → Ready`, `Approved → Blocked`, `Blocked → Approved`.

**A23.** Тесты с поддельной forge покрывают: открытие, слияние, закрытие,
конфликт, возврат в `Approved` без второго PR, повторное открытие после
`pr-closed`, повторный проход без дублей, ветку без коммитов, проект без forge,
уборку с пропуском грязной папки и чужого трекера.

**A24.** Живая проверка на GitHub: пустой репозиторий под учёткой `kao73`,
третий проект в `projects.yaml`, одна задача проходит `Ready → … → Approved →`
PR открыт `→` слит руками `→ Done`, папка убрана. Записано в
`docs/notes/stage-5-pr.md`.

**A25.** `gofmt -l .` пуст, `go build ./...`, `go vet ./...`, `go test ./...`
зелены; `smoke.sh` на файловом полигоне проходит.

# Constraints and invariants

- Решения принимает код, а не промпт: маршрут PR-прохода живёт в `workflow.yaml`.
- Агент не видит графа и в трекер не пишет.
- Секретов в репозитории нет: токен forge — только из окружения.
- Сеть у роли не расширяется: фетчит и пушит раннер.
- Строгий разбор YAML сохраняется.
- Язык документов русский, ключи конфигов английские.

# Decisions

- Живая проверка делается сейчас, на пустом репозитории GitHub, а не откладывается
  до шага 5: иначе шаг 5 начался бы с двумя неизвестными разом — новым проектом
  и непроверенным сетевым кодом.
- `tracker` и `forge` кладутся в `projects.yaml`, хотя оба машинные по природе.
  Шаг «конфигурация по машинам» отложен владельцем до момента перед шагом 5;
  перенос этих ключей войдёт в него. Долг записан здесь и в отчёте шага.
- Владелец и имя репозитория для forge выводятся из `repo_url`, а не задаются
  отдельным ключом: два места для одного факта однажды разойдутся.
- Системный проход подписывает свои записи собственным `run_id`, как прогон
  роли: маркер без него невалиден, а разбирать проход по логам надо так же,
  как прогон.
