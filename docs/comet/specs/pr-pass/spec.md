# PR-проход: офис открывает, человек сливает

Полное поведение способности после архивации изменения.

## Граница ответственности

Сливает человек. Офис открывает pull request, следит за ним и убирает за собой.

Авто-слияния нет. Ветка уезжает в `origin` как и раньше — это делает раннер
на своём проходе, не агент.

## Маршрут описан графом, а не кодом

PR-проход задан блоком `pr` в `workflow.yaml`:

```yaml
pr:
  role: office        # имя, которым подписаны маркеры прохода
  from: Approved      # откуда проход берёт задачи
  merged: Done        # PR слит
  conflict: Ready     # ветка не сливается — это работа, а не провал
  closed: Blocked     # PR закрыт без слияния — это разговор с человеком
```

`office` не кладётся в `roles:` и в `tick_order`. Иначе валидатор потребует её
в порядке обхода, а обход полез бы за `roles/office/role.yaml`, которого нет
и не будет: у прохода нет агента.

`Workflow.Role("office")` отдаёт поток с `reads_from = pr.from`; `Order()` его
не называет. Имени `office` в коде раннера нет — оно приходит из конфигурации.

`Approved` перестаёт быть терминальным: теперь это «PR открыт». Терминальный
статус — `Done`.

## Проект без forge

Оба полигона смотрят в локальный bare-репозиторий, forge у них нет.

Такой проект живёт по тому же графу: проход переводит задачу из `pr.from`
сразу в `pr.merged` и пишет `event:pr-skipped` — не `merged`, потому что слияния
не было.

Проверка конфликта идёт всё равно: она локальная и сети не требует.

Терминальность остаётся свойством графа: файловый полигон и `smoke.sh`
не ломаются.

## Проекты и трекеры

Проект в `projects.yaml` обязан назвать свой трекер ключом `tracker`
(`mock` или `jira`): одна и та же задача не живёт разом в файловом трекере
и в JIRA.

Раннер работает только с проектами трекера, названного флагом `--tracker`.
Проекты другого трекера в обход не попадают и в логе не упоминаются.

Подсказка флага `--tracker` называет оба доступных трекера; сообщение
о неизвестном трекере — тоже.

Ключ `tracker`, как и `forge`, машинный по природе и переедет
в `projects.local.yaml` вместе с отложенным шагом «конфигурация по машинам».

## Интерфейс forge

```go
OpenPR(project, branch, base, title, body string) (url string, err error)
PRState(url string) (open | merged | closed, err error)
```

`Mergeable` в интерфейсе нет: конфликт считается локально, и второй forge
обойдётся дешевле.

Первая реализация — GitHub через REST. Токен берётся из `GITHUB_TOKEN`, того же,
которым раннер пушит.

Какой forge у проекта, говорит ключ `forge` в `projects.yaml`. Ключ временный:
он машинный по природе и переедет в `projects.local.yaml` вместе с отложенным
шагом «конфигурация по машинам».

Владелец и имя репозитория выводятся из `repo_url`, а не настраиваются отдельно:
два места для одного факта разошлись бы.

## Конфликт считается локально

`git merge-tree --write-tree` по bare-клону: `origin/<ветка задачи>` против
`origin/<default_branch>`.

Локальной ссылки на ветку задачи может не быть — берётся `origin/`, потому что
клон фетчится на каждом обращении.

Конфликт → задача в `pr.conflict`, запись `event:merge-conflict`, `attempts`
не тратится: разрешать конфликт — это работа, а не провал прогона.

Проверка идёт перед открытием PR и на каждом проходе по открытым.

Конфликт открытый PR не закрывает: задача уходит на доработку, а тот же PR
переиспользуется, когда она вернётся в `pr.from`.

Про открытый pull request запись говорит, только когда он есть. Конфликт бывает
найден и до открытия — тогда обещание «PR подхватит задачу» было бы враньём.

## Состояние PR выводится из переписки

Состояние берётся по **последней** записи роли `pr.role` из семейства
{`pr-opened`, `pr-closed`}.

Не по факту наличия `pr-opened` в истории: PR, закрытый руками, увёл бы задачу
в `Blocked`, ответ человека вернул бы её в `Approved`, и второй PR не открылся
бы никогда.

`merge-conflict` и `merged` в семейство не входят. После конфликта последней
остаётся `pr-opened`, и тот же PR переиспользуется.

## Что делает системный проход

Проход идёт в `tick`, после разбора ответов человека, и не занимает роли.

Задача в `pr.from` без записи семейства или с последней `pr-closed` →
проверка конфликта, затем `OpenPR`.

Тело PR — `brief.md` изменения плюс последний отчёт о прогоне. `brief.md`
читается из bare-клона (`git show origin/<ветка>:<путь>`), а не из worktree:
папки может не быть. Отчёт читается из переписки тикета — в git его нет вовсе.

Имя роли у отчёта не спрашивается: задачу в очередь прохода привёл именно
последний отчёт, кто бы его ни писал.

Задача, пришедшая мимо аналитика (`Backlog → Ready`), каталога изменения не имеет:
тогда телом идут тема и описание тикета.

Ссылка на PR — комментарий с маркером `event:pr-opened` и URL в теле. Интерфейс
трекера не меняется.

Маркер отчёта в тело pull request не идёт: маркер — разметка для раннера,
а pull request читают люди.

Ветка без коммитов (GitHub откажет открыть PR) → `pr.closed` и записка человеку.
Это аномалия, а не падение тика.

Задача с открытым PR → `PRState`: `merged` → `pr.merged` и `event:merged`;
`closed` без слияния → `pr.closed`, `event:pr-closed` и человек.

Ответ человека на `pr-closed` возвращает задачу в `pr.from` штатным механизмом,
и PR открывается заново. Работу, которая не годится, человек двигает в `Ready`
руками — как с любой ролью.

Записи офиса не обрывают серий рабочих ролей: серии считаются по роли, а роль
у этих записей своя.

## Клон нужен без рабочей папки

`merge-tree` и `git show` требуют заведённого и свежего bare-клона, а до этого
изменения его заводила только подготовка worktree.

`Workspaces.Repo(имя проекта, его описание)` заводит и освежает клон
без worktree.

## Уборка рабочих папок

Уборка переезжает из прогона в системный проход. Снос из `work()` уходит.

Идёт она **от папок, а не от задач**: `Workspaces.List()` — единицы записей,
просеянных списком проектов своего трекера. В `${OFFICE_HOME}/repos` лежат клоны
обоих полигонов, и проход `--tracker jira` не вправе трогать папки mock-проектов.

По каждой папке спрашивается статус её задачи; терминальный → `Remove` под
замком. Занятая папка пропускается.

Не `List(project, [Done])`: в живом проекте `Done` растёт вечно.

**Грязная папка не сносится**, а пропускается с записью в лог. Раньше снос стоял
сразу за успешным пушем и был его защитой; у системного прохода такой защиты нет,
а `Remove` — это `worktree remove --force`. Убирает такую папку человек,
`runner worktree rm --force`: без флага команда откажется и объяснит, почему.

Уборка покрывает и задачу, которую человек перевёл в терминальный статус руками.

`Workspaces.TryLock(запись из List)` берёт замок, не создавая папки: путь
к ней уже известен из обхода, и выводить его заново из конфигурации проекта
хозяйству папок не по чему.

Папка теперь живёт до слияния, то есть неделю человеческого времени. На 3–5
задачах это ничего не стоит.

## Роль implementer и конфликт

Контекст говорит роли, что задача вернулась с конфликтом.

Тогда роль сливает `origin/<default_branch>` в ветку — он уже принесён, сеть
не нужна, — разрешает конфликт, прогоняет тесты и завершает `done`
с `next_owner: reviewer`.

В allow добавляется `git merge`. `git fetch` не добавляется: у роли нет ни сети
к forge, ни токена, а фетчит раннер. `rebase` и `reset` не добавляются: история
ветки общая.

Ревьюер разбирает слияние как обычную работу.

## Workflow полигона

Статус `Done` заводит `scripts/jira-setup.sh`, а `scripts/jira-workflow.sh` ставит
под него шаг и добавляет переходы `Approved → Done`, `Approved → Ready`,
`Approved → Blocked` и `Blocked → Approved`.

Без последнего ответ человека на `pr-closed` через штатный unblock не сработал
бы.

## Живая проверка

Реализация forge проверена не только поддельной: пустой репозиторий на GitHub,
отдельный проект в `projects.yaml` с `forge: github`, и одна задача, прошедшая
`Ready → … → Approved →` PR открыт `→` слит человеком `→ Done` с убранной папкой.

Токен берётся из окружения на время прогона и в репозиторий не попадает.

Что вышло, записано в `docs/notes/stage-5-pr.md`.
