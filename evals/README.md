# evals/

Golden-кейсы для `cmd/eval-roles`: каждый — фикстура плюс постановка плюс
декларативные проверки исхода. Прогоняются `./bin/eval-roles`, см.
[docs/guide/development.md](../docs/guide/development.md), раздел «Golden-кейсы
ролей (eval-roles)».

Пути `roles/…` ниже, как и везде в документации, — от корня офиса
(`office/` в этом репозитории), а не от корня репозитория; подробнее —
`docs/DESIGN.md`, §2.5.

## Структура кейса

```
evals/<role>/<case-id>/
  fixture/       рабочая папка роли: копируется во временный git-репозиторий
                 и коммитится одним коммитом перед прогоном
  task.md        постановка задачи, как её увидит роль
  expect.yaml    ожидаемый исход и список проверок
```

`<role>` обязан быть именем настоящей роли из `roles/`, а `role:` внутри
`expect.yaml` — совпадать с именем каталога `<role>`. `fixture/` не может
быть пустым каталогом: `eval-roles` коммитит его как есть, а `git commit` на
пустом дереве проваливается.

**Известное ограничение — reviewer без базовой ветки.** `materializeFixture`
кладёт всю фикстуру одним коммитом, а `runRoleAgent` вызывает `run-agent` без
`--base` — диффа для просмотра нет вовсе. Кейсы `evals/reviewer/*`, чьи
`task.md` говорят «review this change», сейчас оцениваются в конфигурации,
которой в проде не бывает (`roles/reviewer/role.md` строит разбор вокруг
`git diff <база>...HEAD`). Исправление — второй коммит в фикстуре плюс
`--base` в `invoke.go` — не сделано.

Следствие для `evals/reviewer/capability-spot-defect`: различение теперь на
`next_owner: implementer`, но раз диффа нет, ревьюер, вернувший работу автору
по совсем другой причине («не вижу, что изменилось — покажите дифф»), тоже
даёт `done` + `next_owner: implementer` и слабый grep на «A1» (реальный id
критерия приёмки, не литеральный текст постановки) его не отсеет. Остаточный
риск ложного PASS не по сути кейса — сузился с round 2 (там ложным PASS было
и одобрение), но не закрыт.

## expect.yaml

```yaml
role: implementer
checks:
  - kind: outcome
    expect: done              # done | needs_human | blocked | failed | split
    next_owner: implementer   # необязательно — сверяется с обязательным полем
                              # результата роли (roles/*/role.md, «Выход»)
  - kind: diff_scope
    allow: ["calc.go", "docs/changes/_manual/**"]  # "**" — любое число сегментов
  - kind: fixture_tests
    command: "go test ./..."  # выполняется внутри фикстуры через `sh -c`,
                              # таймаут — 5 минут, не настраивается
```

`outcome`-проверки на `needs_human`/`split` берут ещё пару полей — оба
проверяются только при этом `expect` (LoadCase отвергнет их при любом
другом, тем же приёмом, что и неизвестный `expect`):

```yaml
  - kind: outcome
    expect: split
    questions_not_empty: true # только вместе с needs_human или split
    children_count_min: 2     # только вместе с split, минимум 2 — минимум
                              # элементов в split.children[], не точное
                              # число; 1 или меньше отвергается загрузкой
                              # (непустой список и так гарантирован контрактом)
```

| kind | Проверяет | Обязательные поля |
|---|---|---|
| `outcome` | `Result.Outcome` роли совпадает с `expect`; если задан `next_owner` — ещё и `Result.NextOwner` с ним; если задан `children_count_min` (только при `expect: split`) — ещё и что элементов `split.children[]` не меньше | `expect` |
| `diff_scope` | всё, что роль изменила (закоммиченное и нет), укладывается в `allow` | — (пустой `allow` — законный запрет любых изменений) |
| `fixture_tests` | команда внутри фикстуры выходит с кодом 0 в течение 5 минут | `command` |
| `llm_judge` | зарезервирован, обработчика ещё нет — любой кейс с ним всегда `failed` (не `errored`: `dispatchCheck` намеренно не считает промах диспетчера инфраструктурной бедой) | — |

`LoadCase` проверяет `expect.yaml` при загрузке: неизвестный `kind` и
пропущенные обязательные поля — это ошибка загрузки (`errored` без единого
платного прогона роли), а не повод тратить прогон на то, что было предрешено
опечаткой.

## Что делает кейс полезным

Зелёный кейс ничего не доказывает сам по себе — доказывает то, что он умеет
и краснеть на настоящей ошибке. Перед тем как считать новый кейс готовым:

1. **Фикстура несёт настоящую проблему**, которую роль обязана заметить или
   исправить — не декоративный код. Пример: `implementer/capability-basic-bugfix`
   — `calc.go` содержит реальный баг, а `fixture_tests: go test ./...` его ловит.
2. **Эскалационный кейс несёт то, на что ссылается его task.md.** Если
   постановка говорит «один из документов утверждает X», в `fixture/` обязан
   лежать документ, реально утверждающий X — иначе кейс проверяет не конфликт
   постановки с документом, а исчезновение самой информации, что не то же самое.
3. **Различение «роль пришла к верному выводу» или «к неверному» — задача
   `next_owner`, не grep по свободному тексту.** У ролей уже есть типизированный,
   обязательный ответ на этот вопрос (`roles/*/role.md`, раздел «Выход») —
   `next_owner: implementer` значит «нашёл, что чинить», `next_owner: human` —
   «одобрил». `evals/reviewer/capability-spot-defect/expect.yaml` в round 1
   пытался различать это одним grep по словам-триггерам (`grep -qi 'ошиб'`
   совпадёт и с «ошибка найдена», и с «ошибок **не** найдено»), а в round 2 —
   парой позитивного/негативного grep, но позитивная и негативная
   альтернативы буквально пересекались как подстроки («некорректн» внутри
   «корректно»). У grep нет границ слова и нет понимания отрицания — не
   пытайтесь различать вывод роли этим слоем, используйте `next_owner`.
   Свободный текст (`grep`) годится только как слабая, не обязанная быть
   точной подсказка «разбор был не мимо темы» — см. пример выше.
4. **Демонстрация красного сигнала не требует реальных денег.** Подмените
   `EVAL_ROLES_RUN_AGENT_BIN` на `cmd/eval-roles/testdata/fakeagent` (`go build`
   его отдельно) и заставьте роль «соврать» через `FAKE_AGENT_RESULT` — так
   доказывается, что проверка действительно способна провалить кейс, без
   платного прогона настоящей роли. Пример — `TestEvaluateCaseCatchesUnfixedBug`
   и `TestEvaluateCaseSpotDefectDistinguishesFoundVsMissed` в
   `cmd/eval-roles/run_test.go`.
