# evals/

Golden-кейсы для `cmd/eval-roles`: каждый — фикстура плюс постановка плюс
декларативные проверки исхода. Прогоняются `./bin/eval-roles`, см. README.md
репозитория, раздел «Golden-кейсы ролей (eval-roles)».

## Структура кейса

```
evals/<role>/<case-id>/
  fixture/       рабочая папка роли: копируется во временный git-репозиторий
                 и коммитится одним коммитом перед прогоном
  task.md        постановка задачи, как её увидит роль
  expect.yaml    ожидаемый исход и список проверок
```

`<role>` обязан быть именем настоящей роли из `roles/`, а `expect.yaml`'s
`role:` — совпадать с именем каталога `<role>`. `fixture/` не может быть
пустым каталогом: `eval-roles` коммитит его как есть, а `git commit` на
пустом дереве проваливается.

## expect.yaml

```yaml
role: implementer
checks:
  - kind: outcome
    expect: done              # done | needs_human | blocked | failed
    questions_not_empty: true # только вместе с needs_human
  - kind: diff_scope
    allow: ["calc.go", "docs/changes/_manual/**"]  # "**" — любое число сегментов
  - kind: fixture_tests
    command: "go test ./..."  # выполняется внутри фикстуры через `sh -c`
```

| kind | Проверяет | Обязательные поля |
|---|---|---|
| `outcome` | `Result.Outcome` роли совпадает с `expect` | `expect` |
| `diff_scope` | всё, что роль изменила (закоммиченное и нет), укладывается в `allow` | — (пустой `allow` — законный запрет любых изменений) |
| `fixture_tests` | команда внутри фикстуры выходит с кодом 0 | `command` |
| `llm_judge` | зарезервирован, обработчика ещё нет — любой кейс с ним всегда errored | — |

`LoadCase` проверяет `expect.yaml` при загрузке: неизвестный `kind` и
пропущенные обязательные поля — это ошибка загрузки (`errored` без единого
платного прогона роли), а не повод тратить прогон на то, что было предрешено
опечаткой.

## Что делает кейс полезным

Зелёный кейс ничего не доказывает сам по себе — доказывает то, что он умеет
и краснеть на настоящей ошибке. Перед тем как считать новый кейс готовым:

1. **Фикстура несёт настоящую проблему**, которую роль обязана заметить или
   исправить — не декоративный код. Пример: `implementer/capability-basic-bugfix`
   — `calc.go` содержит реальный баг, а `fixture_tests: go test ./...` его ловит.
2. **Эскалационный кейс несёт то, на что ссылается его task.md.** Если
   постановка говорит «один из документов утверждает X», в `fixture/` обязан
   лежать документ, реально утверждающий X — иначе кейс проверяет не конфликт
   постановки с документом, а исчезновение самой информации, что не то же самое.
3. **`fixture_tests`-проверка по свободному тексту (`.agent/result.json`)
   отличает верный вывод от неверного, а не просто ловит ключевое слово.**
   `grep -qi 'ошиб'` совпадёт и с «ошибка найдена», и с «ошибок **не**
   найдено» — реальный случай, найденный внешним ревью и исправленный в
   `evals/reviewer/capability-spot-defect/expect.yaml`. Проверяйте фразу целиком
   или комбинируйте позитивный и негативный grep.
4. **Демонстрация красного сигнала не требует реальных денег.** Подмените
   `EVAL_ROLES_RUN_AGENT_BIN` на `cmd/eval-roles/testdata/fakeagent` (`go build`
   его отдельно) и заставьте роль «соврать» через `FAKE_AGENT_RESULT` — так
   доказывается, что проверка действительно способна провалить кейс, без
   платного прогона настоящей роли. Пример — `TestEvaluateCaseCatchesUnfixedBug`
   и `TestEvaluateCaseSpotDefectDistinguishesFoundVsMissed` в
   `cmd/eval-roles/run_test.go`.
